# Дополнительные базы данных

Кроме основной базы стенда (`postgres`) namespace может поднимать другие
кластеры PostgreSQL — например, собственную базу observer'а. Такой кластер
**объявляется в конфигурации workspace**, и добавление ещё одного не требует
изменений в лончере.

## Объявление

```yaml
# workspace-v1.yml
databases:
  - id: billing-postgres        # id зависимости и имя контейнера
    image: postgres:17.5        # запасной образ; запись в бандле важнее
    user: billing               # POSTGRES_USER, по умолчанию postgres
    db: billing                 # POSTGRES_DB, по умолчанию = user
    port: 14777                 # публикуется в desktop-режиме; 0 — не публиковать
    memoryLimit: 256m
    volumeBase: billing_pg      # основа имени тома; по умолчанию = id
    requiredBy: billing         # поднимать только если это приложение есть
    settings:                   # серверные настройки, попадают в -c key=value
      shared_buffers: 64MB
      work_mem: 8MB
```

Минимальная рабочая запись — один `id`: остальное берётся из умолчаний самого
образа PostgreSQL.

**Пароля в конфигурации нет и не будет.** Эти кластеры доступны только внутри
docker-сети namespace и в server-режиме наружу не публикуются, поэтому лончер
выдаёт им пароль по имени пользователя. Конфигурация workspace лежит в git — это
не место для учётных данных.

Поменять пароль задним числом нельзя: `POSTGRES_PASSWORD` образ читает только при
первичной инициализации кластера, поэтому на уже созданной базе новый пароль
получит сервис, а сама база останется со старым.

## Что объявленный кластер получает автоматически

Ровно то же, что основная база стенда:

* **пин версии** — бандл, поднимающий мажор на существующих данных,
  придерживается и показывается как предложение обновиться;
* **счётчик поколений тома** — `billing_pg2`, после миграции `billing_pg3`;
  имя тома и есть способ найти данные, поэтому `volumeBase` менять нельзя;
* **раскладку данных по мажору** — явный `PGDATA` до 17, родительский монтаж
  с 18;
* **миграцию и откат**:

```bash
citeck deps                              # кластер в общем списке
citeck deps upgrade billing-postgres     # дамп → новый том → проверка → коммит
citeck deps rollback billing-postgres    # вернуться на сохранённый том
```

Кластеры независимы: у каждого свой пин, своё поколение тома и свой каталог
дампа; миграция одного не трогает данные другого.

## requiredBy

Если база объявлена «для» приложения, она генерируется только там, где это
приложение есть. Так собственная база observer'а не появляется на стендах без
observer'а. Без `requiredBy` кластер поднимается везде, где используется этот
workspace.

Приложение и его база — владелец и компаньон: если владельца добавляют в
`detachedApps` шаблона, базу нужно добавить туда же, иначе на стенде с
выключенным сервисом поднимется одна база (см.
[что стартует на стенде](app-startup-and-detach.md)).

## Встроенные умолчания

Лончер знает базу observer'а (`observer-postgres`) без объявления: её настройки
зашиты как умолчания. Запись в `databases:` с тем же `id` переопределяет их
**по полям** — можно поменять только лимит памяти и оставить остальное.

Основная база стенда (`postgres`) через эту секцию не настраивается и не
переопределяется: у неё собственное имя тома, init-скрипты по датасорсам
приложений и пин, засеянный из реальных данных в поле.
