# Дополнительные базы данных и хранилища

Кроме основной базы стенда (`postgres`) namespace может поднимать другие
кластеры PostgreSQL и векторные хранилища Qdrant — например, собственную базу
observer'а, которую объявляет сам workspace (см. [Observer](observer.md)). Такой сервис **объявляется в `additionalApps:` конфигурации
workspace** с указанием типа, и добавление ещё одного не требует изменений в
лончере.

## Типы записей

`additionalApps:` — список кастомных сервисов. Запись **без `type`** остаётся
тем, чем была: произвольный контейнер (образ, env, cmd, тома, пробы), который
лончер просто запускает. Запись **с `type`** — сервис, который лончер знает:
он регистрируется в реестре зависимостей и получает пин версии, том со
счётчиком поколений, миграцию мажора и откат.

Тип полностью определяет набор настроек записи: она читается как своя
структура и ничего больше. Ключи от другой формы просто не читаются — конфиг
это объявление, а не скрипт, и падать из-за лишнего ключа значило бы ломать
стенды из-за опечатки.

```yaml
# workspace-v1.yml
additionalApps:
  - name: billing-postgres      # id зависимости и имя контейнера
    type: POSTGRES
    image: postgres:17.5        # запасной образ; запись в бандле важнее
    user: billing               # POSTGRES_USER, по умолчанию postgres
    db: billing                 # POSTGRES_DB, по умолчанию = user
    password: ${secret:billing-db}  # POSTGRES_PASSWORD, по умолчанию = user
    port: 14777                 # публикуется в desktop-режиме; 0 — не публиковать
    memoryLimit: 256m
    volumeBase: billing_pg      # основа имени тома; по умолчанию = name
    settings:                   # серверные настройки, попадают в -c key=value
      shared_buffers: 64MB
      work_mem: 8MB

  - name: billing-qdrant
    type: QDRANT
    memoryLimit: 1g
    httpPort: 16333
    grpcPort: 16334
```

Минимальная рабочая запись — `name` и `type`: остальное берётся из умолчаний
самого образа.

**Пароль** — ключ `password:`, и задавать его нужно **ссылкой на секрет**
namespace, `${secret:<id>}` (см. [Секреты workspace](workspace-secrets.md)):
тогда и база, и сервис, который к ней подключается, читают одно значение.
Без ключа пароль равен имени пользователя. Если у namespace нет значения
секрета, кластер **не поднимается** — вместе со всем, что от него зависит:
база, инициализированная с пустым паролем, так бы его и сохранила.

Поменять пароль задним числом нельзя: `POSTGRES_PASSWORD` образ читает только при
первичной инициализации кластера. Поэтому значение секрета namespace сохраняет у
себя один раз и дальше не меняет — правка умолчания в workspace до уже
созданной базы не доходит.

## Кто решает, что сервис существует

**Бандл — тем, что называет его образ.** Это то же правило, по которому на
стенде появляются `qdrant` и сам `observer`: есть ли сервис, решает релиз,
который стенд запускает.

```yaml
# бандл
dependencies:
  billing-postgres:
    image: postgres:18.6
```

Запись в `additionalApps:` отвечает только на вопрос «как он настроен».
Поэтому на стенде, чей бандл не поставляет сервис, не появится и его база —
никакого отдельного выключателя держать не нужно. Запись, назвавшая
собственный `image:`, поднимет сервис и без записи в бандле: это запасной
вариант для стенда, который пинит версию у себя.

Приложение и его база — владелец и компаньон: если владельца добавляют в
`detachedApps` шаблона, базу нужно добавить туда же, иначе на стенде с
выключенным сервисом поднимется одна база (см.
[что стартует на стенде](app-startup-and-detach.md)). Запускаются они тоже по
отдельности: `citeck start observer` поднимет сервис, который будет ждать свою
базу в `DEPS_WAITING`, пока не запустят её.

## Что объявленный сервис получает автоматически

Ровно то же, что основная база стенда:

* **пин версии** — бандл, поднимающий мажор на существующих данных,
  придерживается и показывается как предложение обновиться;
* **счётчик поколений тома** — `billing_pg2`, после миграции `billing_pg3`;
  имя тома и есть способ найти данные, поэтому `volumeBase` менять нельзя;
* **раскладку данных по мажору** — явный `PGDATA` до 17, родительский монтаж
  с 18;
* **миграцию и откат**:

```bash
citeck deps                              # кластер в общем списке
citeck deps upgrade billing-postgres     # дамп → новый том → проверка → коммит
citeck deps rollback billing-postgres    # вернуться на сохранённый том
```

Сервисы независимы: у каждого свой пин, своё поколение тома и свой каталог
дампа; миграция одного не трогает данные другого. У Qdrant правило вендора
своё — совместимость хранилища ровно через один минор, поэтому бандл, прыгающий
дальше, придерживается с предложением промежуточного шага.

План миграции и откат объявленный кластер получает **по своему виду**: у
`type: POSTGRES` — тот же дамп/восстановление, что у основной базы, у
`type: QDRANT` — та же копия тома, что у встроенного хранилища, каждый со своим
id. Журнал прерванной миграции кластера, который активный workspace больше не
объявляет, лончер не трогает: откатить его можно, вернувшись на workspace, где
кластер объявлен. (До 2.15.0 объявленный кластер показывался как обновляемый,
но `citeck deps upgrade` на нём падал внутренней ошибкой — плана для
неизвестного id не было.)

## Встроенных баз нет

Лончер не знает ни одной дополнительной базы сам: база observer'а — такая же
объявленная запись в конфигурации workspace, как любая другая. Встроенное у
лончера осталось только одно — векторное хранилище `qdrant`, которое запись с
тем же `name` и `type: QDRANT` переопределяет **по полям** (например, только
лимит памяти).

Основная база стенда (`postgres`) через эту секцию не настраивается и не
переопределяется: у неё собственное имя тома, init-скрипты по датасорсам
приложений и пин, засеянный из реальных данных в поле. Запись с таким именем
отклоняется при загрузке конфигурации.
