# Хранение контента: база данных или S3

Файлы, которые пользователи загружают в Citeck (вложения, документы, их
версии), хранит сервис ecos-content (`content`). Где именно он их хранит,
выбирается для каждого namespace — в интерфейсе это поле **«Способ хранения
контента»**:

| Вариант | `namespace.yml` | Что это |
|---|---|---|
| **База данных** (по умолчанию) | ключа нет или `type: DB` | файлы лежат в PostgreSQL стенда — так работают все namespace, созданные до появления выбора |
| **S3 (SeaweedFS)** | `type: S3` | файлы лежат в S3-хранилище, которое Launcher поднимает рядом со стендом и сам подключает к ecos-content |

```yaml
# namespace.yml
contentStorage:
  type: S3
```

Отсутствие ключа означает «База данных», и Launcher его не дописывает: у
существующих namespace файл конфигурации не меняется, `apiVersion` тоже.
Регистр значения не важен (`s3` — то же, что `S3`); неизвестное значение —
ошибка конфигурации. `type: S3` нельзя сочетать с блоком `s3:` (подключение к
**внешнему** S3, `citeck setup s3`): оба решают, куда ecos-content пишет файлы,
и такая конфигурация отклоняется.

Вариант S3 есть только у Enterprise: в Community нет ecos-content.

## Где выбирается

* **Desktop** — диалог создания и редактирования namespace, вкладка
  «Основное». При создании по умолчанию выбрана база данных, и выбор
  отправляется всегда — в том числе «База данных». Новый namespace получает
  способ хранения только из этого выбора: если `namespaceTemplates[].config`
  шаблона задаёт `contentStorage`, значение игнорируется (с предупреждением в
  логе) — необратимый выбор делает оператор, а не шаблон. У namespace с
  внешним S3 (блок `s3:`) вариант S3 в диалоге редактирования показан
  недоступным.
* **Server** — `citeck install` спрашивает способ хранения после выбора релиза,
  если для этого релиза S3 доступен (по умолчанию — база данных); у
  существующего namespace — `citeck setup content-storage` (настройка видна,
  только если в бандле есть ecos-content). Эта настройка работает только при
  запущенном демоне: новая конфигурация уходит в него через
  `PUT /api/v1/config`, и демон сам проверяет правила, снимает с хранилища
  отметку «остановлено» и применяет конфигурацию. `citeck setup history --undo`
  отказывается откатывать запись, которая изменила бы способ хранения.
* **API** — поле `contentStorage` (`"DB"` | `"S3"`) при создании и
  редактировании namespace, а также полная конфигурация через
  `PUT /api/v1/config`.

Правила ниже проверяет сам Launcher на каждом из этих путей. Правка
`namespace.yml` руками, в обход Launcher, их не проходит — переключать способ
хранения так не нужно.

## Когда вариант S3 доступен

Доступность определяется бандлом, на котором стоит namespace, и конфигурацией
workspace. Бандл читается из локальной копии, без обращения к git — диалог
показывает ровно то, что потом примет сохранение.

| Причина | Что видно | Что это значит |
|---|---|---|
| `NO_CONTENT_APP` | вариант S3 **скрыт** | в бандле нет ecos-content (Community) — вопрос не стоит |
| `NO_PROVIDER_CONFIG` | вариант недоступен, с подсказкой | в конфигурации workspace нет блока `contentStorage.s3` (или он неполон) |
| `NO_PROVIDER_APP` | то же | блок называет приложение, которого нет среди `additionalApps` workspace (или оно выключено) |
| `PROVIDER_CONFLICT` | то же | имя хранилища занято приложением платформы (встроенным или webapp, который workspace перечисляет в `webapps:` и который есть в бандле — генератор оставит его, а запись пропустит), или хранилище само зависит от ecos-content (зависимость ecos-content от него замкнула бы цикл) |
| `NO_PROVIDER_IMAGE` | то же | ни бандл, ни запись в workspace не называют образ хранилища — этот релиз SeaweedFS не поставляет |
| `BUNDLE_UNRESOLVED` | то же | бандла нет в локальной копии репозитория — проверить нечего, и выбрать S3 на нём нельзя |

Сохранение с недоступным вариантом отклоняется: HTTP 409
`CONTENT_STORAGE_UNAVAILABLE` с той же причиной, текстом на языке Launcher.
Последний случай строже, чем проверка версии лаунчера: S3 нельзя отменить
(следующий раздел), поэтому непроверенный выбор не принимается.

## Только в одну сторону

* **База данных → S3 — можно**: в диалоге редактирования, через
  `citeck setup content-storage`, через `PUT /api/v1/config`.
* **S3 → база данных — нельзя никогда**: HTTP 409 `CONTENT_STORAGE_DOWNGRADE`.
  Полная конфигурация, в которой ключа `contentStorage` нет, тоже считается
  возвратом к базе данных и отклоняется. Файлы, уже записанные в S3, в базе
  отсутствуют, и Launcher их никуда не переносит. Сохранённую конфигурацию
  Launcher для этой проверки читает так, чтобы S3 нельзя было потерять
  незаметно: если она не разбирается как YAML (ручная правка с синтаксической
  ошибкой), блок `contentStorage` ищется в тексте, а если её не удаётся
  прочитать вовсе, запись отклоняется (HTTP 500) — а не считается переходом
  «база данных → база данных».
* Файлы, загруженные **до** переключения на S3, Launcher тоже не переносит:
  они остаются там, куда были записаны.
* У namespace на S3 можно сменить бандл, только если на новом бандле S3
  по-прежнему доступен. Правка, которая не трогает ни способ хранения, ни
  бандл (переименование, настройки прокси и т. п.), проходит всегда — даже если
  конфигурация workspace с тех пор изменилась; такое состояние Launcher
  показывает отдельно (см. «Если подключить не получилось»).

## Что Launcher делает для namespace на S3

Хранилище — обычная запись `additionalApps` в конфигурации workspace
(`seaweedfs`), а блок `contentStorage.s3` называет её и описывает, как
ecos-content до неё достучаться. Для namespace на S3 Launcher делает три вещи.

**1. Хранилище стартует вместе с namespace.** Шаблон workspace держит
`seaweedfs` в `detachedApps`, чтобы namespace на базе данных за него не платил.
Для namespace на S3 это правило не действует: новый namespace поднимает
хранилище вместе с остальными приложениями. При переключении существующего
namespace с базы данных на S3 Launcher один раз снимает с хранилища отметку
«остановлено» и применяет конфигурацию — это часть того же действия оператора.
На обычной загрузке и `citeck reload` отметки не снимаются: хранилище,
остановленное оператором после переключения, остаётся остановленным (см. ниже).

**2. ecos-content ждёт хранилище.** В namespace на S3 ecos-content зависит от
хранилища и стартует после него. Больше в его конфигурации ничего не меняется:
у namespace на базе данных контейнер ecos-content байт в байт тот же, что и
раньше, и обновление Launcher его не пересоздаёт.

**3. Подключение в ECOS — один раз, автоматически.** Когда `gateway`,
`emodel`, `eapps`, `content` и само хранилище в состоянии RUNNING (статус
namespace целиком не важен — одно постороннее приложение может держать его в
STALLED), демон Launcher подключает ecos-content к хранилищу. Хранилище входит
в это условие потому, что переключить ecos-content на остановленный S3 —
значит сразу сломать любую загрузку файла. Он обращается к records API
шлюза напрямую, минуя прокси, и создаёт записи, имена которых строятся из имени
приложения-хранилища (`<app>` = `contentStorage.s3.app`):

| Запись | Что в ней |
|---|---|
| `emodel/secret@<app>-s3-credentials` | учётные данные: `accessKey` и значение `secretKey` этого namespace |
| `emodel/endpoint@<app>-s3` | адрес `url` и ссылка на секрет |
| `content/storage@<app>-s3` | хранилище типа S3: эндпоинт и `bucket` |
| `eapps/config@app/emodel$default-content-storage` | хранилище по умолчанию переключается на `content/storage@<app>-s3` |

Встроенные идентификаторы ecos-content (`content-storage-s3…`) не
используются. Выбор хранилища по умолчанию, сделанный администратором,
Launcher не перезаписывает никогда:

* хранилище по умолчанию указывает на **чужое** хранилище (не базу данных и не
  `content/storage@<app>-s3`) — «настроено администратором», Launcher в ECOS
  ничего не пишет;
* по умолчанию уже стоит его хранилище — «подключено»; Launcher только
  приводит свои секрет и эндпоинт к текущим значениям (см.
  [«Ключ S3 в ECOS»](#ключ-s3-в-ecos));
* хранилище `content/storage@<app>-s3` уже есть, а по умолчанию стоит база
  данных — значит, администратор вернул базу намеренно; хранилище по
  умолчанию Launcher не трогает (свои секрет и эндпоинт поддерживает так же).
  Исключение — переключение, которое Launcher начал сам и не довёл до конца
  (см. ниже);
* иначе существующие секрет и эндпоинт приводятся к текущим значениям,
  создаются **отсутствующие** записи, переключается хранилище по умолчанию, и
  результат перечитывается для проверки. Запись, на которую ECOS пока не может
  ответить (сервис записей ещё не зарегистрирован, нет ответа шлюза),
  повторяется в пределах того же 15-минутного окна; обычная ошибка ECOS сразу
  показывается как `error`.

Отметки «уже подключено» Launcher не хранит: решение каждый раз выводится из
состояния самой ECOS. Хранит он две вещи, и ни одна из них не вердикт: что
записал в свой секрет в последний раз (см. [«Ключ S3 в ECOS»](#ключ-s3-в-ecos))
и что **начал** переключение на своё хранилище и ещё не увидел его
подтверждения (поле `contentStorageSwitchPending` в состоянии namespace).
Отметка о переключении записывается перед первой записью в ECOS и стирается,
как только ECOS ответит вердиктом. Без неё сбой между созданием хранилища и
переключением (ответ 500, остановка namespace, перезапуск демона) выглядел бы
в ECOS ровно как «администратор вернул базу», и namespace навсегда остался бы
на базе данных, считая себя подключённым к S3; с ней следующий запуск просто
доводит переключение. Если
после такого сбоя администратор действительно хочет базу данных, пусть
переключит обратно уже после того, как Launcher подключит S3.

Существование записи Launcher определяет по атрибуту `_notExists`: ECOS
отвечает `true` только для записи, которой нет (и для сервиса записей, который
ещё не зарегистрирован), а для существующей не отвечает ничего — `false` она
не возвращает никогда. Готовность конфигурации определяется по её значению:
пока артефакт не развёрнут, значения нет. Значение, которое не является
объектом со строковым `ref`, Launcher не понимает и не перезаписывает — это
ошибка, а не «ничего не выбрано». Поэтому после восстановления снапшота или на пустой базе
подключение произойдёт снова, а на уже подключённом стенде — ничего не
изменит. Приложения ECOS разворачивают свои артефакты асинхронно, поэтому
перед записью Launcher дожидается, пока нужные записи станут доступны (опрос
раз в 15 секунд, до 15 минут). Пока идёт снапшот, миграция или откат
зависимости, подключение откладывается до следующего события. Проверка
выполняется один раз после каждого подъёма платформы: перезапуск любого из
нужных приложений (остановка namespace, восстановление снапшота, обновление)
запускает её снова, а уже подключённый стенд при этом не показывает
промежуточного «ожидания».

Состояние подключения видно на баннере дашборда и в строке
`Content storage:` команды `citeck status`:

| Состояние | Что значит |
|---|---|
| `pending` | ещё не все из `gateway`, `emodel`, `eapps`, `content` и хранилища в RUNNING. На остановленном namespace баннер не показывается, а `citeck status` пишет «проверяется при запуске»: признака «подключено» Launcher не хранит, поэтому после остановки и после перезапуска демона любой namespace на S3 читается как `pending` |
| `waiting` | Launcher ждёт, пока ECOS будет готова принять записи |
| `provisioning` | записи создаются |
| `connected` | ecos-content хранит новые файлы в S3 |
| `admin-managed` | хранилище по умолчанию выбрал администратор; Launcher его не трогает |
| `error` | подключение не удалось — текст ошибки рядом |

При ошибке Launcher повторяет попытку сам при следующем изменении статусов
приложений (не чаще раза в 5 минут); на баннере есть кнопка повтора, в API —
`POST /api/v1/namespace/content-storage/provision`.

## Ключ S3 в ECOS

Секрет `emodel/secret@<app>-s3-credentials` и эндпоинт `emodel/endpoint@<app>-s3`
— **записи Launcher**. При каждой проверке (один раз после каждого подъёма
платформы и по кнопке повтора) он приводит те из них, что есть, к текущим
значениям namespace: в секрете — `accessKey` и значение `secretKey` этого
namespace, в эндпоинте — `url` из `contentStorage.s3` и ссылка на этот секрет.
**Правка этих двух записей в ECOS вручную будет перезаписана.** Хранилище
`content/storage@<app>-s3` и хранилище по умолчанию Launcher не переписывает, а
если администратор сделал хранилищем по умолчанию своё (не базу данных и не
`content/storage@<app>-s3`), не пишет в ECOS вообще ничего — и в эти две
записи тоже.

Зачем. Ключ живёт в двух местах: в значении секрета namespace, с которым
запущен контейнер хранилища, и в базе ECOS, откуда его берёт ecos-content. Всё,
что даёт namespace **новый** ключ при старой базе, их разводит: снапшот,
восстановленный в новый namespace, и сброс секретов на desktop (генерируемый
ключ получает новое значение, см. [Секреты workspace](workspace-secrets.md)).
SeaweedFS берёт ключ только из окружения и в томе его не хранит, поэтому
хранилище сразу работает с новым ключом — а без обновления секрета в ECOS каждая
загрузка файла получала бы 403 при баннере «подключено».

Как Launcher понимает, что секрет устарел. Прочитать ключ обратно нельзя:
ECOS не отдаёт данные секрета ни атрибутом, ни запросом. Поэтому Launcher
запоминает свою последнюю запись — поле `contentStorageSecretWrite` в
состоянии namespace: ссылку на секрет, солёный хэш SHA-256 обоих ключей (не
сами ключи) и время изменения секрета `modified`, которое ECOS назвала сразу
после записи — и переписывает секрет, когда:

* такой отметки нет (новый namespace, в том числе созданный из снапшота;
  секрет, созданный вручную);
* хэш не совпадает с текущими ключами (сброс секретов, другой `accessKey`);
* `modified` в ECOS сдвинулся (секрет правили в ECOS, восстановили базу
  другого стенда);
* ECOS не сообщает `modified` — тогда при каждой проверке.

Актуальный секрет не переписывается: каждое сохранение секрета заново шифрует
данные, сдвигает `modified` и заставляет каждый экземпляр ecos-content
пересоздать S3-клиенты. Эндпоинт сравнивается напрямую — его `url` и ссылку на
секрет ECOS отдаёт.

Перезапускать ecos-content не нужно. После каждого сохранения секрета emodel
рассылает событие `secret-changed`; каждый экземпляр ecos-content по нему
закрывает хранилище, построенное на эндпоинте с этим секретом, и следующий
запрос строит S3-клиент заново — уже с текущими эндпоинтом и ключом.
Изменение эндпоинта действует так же, через `endpoint-changed`. Единственная
щель — доставка: очередь этих событий не сохраняется на диск, и ecos-content,
пропустивший событие (в этот момент был недоступен RabbitMQ или ZooKeeper),
работает со старым ключом до перезапуска: `citeck restart content`.

Ключ, изменённый на конкретном стенде в обход секретов namespace
(`citeck edit seaweedfs` с другим `AWS_SECRET_ACCESS_KEY`), Launcher **не
перезаписывает**: если ключа namespace нет ни в окружении, ни в командной
строке запущенного контейнера хранилища, Launcher не знает, какой ключ оно
проверяет, и оставляет секрет в ECOS как есть (в логе — предупреждение). Такой
ключ в ECOS меняют вручную.

Ошибка записи — состояние `error` с текстом «Не удалось обновить … в ECOS»;
повтор — как у остальных шагов.

## Остановка хранилища

`citeck stop seaweedfs` (или кнопка остановки в таблице приложений) на
namespace с S3 **не запрещена**: команда предупреждает в stderr и
останавливает хранилище, UI просит подтверждения. Пока хранилище остановлено,
загрузка и скачивание файлов в ECOS не работают. Уже запущенный ecos-content
продолжает работать, а при следующем старте будет ждать хранилище в
`DEPS_WAITING`, и namespace перейдёт в `STALLED`. Остановка запоминается как
решение оператора и переживает `citeck reload`; вернуть хранилище:

```bash
citeck start seaweedfs
```

## Если подключить не получилось

Проблемы генерации **никогда не мешают** стенду подняться: остальные
приложения стартуют как обычно, а проблема показывается на баннере
(не скрывается) и в `citeck status`.

| Проблема | Что случилось |
|---|---|
| `PROVIDER_NOT_GENERATED` | хранилище не попало в namespace: у namespace нет значения его секрета (например, хранилище секретов на desktop ещё заперто мастер-паролем) или нет приложения, от которого оно зависит. ecos-content в таком случае хранилище **не ждёт** — иначе он исчез бы из namespace вместе со всем, что от него зависит |
| `PROVIDER_CONFLICT` | хранилище нельзя подключить в том виде, в каком его описывает workspace: его имя занято приложением платформы, или оно (напрямую или через другие приложения, в том числе через `dependsOn` из `namespace.yml`) зависит от ecos-content. Такую зависимость Launcher не добавляет — цикл сломал бы генерацию всего namespace |
| `NO_PROVIDER_IMAGE`, `NO_PROVIDER_APP`, `NO_PROVIDER_CONFIG` | бандл или конфигурация workspace изменились так, что хранилища больше нет (см. таблицу доступности) |
| `NO_CONTENT_APP` | в namespace нет ecos-content |

## Конфигурация workspace

```yaml
# workspace-v1.yml
secrets:
  - generated: seaweedfs-s3          # ключ S3: свой у каждого namespace
    length: 40
  - generated: seaweedfs-jwt         # ключ подписи токенов SeaweedFS
    length: 48
additionalApps:
  - name: seaweedfs                  # без image: образ называет бандл
    kind: THIRD_PARTY
    cmd: [mini, -dir=/data, …, -disableHttp, -admin.ui=true, …]
    environments:
      AWS_ACCESS_KEY_ID: citeck
      AWS_SECRET_ACCESS_KEY: ${secret:seaweedfs-s3}
      WEED_JWT_SIGNING_KEY: ${secret:seaweedfs-jwt}   # и ещё три WEED_JWT_*
      WEED_ADMIN_USER: admin
      WEED_ADMIN_PASSWORD: ${ADMIN_PASSWORD}
      S3_BUCKET: ecos-content
    volumes: ["seaweedfs2:/data"]
    ports: ["8333:8333", "23646:23646"]
    # … probes, resources
contentStorage:
  s3:
    app: seaweedfs                   # запись additionalApps выше
    title: SeaweedFS                 # необязательно: название в подписи «S3 (SeaweedFS)»
    url: http://seaweedfs:8333       # адрес, как его видит ecos-content
    bucket: ecos-content             # = S3_BUCKET записи
    accessKey: citeck                # = AWS_ACCESS_KEY_ID записи
    secretKey: ${secret:seaweedfs-s3} # = AWS_SECRET_ACCESS_KEY записи
links:
  - name: SeaweedFS                  # admin UI на боковой панели (desktop)
    url: http://127.0.0.1:23646
    dependsOn: [seaweedfs]
```

* Пять полей `contentStorage.s3` обязательны (`title` — нет: без него в
  подписи варианта стоит имя приложения); блок, в котором чего-то не хватает
  или который не читается, считается отсутствующим (с предупреждением в логе)
  и не ломает остальную конфигурацию workspace.
* Обе половины описывают **одно** хранилище, и связывает их только файл:
  `url`, `bucket`, `accessKey` и `secretKey` должны совпадать с тем, с чем
  настроен контейнер. Эталонная копия этих блоков (секреты, запись, блок
  `contentStorage` и ссылка) лежит в репозитории Launcher,
  `internal/namespace/testdata/content-storage-workspace.yml`, и тесты
  генератора проверяют на ней это соответствие и правила раздела
  [«Защита хранилища»](#защита-хранилища) — держите копию и workspace
  одинаковыми.
* Образ хранилища берётся по обычному правилу записей `additionalApps`
  ([приоритет образов](config-layers.md)): запись в бандле
  (`dependencies.seaweedfs`) важнее собственного `image:` записи. Бандл, который
  образ не называет, хранилища не получает — и вариант S3 на нём недоступен.
* Оба ключа — **генерируемые** секреты namespace (см.
  [Секреты workspace](workspace-secrets.md)): значение создаётся при первой
  генерации namespace, своё у каждого стенда, и дальше не меняется; `secretKey`
  подставляется из той же копии, что и в контейнер. Опубликованного в
  workspace ключа, одинакового у всех, кто читает репозиторий, нет. Namespace,
  восстановленный из снапшота в новый namespace, получит новые значения, и
  Launcher перепишет новым ключом секрет в базе ECOS (см.
  [«Ключ S3 в ECOS»](#ключ-s3-в-ecos)).
* Лаунчеры, которые не знают `contentStorage`, ключ в конфигурации workspace
  игнорируют. Они же появились до генерируемых секретов и записи
  `generated:` пропускают: namespace, у которого значений ключей ещё нет,
  хранилища у такого Launcher не получает вовсе — оно не запускается с пустым
  ключом. У namespace, которому этот Launcher уже создал ключи, хранилище
  остаётся обычной записью `additionalApps` и продолжает работать: такой
  Launcher читает все сохранённые значения namespace. У namespace на S3 оно в
  состоянии namespace не отцеплено; у остальных шаблон его отцепляет.

## Защита хранилища

SeaweedFS (`weed mini`) — один процесс с несколькими серверами, и у каждого
свои порты. Что требует каждый из них:

| Порт | Что это | Доступ |
|---|---|---|
| 8333 | S3 | ключ `accessKey`/`secretKey`; анонимные запросы отклоняются |
| 8888 | HTTP API filer | закрыт: `-disableHttp` |
| 9340 | HTTP API volume-сервера | чтение и запись файла — только с токеном, подписанным ключом `seaweedfs-jwt` |
| 23646 | admin UI | логин администратора стенда |
| 9333 | master | открыт, только чтение: страница состояния и `/cluster/status` |
| 18333, 18888, 19333, 19340, 33646 | gRPC (S3, filer, master, volume, admin/worker) | **открыты** |

* **gRPC-порты не защищены**, и это известное ограничение: любой контейнер в
  сети namespace может подключиться к ним без учётных данных — в том числе
  к gRPC filer'а, через который читаются и пишутся файлы, и к 33646, где
  регистрируются фоновые worker'ы. Закрыть их можно только mTLS, а для него
  нужен `security.toml` с сертификатами, которые запись `additionalApps` с
  собой не принесёт. Без учётных данных отвечают и несколько страниц только для
  чтения: состояние master (`/` и `/cluster/status` на 9333), `/status`
  volume-сервера и проверки здоровья.
* **Снаружи** в server-режиме не опубликован ни один порт хранилища; на desktop
  опубликованы только 8333 и 23646, и только на 127.0.0.1.
* **Ключ S3** (`seaweedfs-s3`) — генерируемый, 40 символов. Он живёт и в
  базе ECOS: у namespace на S3 Launcher записывает его в секрет, с которым
  подключается ecos-content, и держит этот секрет в актуальном состоянии (см.
  [«Ключ S3 в ECOS»](#ключ-s3-в-ecos)).
* **Ключ подписи** (`seaweedfs-jwt`, 48 символов) подписывает токены, с
  которыми filer и volume-сервер принимают запросы к файлам, — один ключ на
  запись и чтение. В ECOS он не попадает, а хранилище не держит его в томе,
  поэтому новое значение (восстановление в новый namespace, сброс секретов на
  desktop) ничего не ломает.
* **Admin UI** пускает по логину `admin` и паролю администратора стенда — тому
  же, что у RabbitMQ и PgAdmin (на desktop — `admin`). Пароль, изменённый
  `citeck setup admin-password`, admin UI SeaweedFS получает при следующем
  `citeck reload`: контейнер пересоздаётся (файлы остаются в томе), а до этого
  действует старый пароль.
* Учётные данные передаются **только через окружение** контейнера. `weed mini`
  сохраняет свои флаги в `/data/mini.options`, то есть в том хранилища,
  который попадает в каждый снапшот, а переменные окружения не сохраняет: ни
  ключей, ни пароля в томе нет.
* В системном дампе (`citeck dump-system-info`) значения `AWS_SECRET_ACCESS_KEY`,
  `WEED_JWT_*_KEY` и `WEED_ADMIN_PASSWORD` замаскированы. `AWS_ACCESS_KEY_ID`
  (`citeck`) — имя пользователя, а не секрет, и не маскируется: иначе в дампе
  пропали бы все имена контейнеров `citeck_*` и образов `harbor.citeck.ru`.

## Admin UI

Встроенный в SeaweedFS веб-интерфейс показывает файлы бакета `ecos-content`
(их можно скачать), тома и состояние кластера. Файлы ecos-content в нём лучше
не удалять и не переименовывать: ECOS ссылается на них по ключу, и такой файл
перестанет открываться.

* **Desktop** — ссылка **SeaweedFS** на боковой панели
  (`http://127.0.0.1:23646`). Её нет, если в бандле нет SeaweedFS, и она серая,
  пока хранилище не запущено — у namespace на базе данных, пока его не
  запустили `citeck start seaweedfs`. Логин `admin`, пароль `admin`.
* **Server** — порт не публикуется, боковой панели нет. Admin UI доступен
  через SSH-туннель к контейнеру:

  ```bash
  # на сервере: адрес контейнера хранилища в сети namespace
  docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' citeck_seaweedfs_<namespace>
  # на своей машине
  ssh -N -L 23646:<адрес контейнера>:23646 <пользователь>@<сервер>
  ```

  Затем открыть `http://127.0.0.1:23646` и войти как `admin` с паролем
  администратора стенда. Адрес контейнера меняется при каждом его
  пересоздании. С rootless Docker адрес контейнера с самого сервера
  недоступен, и такой туннель не работает.

## Ресурсы

* **Память** — лимит контейнера 1 GiB (`GOMEMLIMIT` 512 MiB). В покое —
  около 130 MiB анонимной памяти, около 0,26 GiB вместе со страничным кэшем;
  при 16 параллельных загрузках по 100 MiB — до ~0,6 GiB анонимной памяти.
  Загрузки сверх 128 MiB одновременно (`-s3.concurrentUploadLimitMB`) ждут в
  очереди, а не увеличивают память.
* **Образ** — ~0,5 GB в распакованном виде, ~0,7 GB в хранилище образов
  containerd.
* **Диск** — том `seaweedfs2` растёт вместе с контентом. Данные лежат в
  томах SeaweedFS по 256 MB (`-master.volumeSizeLimitMB`); место удалённых
  файлов освобождается не сразу, а при уплотнении тома, которое начинается,
  когда удалённое занимает больше 30 % тома (порог `garbageThreshold` 0,3).

## Старые версии Launcher и откат

Launcher, который не знает `contentStorage`, читает `namespace.yml` без этого
ключа и **теряет его при любом сохранении** namespace: правка в диалоге,
обновление, `citeck setup <что угодно>`. Так бывает и без участия оператора —
при автоматическом откате desktop-обновления, которое не прошло проверку
здоровья, или при откате `install.sh`/`citeck upgrade` на сервере. Вернувшись
на этот Launcher, такой namespace читается как «База данных»: ecos-content не
ждёт хранилище, при остановке хранилища нет предупреждения, подключение не
проверяется — а в ECOS хранилищем по умолчанию остаётся
`content/storage@<app>-s3`. Снова выбрать S3 безопасно: подключение увидит,
что по умолчанию уже стоит его хранилище, и ничего не запишет (`connected`).

Ключи хранилища откат не затрагивает: Launcher без генерируемых секретов
записи `generated:` пропускает, но значения, которые namespace уже сохранил,
читает, так что хранилище продолжает работать с теми же ключами. Новых ключей
он не создаёт — namespace, у которого их ещё нет, хранилища у него не получит.

## Снапшоты

Снапшот содержит тома (в том числе базу ECOS и том хранилища `seaweedfs2`), но
не конфигурацию namespace. Если восстановить снапшот namespace на S3 в
namespace на базе данных (или создать из такого снапшота новый namespace на
базе данных), в ECOS хранилищем по умолчанию останется
`content/storage@<app>-s3`, а шаблон `default` держит хранилище отцеплённым:
загрузка и скачивание файлов не работают, и Launcher об этом не сообщает —
для namespace на базе данных он ECOS не проверяет. Переключите такой namespace
на S3: подключение найдёт своё хранилище по умолчанию (`connected`) и приведёт
секрет в ECOS к ключу этого namespace. Одного `citeck start seaweedfs` хватит
только тому же namespace, из которого снапшот сделан: у нового namespace свой
ключ S3, а в восстановленной базе ECOS — ключ исходного, и каждая загрузка
файла получит 403.

## Подключение вручную

На namespace с базой данных хранилище можно включить и подключить
самостоятельно: `citeck start seaweedfs`, затем в ECOS создать секрет, эндпоинт
и хранилище S3 с параметрами из `contentStorage.s3` и выбрать его хранилищем по
умолчанию. Ключ `secretKey` у каждого namespace свой, в workspace его нет;
значение видно в окружении контейнера хранилища:

```bash
docker exec citeck_seaweedfs_<namespace> printenv AWS_SECRET_ACCESS_KEY             # server
docker exec citeck_seaweedfs_<namespace>_<workspace> printenv AWS_SECRET_ACCESS_KEY # desktop
```

Такой секрет — запись администратора, и Launcher его не поддерживает: если
namespace получит новый ключ (сброс секретов на desktop), секрет в ECOS нужно
поменять вручную. Если потом переключить такой namespace на S3, Launcher
увидит, что хранилище по умолчанию уже выбрано, и ничего не перезапишет
(`admin-managed`).

## Чего Launcher не делает

* Не переносит файлы — ни из базы в S3 при переключении, ни обратно.
* Не переписывает хранилище `content/storage@<app>-s3` и хранилище по
  умолчанию, а при чужом хранилище по умолчанию — вообще ничего в ECOS.
* Не переносит в ECOS ключ, изменённый на стенде в обход секретов namespace
  (`citeck edit seaweedfs`): секрет `emodel/secret@seaweedfs-s3-credentials`
  тогда нужно поменять вручную (см. [«Ключ S3 в ECOS»](#ключ-s3-в-ecos)).
* Не закрывает gRPC-порты SeaweedFS: любой контейнер в сети namespace
  подключается к ним без учётных данных (см.
  [«Защита хранилища»](#защита-хранилища)).
