# Хранение контента: база данных или S3

Файлы, которые пользователи загружают в Citeck (вложения, документы, их
версии), хранит сервис ecos-content (`content`). Где именно он их хранит,
выбирается для каждого namespace — в интерфейсе это поле **«Способ хранения
контента»**:

| Вариант | `namespace.yml` | Что это |
|---|---|---|
| **База данных** (по умолчанию) | ключа нет или `type: DB` | файлы лежат в PostgreSQL стенда — так работают все namespace, созданные до появления выбора |
| **S3 (SeaweedFS)** | `type: S3` | файлы лежат в S3-хранилище, которое Launcher поднимает рядом со стендом и сам подключает к ecos-content |

```yaml
# namespace.yml
contentStorage:
  type: S3
```

Отсутствие ключа означает «База данных», и Launcher его не дописывает: у
существующих namespace файл конфигурации не меняется, `apiVersion` тоже.
Регистр значения не важен (`s3` — то же, что `S3`); неизвестное значение —
ошибка конфигурации. `type: S3` нельзя сочетать с блоком `s3:` (подключение к
**внешнему** S3, `citeck setup s3`): оба решают, куда ecos-content пишет файлы,
и такая конфигурация отклоняется.

Вариант S3 есть только у Enterprise: в Community нет ecos-content.

## Где выбирается

* **Desktop** — диалог создания и редактирования namespace, вкладка
  Advanced («Дополнительно»). На вкладке «Основное» способ хранения не
  показывается. Если для namespace нет ни настройки content storage, ни
  legacy MongoDB, пустая вкладка Advanced не появляется. При создании по
  умолчанию выбрана база данных, и выбор
  отправляется всегда — в том числе «База данных». Новый namespace получает
  способ хранения только из этого выбора: если `namespaceTemplates[].config`
  шаблона задаёт `contentStorage`, значение игнорируется (с предупреждением в
  логе) — необратимый выбор делает оператор, а не шаблон. У namespace с
  внешним S3 (блок `s3:`) вариант S3 в диалоге редактирования показан
  недоступным. Выбор сохраняется при переключении вкладок; у существующего
  S3 namespace текущее хранилище и предупреждение о необратимости показаны
  в Advanced без возможности переключить его обратно на базу данных.
* **Server** — `citeck install` спрашивает способ хранения после выбора релиза,
  если для этого релиза S3 доступен (по умолчанию — база данных); у
  существующего namespace — `citeck setup content-storage` (настройка видна,
  только если в бандле есть ecos-content). Эта настройка работает только при
  запущенном демоне: новая конфигурация уходит в него через
  `PUT /api/v1/config`, и демон сам проверяет правила, снимает с хранилища
  отметку «остановлено» и применяет конфигурацию. `citeck setup history --undo`
  отказывается откатывать запись, которая изменила бы способ хранения.
* **API** — поле `contentStorage` (`"DB"` | `"S3"`) при создании и
  редактировании namespace, а также полная конфигурация через
  `PUT /api/v1/config`.

Правила ниже проверяет сам Launcher на каждом из этих путей. Правка
`namespace.yml` руками, в обход Launcher, их не проходит — переключать способ
хранения так не нужно.

## Когда вариант S3 доступен

Доступность определяется бандлом, на котором стоит namespace, и конфигурацией
workspace. Бандл читается из локальной копии, без обращения к git — диалог
показывает ровно то, что потом примет сохранение.

| Причина | Что видно | Что это значит |
|---|---|---|
| `NO_CONTENT_APP` | вариант S3 **скрыт** | в бандле нет ecos-content (Community) — вопрос не стоит |
| `NO_PROVIDER_CONFIG` | вариант недоступен, с подсказкой | в конфигурации workspace нет блока `contentStorage.s3` (или он неполон) |
| `NO_PROVIDER_APP` | то же | блок называет приложение, которого нет среди `additionalApps` workspace (или оно выключено) |
| `PROVIDER_CONFLICT` | то же | имя хранилища занято приложением платформы (встроенным или webapp, который workspace перечисляет в `webapps:` и который есть в бандле — генератор оставит его, а запись пропустит), или хранилище само зависит от ecos-content (зависимость ecos-content от него замкнула бы цикл) |
| `NO_PROVIDER_IMAGE` | то же | ни бандл, ни запись в workspace не называют образ хранилища — этот релиз SeaweedFS не поставляет |
| `BUNDLE_UNRESOLVED` | то же | бандла нет в локальной копии репозитория — проверить нечего, и выбрать S3 на нём нельзя |

Сохранение с недоступным вариантом отклоняется: HTTP 409
`CONTENT_STORAGE_UNAVAILABLE` с той же причиной, текстом на языке Launcher.
Последний случай строже, чем проверка версии лаунчера: S3 нельзя отменить
(следующий раздел), поэтому непроверенный выбор не принимается.

## Только в одну сторону

* **База данных → S3 — можно**: в диалоге редактирования, через
  `citeck setup content-storage`, через `PUT /api/v1/config`.
* **S3 → база данных — нельзя никогда**: HTTP 409 `CONTENT_STORAGE_DOWNGRADE`.
  Полная конфигурация, в которой ключа `contentStorage` нет, тоже считается
  возвратом к базе данных и отклоняется. Файлы, уже записанные в S3, в базе
  отсутствуют, и Launcher их никуда не переносит. Сохранённую конфигурацию
  Launcher для этой проверки читает так, чтобы S3 нельзя было потерять
  незаметно: если она не разбирается как YAML (ручная правка с синтаксической
  ошибкой), блок `contentStorage` ищется в тексте, а если её не удаётся
  прочитать вовсе, запись отклоняется (HTTP 500) — а не считается переходом
  «база данных → база данных».
* Файлы, загруженные **до** переключения на S3, Launcher тоже не переносит:
  они остаются там, куда были записаны.
* У namespace на S3 можно сменить бандл, только если на новом бандле S3
  по-прежнему доступен. Правка, которая не трогает ни способ хранения, ни
  бандл (переименование, настройки прокси и т. п.), проходит всегда — даже если
  конфигурация workspace с тех пор изменилась; такое состояние Launcher
  показывает отдельно (см. «Если подключить не получилось»).
  Это правило действует и для `citeck setup history --undo`: если откат меняет
  бандл namespace на S3, сохранение проходит через общий write gate демона.
  Обычные настройки `citeck setup` и history undo используют один writer:
  при работающем демоне — `PUT /api/v1/config`, без него — локальную запись
  с общей политикой переходов. Offline-смена бандла на S3 отклоняется.
  Отказ или ошибка online-записи не приводят к записи файла в обход демона.
  Перед online-сохранением проверяется совпадение исходной конфигурации с
  текущей сохранённой конфигурацией активного namespace. Для обычных настроек
  сохранена семантика «сохранить» / «сохранить и применить»; undo по-прежнему
  предлагает отдельный reload. Откат остальных настроек работает и без демона.

Одного обновления Launcher недостаточно, чтобы появился вариант S3:
workspace должен содержать согласованные `contentStorage.s3`, секреты,
`additionalApps`, ссылку и настройку `detachedApps`, а выбранный бандл — образ
провайдера. Эталон в `internal/namespace/testdata/content-storage-workspace.yml`
проверяет конфигурацию внутри репозитория Launcher; тесты не подтверждают,
что эти блоки уже опубликованы в используемом внешнем workspace. До их
публикации отсутствие варианта S3 или `NO_PROVIDER_CONFIG` ожидаемо.

## Что Launcher делает для namespace на S3

Хранилище — обычная запись `additionalApps` в конфигурации workspace
(`seaweedfs`), а блок `contentStorage.s3` называет её и описывает, как
ecos-content до неё достучаться. Для namespace на S3 Launcher делает три вещи.

**1. Хранилище стартует вместе с namespace.** Шаблон workspace держит
`seaweedfs` в `detachedApps`, чтобы namespace на базе данных за него не платил.
Для namespace на S3 это правило не действует: новый namespace поднимает
хранилище вместе с остальными приложениями. При переключении существующего
namespace с базы данных на S3 Launcher один раз снимает с хранилища отметку
«остановлено» и применяет конфигурацию — это часть того же действия оператора.
На обычной загрузке и `citeck reload` отметки не снимаются: хранилище,
остановленное оператором после переключения, остаётся остановленным (см. ниже).

**2. ecos-content ждёт хранилище.** Для S3 контейнер зависит от провайдера.
Launcher передаёт ему штатные настройки платформы через окружение:

```text
ECOS_ENDPOINT_CONTENT_STORAGE_S3_ENDPOINT_URL=<contentStorage.s3.url>
ECOS_ENDPOINT_CONTENT_STORAGE_S3_ENDPOINT_CREDENTIALS=content-storage-s3-credentials
ECOS_SECRET_CONTENT_STORAGE_S3_CREDENTIALS_TYPE=BASIC
ECOS_SECRET_CONTENT_STORAGE_S3_CREDENTIALS_USERNAME=<accessKey>
ECOS_SECRET_CONTENT_STORAGE_S3_CREDENTIALS_PASSWORD=<разрешённый secretKey namespace>
```

Используется встроенное хранилище `content/storage@content-storage-s3`, его
endpoint `content-storage-s3-endpoint` и bucket `ecos-content`. Launcher не
создаёт и не обновляет записи секретов, endpoint или S3-хранилищ в ECOS.
Переменные окружения имеют приоритет над настройками endpoint/секрета из БД.
Для namespace на DB окружение и deployment hash ecos-content остаются прежними.

**3. Выбор хранилища в ECOS — автоматически.** После перехода `gateway`,
`emodel`, `eapps`, `content` и провайдера в RUNNING daemon обращается напрямую
к Records API gateway. Единственная remote mutation — запись
`eapps/config@app/emodel$default-content-storage`:

```json
{"_value?json":{"ref":"content/storage@content-storage-s3","config":{}}}
```

Запрос идёт напрямую на внутренний HTTP endpoint gateway:
`POST /api/records/mutate`, JSON Records API v1, заголовок `X-ECOS-User: admin`.
Gateway направляет запись `eapps/config@...` в eapps; это config для emodel.
Пароль администратора и OIDC-токен не передаются, публичный proxy не участвует.
Поэтому смена admin-пароля и режима BASIC/KEYCLOAK сама по себе не меняет
аутентификацию этого запроса. Platform user admin должен сохранять право менять config.
На живом стенде проверены смена пароля и переход BASIC → Keycloak:
[результаты](reviews/content-storage-s3-live.md).

Перед решением Launcher читает актуальный config. Непосредственно перед
мутацией перечитывает его ещё раз, после мутации — проверяет результат.
Условная запись не применяется: это согласованное решение от 2026-10-07.
Изменение между последним чтением и записью не исключается атомарно.

* Штатное S3 уже выбрано — `connected`, remote writes не нужны.
* Выбрано другое хранилище — `admin-managed`, выбор сохраняется.
* Первоначальный LOCAL или пустая ссылка — переключение на штатное S3.
* После ранее подтверждённого S3 config снова указывает на LOCAL —
  `admin-managed`, Launcher не отменяет ручной возврат администратора.

Перед мутацией сохраняется `contentStorageSwitchPending`; отказ сохранения
блокирует запись в ECOS. После подтверждения одним сохранением очищается
маркер и записывается `contentStorageDefaultSet` — история подтверждённого
переключения. Это не текущий статус: результат всегда выводится из config ECOS.
История восстанавливается при загрузке namespace. Незавершённое переключение
повторяется после перезапуска; новый выбор другого хранилища прекращает его.

Готовность config и встроенного S3-хранилища проверяется каждые 15 секунд,
до 15 минут. `null` у config означает, что артефакт ещё не готов; неизвестный
формат значения вызывает ошибку. Для `_notExists` только `true` означает
отсутствие — `null`, отсутствие атрибута и `false` считаются существованием.

Перед записью повторно проверяются текущая задача и доступность платформы.
Барьер данных удерживается на время чтения перед мутацией, самой мутации и
проверочного чтения, с ограниченным временем каждого HTTP-запроса. Snapshot,
миграция и rollback не могут пересечь этот участок. Смена namespace отменяет
задачу; поколение сброса отбрасывает отложенные проверки старого namespace.

При временных сетевых ошибках запись повторяется в пределах бюджета готовности.
Обычный отказ или несовпадение результата показывают `error` с причиной.
**Повтор после ошибки запускается таймером через 5 минут**, без нажатия кнопки
или изменения статусов приложений. Если платформа остановлена или занята,
таймер продолжает попытки до её готовности. Кнопка повтора и
`POST /api/v1/namespace/content-storage/provision` позволяют попробовать раньше.

| Состояние | Что значит |
|---|---|
| `pending` | задача ещё не может начаться; на остановленном namespace проверяется при запуске |
| `waiting` | ожидание готовности ECOS и встроенного S3-хранилища |
| `provisioning` | переключение config хранилища по умолчанию |
| `connected` | config указывает на штатное S3 для нового контента |
| `admin-managed` | выбор администратора сохранён |
| `error` | попытка не удалась; причина показана, повтор автоматический |

## Ключ S3 в ECOS

Ключ хранится в секретах namespace и передаётся через env одновременно в
провайдер и ecos-content. В БД ECOS Launcher его не записывает. После сброса
секретов или восстановления в новый namespace генерация подставляет новое
значение в оба контейнера; изменение окружения пересоздаёт ecos-content.
Если значение отсутствует, генерация сообщает проблему и не подключает S3.

Ключи и endpoint меняйте через конфигурацию workspace/секреты namespace.
Правки секретов и endpoint в БД перекрываются env платформы. Изменение ключа
только у провайдера через `citeck edit` не обновляет окружение ecos-content:
такую индивидуальную настройку нужно согласовать в обоих контейнерах.

## Остановка хранилища

`citeck stop seaweedfs` (или кнопка остановки в таблице приложений) на
namespace с S3 **не запрещена**: команда предупреждает в stderr и
останавливает хранилище, UI просит подтверждения. Пока хранилище остановлено,
загрузка и скачивание файлов в ECOS не работают. Уже запущенный ecos-content
продолжает работать, а при следующем старте будет ждать хранилище в
`DEPS_WAITING`, и namespace перейдёт в `STALLED`. Остановка запоминается как
решение оператора и переживает `citeck reload`; вернуть хранилище:

```bash
citeck start seaweedfs
```

## Если подключить не получилось

Проблемы генерации **никогда не мешают** стенду подняться: остальные
приложения стартуют как обычно, а проблема показывается на баннере
(не скрывается) и в `citeck status`.

| Проблема | Что случилось |
|---|---|
| `PROVIDER_NOT_GENERATED` | подключение S3 не сгенерировано: у namespace нет значения секрета провайдера или подключения (например, хранилище секретов на desktop ещё заперто мастер-паролем) или нет приложения, от которого оно зависит. ecos-content в таком случае хранилище **не ждёт** — иначе он исчез бы из namespace вместе со всем, что от него зависит |
| `PROVIDER_CONFLICT` | хранилище нельзя подключить в том виде, в каком его описывает workspace: его имя занято приложением платформы, или оно (напрямую или через другие приложения, в том числе через `dependsOn` из `namespace.yml`) зависит от ecos-content. Такую зависимость Launcher не добавляет — цикл сломал бы генерацию всего namespace |
| `NO_PROVIDER_IMAGE`, `NO_PROVIDER_APP`, `NO_PROVIDER_CONFIG` | бандл или конфигурация workspace изменились так, что хранилища больше нет (см. таблицу доступности) |
| `NO_CONTENT_APP` | в namespace нет ecos-content |

## Конфигурация workspace

```yaml
# workspace-v1.yml
secrets:
  - id: seaweedfs-s3-key      # ключ S3: свой у каждого namespace
    generated:
      length: 40
  - id: seaweedfs-jwt         # ключ подписи токенов SeaweedFS
    generated:
      length: 48
additionalApps:
  - name: seaweedfs                  # без image: образ называет бандл
    type: SEAWEEDFS
    settings:
      admin.ui: true
      s3.readerCacheSizeMB: 64
      s3.concurrentUploadLimitMB: 128
    environments:
      AWS_ACCESS_KEY_ID: citeck
      AWS_SECRET_ACCESS_KEY: ${secret:seaweedfs-s3-key}
      WEED_JWT_SIGNING_KEY: ${secret:seaweedfs-jwt}   # и ещё три WEED_JWT_*
      WEED_ADMIN_USER: admin
      WEED_ADMIN_PASSWORD: ${ADMIN_PASSWORD}
      S3_BUCKET: ecos-content
    # mini, data volume/generation, probes, resource defaults and desktop
    # ports are supplied by Launcher; volumeBase defaults to the app name.
contentStorage:
  s3:
    app: seaweedfs                   # запись additionalApps выше
    title: SeaweedFS                 # необязательно: название в подписи «S3 (SeaweedFS)»
    url: http://seaweedfs:8333       # адрес, как его видит ecos-content
    bucket: ecos-content             # = S3_BUCKET записи
    accessKey: citeck                # = AWS_ACCESS_KEY_ID записи
    secretKey: ${secret:seaweedfs-s3-key} # = AWS_SECRET_ACCESS_KEY записи
links:
  - name: SeaweedFS                  # admin UI на боковой панели (desktop)
    url: http://127.0.0.1:23646
    dependsOn: [seaweedfs]
```

* Поля `app`, `url`, `accessKey`, `secretKey` обязательны. `bucket` можно
  опустить: используется `ecos-content`; другое имя отклоняется. `title` необязателен: без него в
  подписи варианта стоит имя приложения. Блок, в котором чего-то не хватает
  или который не читается, считается отсутствующим (с предупреждением в логе)
  и не ломает остальную конфигурацию workspace.
* Обе половины описывают **одно** хранилище, и связывает их только файл:
  `url`, `bucket`, `accessKey` и `secretKey` должны совпадать с тем, с чем
  настроен контейнер. Эталонная копия этих блоков (секреты, запись, блок
  `contentStorage` и ссылка) лежит в репозитории Launcher,
  `internal/namespace/testdata/content-storage-workspace.yml`, и тесты
  генератора проверяют на ней это соответствие и правила раздела
  [«Защита хранилища»](#защита-хранилища) — держите копию и workspace
  одинаковыми.
* Образ хранилища берётся по обычному правилу записей `additionalApps`
  ([приоритет образов](config-layers.md)): запись в бандле
  (`dependencies.seaweedfs`) важнее собственного `image:` записи. Бандл, который
  образ не называет, хранилища не получает — и вариант S3 на нём недоступен.
* Оба ключа — **генерируемые** секреты namespace (см.
  [Секреты workspace](workspace-secrets.md)): значение создаётся при первой
  генерации namespace, своё у каждого стенда, и дальше не меняется; `secretKey`
  подставляется из той же копии, что и в контейнер. Опубликованного в
  workspace ключа, одинакового у всех, кто читает репозиторий, нет (логин admin
  UI на desktop — другое дело, см. [«Защита хранилища»](#защита-хранилища)).
  При `snapshot export --include-secrets` сохранённые ключи попадают в архив
  и восстанавливаются в vault целевого namespace до генерации. Без параметра
  импорт сохраняет имеющиеся ключи сервера; в новом namespace отсутствующие
  generated keys создаются заново. Для переноса используйте экспорт с ключами
  (см. [снапшоты](snapshots.md)).
* Ключ S3 называется `seaweedfs-s3-key`, а не `seaweedfs-s3`: под id
  `seaweedfs-s3` в предварительной версии этой конфигурации был постоянный
  опубликованный ключ, а namespace, однажды сохранивший значение, хранит его
  навсегда — другой вид секрета получает только новый id (см.
  [Секреты workspace](workspace-secrets.md)).
* Конфигурация с `id:` / `generated:` требует Launcher с поддержкой
  генерируемых секретов. Версия без этой поддержки видит `id:` как константу
  с пустым значением и не умеет создать ключ; использовать такой workspace
  на ней нельзя. Ранее записанный scalar-формат `generated: <id>` нынешний
  Launcher также читает, поэтому существующие workspace не требуют
  немедленной миграции (см. [Секреты workspace](workspace-secrets.md)).

## Защита хранилища

SeaweedFS (`weed mini`) — один процесс с несколькими серверами, и у каждого
свои порты. Что требует каждый из них:

| Порт | Что это | Доступ |
|---|---|---|
| 8333 | S3 | ключ `accessKey`/`secretKey`; анонимные запросы отклоняются |
| 8888 | HTTP API filer | закрыт: `-disableHttp` |
| 9340 | HTTP API volume-сервера | чтение и запись файла — только с токеном, подписанным ключом `seaweedfs-jwt` |
| 23646 | admin UI | логин администратора стенда; без него отвечают только `/health` и `/metrics` (метрики Prometheus всего процесса) |
| 9333 | master | открыт, только чтение: страница состояния и `/cluster/status`; `/dir/assign` и `/dir/lookup`, которые выдают токены volume-сервера, закрыты `-disableHttp` |
| 18333, 18888, 19333, 19340, 33646 | gRPC (S3, filer, master, volume, admin/worker) | **открыты** |

* **gRPC-порты не защищены**, и это известное ограничение: любой контейнер в
  сети namespace может подключиться к ним без учётных данных — в том числе
  к gRPC filer'а, через который читаются и пишутся файлы, и к 33646, где
  регистрируются фоновые worker'ы. Закрыть их можно только mTLS, а для него
  нужен `security.toml` с сертификатами, которые запись `additionalApps` с
  собой не принесёт. Без учётных данных отвечают и несколько страниц только для
  чтения: состояние master (`/` и `/cluster/status` на 9333), `/status`
  volume-сервера, `/metrics` admin-порта (метрики Prometheus всего процесса
  `weed mini`, в том числе трафик по бакетам) и проверки здоровья.
* **`-disableHttp`** закрывает не только HTTP API filer'а, но и HTTP API
  master'а: `/dir/assign` и `/dir/lookup` выдают токены, с которыми
  volume-сервер принимает запросы к файлам. Без этого флага ключ подписи не
  защищал бы файлы ни от одного HTTP-клиента в сети namespace.
* **Снаружи** в server-режиме не опубликован ни один порт хранилища; на desktop
  опубликованы только 8333 и 23646, и только на 127.0.0.1.
* **Ключ S3** (`seaweedfs-s3-key`) — генерируемый, 40 символов. Он живёт и в
  окружении ecos-content: у namespace на S3 Launcher передаёт его через
  штатные переменные ECOS_SECRET_* (см.
  [«Ключ S3 в ECOS»](#ключ-s3-в-ecos)).
* **Ключ подписи** (`seaweedfs-jwt`, 48 символов) подписывает токены, с
  которыми filer и volume-сервер принимают запросы к файлам, — один ключ на
  запись и чтение. В ECOS он не попадает, а хранилище не держит его в томе,
  поэтому новое значение (восстановление в новый namespace, сброс секретов на
  desktop) ничего не ломает.
* **Admin UI** пускает по логину `admin` и паролю администратора стенда — тому
  же, что у RabbitMQ и PgAdmin (на desktop — `admin`). Пароль, изменённый
  `citeck setup admin-password`, admin UI SeaweedFS получает при следующем
  `citeck reload`: контейнер пересоздаётся (файлы остаются в томе), а до этого
  действует старый пароль — команда называет приложения, которые его ещё
  принимают. Повторная смена пароля до `reload` не скрывает это предупреждение:
  для объявленных в workspace полей `${ADMIN_PASSWORD}` сравнивается конфигурация
  работающего контейнера с новым паролем, а не только с предыдущим значением
  системного секрета. Уже открытые сессии смена пароля **не завершает**: ключ, которым
  SeaweedFS подписывает сессии admin UI, лежит в томе
  (`/data/admin/.session_key`), и сессия действует до 24 часов, в том числе
  после пересоздания контейнера. Чтобы завершить их сразу, удалите этот файл
  перед `citeck reload`:
  `docker exec citeck_seaweedfs_<namespace> rm /data/admin/.session_key`.
* **На desktop** логин admin UI — `admin`/`admin`, как у RabbitMQ и PgAdmin.
  После импорта с системными секретами действует импортированный admin-пароль.
  Любой процесс на этой машине, который дотянется до `127.0.0.1:23646`, и любой
  контейнер в сети namespace (`seaweedfs:23646`) получают полный доступ к
  хранилищу: файлы, бакеты, пользователи и ключи S3. Генерируемые ключи
  защищают хранилище в server-режиме и от тех, кто не может войти в admin UI, —
  но не от процессов на самой машине.
* Учётные данные Launcher передаются **только через окружение** контейнера.
  `weed mini` сохраняет свои флаги в `/data/mini.options`, то есть в том
  хранилища, который попадает в каждый снапшот, а переменные окружения не
  сохраняет: ни ключа S3, ни ключа подписи, ни пароля в томе нет. Свои ключи
  SeaweedFS в томе держит — ключ подписи сессий admin UI
  (`/data/admin/.session_key`) и ключи шифрования SSE (`/data/.mini_sse_kek`,
  `/data/.mini_kek_passphrase`), — и они попадают в каждый снапшот вместе с
  данными: namespace, восстановленный из снапшота, получает их тоже.
* В системном дампе (`citeck dump-system-info`) значения `AWS_SECRET_ACCESS_KEY`,
  `WEED_JWT_*_KEY` и `WEED_ADMIN_PASSWORD` замаскированы. `AWS_ACCESS_KEY_ID`
  (`citeck`) — имя пользователя, а не секрет, и не маскируется: иначе в дампе
  пропали бы все имена контейнеров `citeck_*` и образов `harbor.citeck.ru`.

## Admin UI

Встроенный в SeaweedFS веб-интерфейс показывает файлы бакета `ecos-content`
(их можно скачать), тома и состояние кластера. Файлы ecos-content в нём лучше
не удалять и не переименовывать: ECOS ссылается на них по ключу, и такой файл
перестанет открываться.

* **Desktop** — ссылка **SeaweedFS** на боковой панели
  (`http://127.0.0.1:23646`). Её нет, если в бандле нет SeaweedFS, и она серая,
  пока хранилище не запущено — у namespace на базе данных, пока его не
  запустили `citeck start seaweedfs`. Логин `admin`, пароль `admin`.
* **Server** — порт не публикуется, боковой панели нет. Admin UI доступен
  через SSH-туннель к контейнеру:

  ```bash
  # на сервере: адрес контейнера хранилища в сети namespace
  docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' citeck_seaweedfs_<namespace>
  # на своей машине
  ssh -N -L 23646:<адрес контейнера>:23646 <пользователь>@<сервер>
  ```

  Затем открыть `http://127.0.0.1:23646` и войти как `admin` с паролем
  администратора стенда. Адрес контейнера меняется при каждом его
  пересоздании. С rootless Docker адрес контейнера с самого сервера
  недоступен, и такой туннель не работает.
* **Admin UI отвечает 404** (`/` и `/login`; при этом хранилище RUNNING и
  ссылка активна) — том хранилища хоть раз запускался с `-admin.ui=false`
  (так было в предварительной версии конфигурации). `weed mini` сохраняет
  флаги в `/data/mini.options`, а сохранённое значение побеждает флаг,
  переданный со значением по умолчанию, — `-admin.ui=true` именно такой. Один
  раз удалите строку `admin.ui=` и перезапустите хранилище (кнопкой в таблице
  приложений или `citeck restart seaweedfs`):

  ```bash
  docker exec citeck_seaweedfs_<namespace> sed -i '/^admin.ui=/d' /data/mini.options             # server
  docker exec citeck_seaweedfs_<namespace>_<workspace> sed -i '/^admin.ui=/d' /data/mini.options # desktop
  ```

  После перезапуска `weed mini` сохраняет `admin.ui=true`, и шаг больше не
  нужен.

## Ресурсы

* **Память** — лимит контейнера 1 GiB (`GOMEMLIMIT` 512 MiB). В покое —
  около 130 MiB анонимной памяти, около 0,26 GiB вместе со страничным кэшем;
  при 16 параллельных загрузках по 100 MiB — до ~0,6 GiB анонимной памяти.
  Загрузки сверх 128 MiB одновременно (`-s3.concurrentUploadLimitMB`) ждут в
  очереди, а не увеличивают память.
* **Образ** — ~0,5 GB в распакованном виде, ~0,7 GB в хранилище образов
  containerd.
* **Диск** — том `seaweedfs2` растёт вместе с контентом. Данные лежат в
  томах SeaweedFS по 256 MB (`-master.volumeSizeLimitMB`); место удалённых
  файлов освобождается не сразу, а при уплотнении тома, которое начинается,
  когда удалённое занимает больше 30 % тома (порог `garbageThreshold` 0,3).

## Старые версии Launcher и откат

Launcher, который не знает `contentStorage`, читает `namespace.yml` без этого
ключа и **теряет его при любом сохранении** namespace: правка в диалоге,
обновление, `citeck setup <что угодно>`. Так бывает и без участия оператора —
при автоматическом откате desktop-обновления, которое не прошло проверку
здоровья, или при откате `install.sh`/`citeck upgrade` на сервере. Вернувшись
на этот Launcher, такой namespace читается как «База данных»: ecos-content не
ждёт хранилище, при остановке хранилища нет предупреждения, подключение не
проверяется — а в ECOS хранилищем по умолчанию остаётся
`content/storage@content-storage-s3`. Снова выбрать S3 безопасно: подключение увидит,
что по умолчанию уже стоит его хранилище, и ничего не запишет (`connected`).

Старый Launcher не добавляет env для управляемого S3. Пересоздание
контейнера ecos-content такой версией может убрать настройки подключения.
Для продолжения работы используйте версию с поддержкой `contentStorage`.

## Снапшоты

Снапшот содержит выбранные тома ECOS/провайдера и их dependency image/gen pins.
Конфигурация namespace и объекты внешнего S3 в него не входят. По умолчанию
секреты тоже не экспортируются: импорт рассчитан на тот же сервер с прежними
ключами. Для переноса с ключами используйте `citeck snapshot export --include-secrets`:
архив сохранит namespace secrets и JWT/OIDC/admin/SA, а импорт восстановит их
в целевом namespace до генерации. Затем выберите исходный способ хранения S3.
Штатный S3 default из восстановленной БД распознаётся как `connected` без
remote mutation. Подробнее: [снапшоты](snapshots.md).

Если восстановленный config показывает LOCAL, а история namespace уже
содержит подтверждённое переключение, Launcher сохраняет LOCAL как выбор
администратора. Нужный default в таком случае задаётся администратором в ECOS.

## Подключение вручную

Штатный путь — `citeck setup content-storage` или выбор S3 в диалоге namespace.
Для индивидуальной настройки endpoint и ключи можно передать в ecos-content
через штатные env, а в ECOS выбрать встроенное `content/storage@content-storage-s3`
в config хранилища по умолчанию. Создавать дополнительные записи не требуется.

## Чего Launcher не делает

* Не переносит файлы — ни из базы в S3 при переключении, ни обратно.
* Не создаёт и не синхронизирует секреты, endpoint и хранилища в ECOS.
* Не отменяет выбор другого хранилища администратором.
* Не синхронизирует индивидуальные правки ключей только в одном контейнере.
* Не закрывает gRPC-порты SeaweedFS: любой контейнер в сети namespace
  подключается к ним без учётных данных (см.
  [«Защита хранилища»](#защита-хранилища)).

## Границы реализации

Политика переходов DB/S3 и построение сообщений недоступности находятся в
`internal/namespace/content_storage_policy.go`; CLI и daemon используют их
совместно, применяя локаль на своих границах. Общие правила владения данными
при долгих операциях принадлежат `longop.go`.

Планировщик подключения владеет epoch, отменой, single-flight, таймером повтора
и состоянием job. Отдельный `csConnectionRunner` выполняет протокол чтения и
переключения default-config через узкие callbacks. У runner нет ссылки на
`Daemon`, job или полного runtime: он получает только чтение истории,
проверки допустимости, запись WAL/результата и доступ к барьеру мутации.
Проверки актуального job и durable persistence остаются у планировщика.

## Обновление SeaweedFS и локальный запуск content

`type: SEAWEEDFS` включает pin версии, поколения тома и управляемое обновление
через копию. Обычный reload не применяет смену версии к существующим данным.
Используются `citeck deps upgrade seaweedfs` и `citeck deps rollback seaweedfs`;
подробнее — [обновление SeaweedFS](seaweedfs-upgrade.md).

В desktop-режиме S3-порт опубликован на localhost (по умолчанию 8333),
в server-режиме он не публикуется. Это позволяет остановить контейнер `content`
в Launcher и запустить микросервис из IDE, используя обычную локальную
конфигурацию платформы и тот же S3. Namespace предварительно должен быть
настроен на S3; его default-config продолжает определять место записи файлов.

Native ECOS endpoint/secret читаются через `System.getenv`, а не Spring Cloud
Config. Окружение для IDE можно получить без ручного поиска ключа:

```bash
citeck describe content --local-env
# Для IDE или PowerShell можно запросить JSON:
citeck --format json describe content --local-env
```

Текстовый вывод — shell-команды `export` для пяти `ECOS_ENDPOINT_*` /
`ECOS_SECRET_*` переменных. URL заменён на фактически опубликованный
`http://127.0.0.1:<port>`, ключи взяты из текущего окружения content. Вывод
содержит учётные данные: он выдаётся только по явному запросу, не маскируется,
не записывается Launcher в runtime-файлы или снапшоты и не кешируется HTTP.
Экспорт доступен только на desktop при работающем S3-провайдере с опубликованным
портом; обычный `describe` по-прежнему маскирует секреты. Смена ключа требует
обновить окружение локально запущенного процесса.

## Внешний S3 через TUI

`citeck setup s3` настраивает существующий `namespace.s3` для ecos-content.
Этот режим не поднимает и не останавливает внешний S3: backend и выбранный
bucket должны быть подготовлены оператором. Managed `contentStorage.type: S3`
и внешний `s3` остаются взаимоисключающими настройками.

Endpoint и credentials передаются через те же native env providers.
Bucket из namespace применяется к встроенному `content-storage-s3` artifact:
Launcher генерирует его конфигурацию и монтирует файл read-only по штатному
пути образа ecos-content. Смена bucket меняет hash файлов и пересоздаёт content.
Новые provider-derived storage/endpoint/secret записи не создаются.

Внешний режим использует тот же процесс подключения default, что и managed:
после готовности ECOS начальный `LOCAL` переключается на
`content/storage@content-storage-s3`; изменяется только default-config через
Records API, с чтением непосредственно до и после записи и автоматическими
повторами. Ранее подтверждённый S3 с последующим ручным выбором LOCAL либо
другое выбранное администратором хранилище сохраняются. Запущенный managed
provider внешнему режиму не требуется. Неразрешённый secret блокирует
автоматический выбор default.

Явный `region` поддерживается в опубликованном ecos-content **1.7.2**
(COREDEV-629). В 1.7.0 поле не передаётся MinIO clients. Launcher переносит
непустое значение после trim в native artifact; пустое значение не добавляет
region и сохраняет автоматическое определение. DTO имеет тип `String = ""`,
оба MinIO builders — sync и async — получают один выбранный регион.
Изменение region меняет hash смонтированного artifact и пересоздаёт content.

Live-проверка 2026-10-08 на TEST с настоящим TUI и независимым региональным
MinIO подтвердила явный `eu-west-2` при запрещённом GetBucketLocation:
все подписи содержали выбранный регион, location-запросов не было. После
очистки region через TUI оба клиента автоматически определили регион;
sync upload/download, async multipart из трёх частей, complete и abort
прошли в обоих режимах. Managed backend во время внешней проверки был остановлен.

После mirror-back, восстановления исходного managed namespace и cleanup
повторно прочитаны **25 ECOS-файлов**, обе multipart-загрузки по dataKey и
**24 физических S3-объекта** во всех трёх бакетах. Новые данные сохранены
в `launcher-region-custom`; он нужен их существующим dataKey. TEST оставлен
active/RUNNING/S3 connected с прежними KEYCLOAK, credentials, SeaweedFS 4.48,
томом seaweedfs2/gen1 и без публикации backend-портов; content использует 1.7.2.
Ранее отдельно проверены default LOCAL → S3 и custom bucket.
Подробности и границы доказательства — в
[отчёте live-проверки](reviews/content-storage-s3-live.md).

Удаление внешнего `s3` с возвратом к БД запрещено общим write gate: файлы
во внешнем S3 автоматически в БД не переносятся. Запрет действует для API,
offline setup/history undo и пункта Remove в TUI; обычное редактирование
внешних настроек сохраняется. Само изменение endpoint или выбор другого
S3 не переносит прежние данные: их доступность нужно обеспечить отдельно.
