# Секреты workspace

Сервисы, объявленные в конфигурации workspace (`additionalApps:`), ссылаются на
свои реквизиты через **секреты**: раздел `secrets:` перечисляет их с id, а
ссылка `${secret:<id>}` подставляет значение. Пока поддерживаются только
константы; формат оставляет место для генерируемых секретов.

```yaml
# workspace-v1.yml
secrets:
  - id: billing-db
    value: billing
additionalApps:
  - name: billing-postgres
    type: POSTGRES
    user: billing
    password: ${secret:billing-db}
  - name: billing
    environments:
      DB_PASSWORD: ${secret:billing-db}
```

## Значение в workspace — это умолчание

Настоящие значения namespace получает **один раз** — первая генерация, которая
сохраняет состояние, засевает все умолчания из `secrets:`, а не только те, на
которые уже есть ссылки, — и дальше хранит у себя. Правка умолчания в
workspace и даже удаление записи до уже существующего namespace **не доходят**.
Это единственное безопасное прочтение для пароля: база записывает его в свой
том при первой инициализации, и сервис, получивший изменённый пароль, просто не
подключился бы. У каждого namespace своя копия.

## Где работает ссылка

`${secret:<id>}` подставляется везде, где подставляются `${JWT_SECRET}` и
`${ZK_HOST}`: env веб-приложений из конфигурации workspace (`defaultWebappProps`,
`webapps[].defaultProps`; env из `namespace.yml` не подставляется); env, cmd,
init-контейнеры, init-действия и `cloudConfig:` записей `additionalApps`; ключ
`password:` у `type: POSTGRES`.

## Если значения нет

Приложение, которое ссылается на секрет без значения, **не генерируется** — и
вместе с ним всё, что от него зависит; в логе строка
`App excluded from the namespace: a secret it references has no value in this namespace`
с именем приложения и id секрета. Остальной стенд поднимается как обычно.
Явно пустое значение (`value: ""`) — значение, оно подставляется.

## Где хранятся значения

В хранилище секретов лаунчера (`SecretService`) — строками типа `NAMESPACE`,
которые не показываются на странице секретов и не предлагаются как учётка
реестра или git.

* **Мастер-пароль задан** (сервер — всегда, по умолчанию `citeck`) — значения
  зашифрованы, как любой секрет.
* **Мастер-пароля ещё нет** (desktop при первом запуске) — значения хранятся
  открытым текстом: стенд должен подниматься без вопроса о мастер-пароле. Как
  только пароль появляется, они шифруются вместе со всем остальным.
* **Хранилище заперто** (desktop со своим мастер-паролем, ещё не введённым) —
  прочитать значения нельзя, поэтому старт namespace откладывается, а после
  разблокировки namespace перегенерируется и стартует.

Удаление namespace (или workspace целиком) удаляет и его значения.

## Чего здесь нет

* Генерируемых значений — только константы.
* Команды или UI для смены значения у существующего namespace: смена пароля у
  инициализированной базы — это миграция, а не правка поля.
* Переноса значений в снапшоте: снапшот не несёт состояние namespace. Новый
  namespace из снапшота засеет умолчания заново; пока их не меняли, пароль
  совпадёт с тем, что лежит в томе, а если меняли — сервис к базе не подключится.
* Паролей самого стенда (`postgres`, базы веб-приложений, alfresco): эти
  приложения в конфигурации не объявлены, и их пароли остаются в лаунчере.
