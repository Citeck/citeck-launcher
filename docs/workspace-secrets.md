# Секреты workspace

Сервисы, объявленные в конфигурации workspace (`additionalApps:`), ссылаются на
свои реквизиты через **секреты**: раздел `secrets:` перечисляет их, а ссылка
`${secret:<id>}` подставляет значение. Запись бывает двух видов — **константа**
(значение по умолчанию записано в workspace) и **генерируемая** (значение
придумывает Launcher, своё для каждого namespace).

```yaml
# workspace-v2.yml
secrets:
  # Константа: умолчание, которое namespace скопирует себе.
  - id: billing-db
    value: billing
  # Генерируемое значение: своё у каждого namespace.
  - id: billing-api-key
    generated:
      length: 40            # необязательно; 16..128, по умолчанию 40
additionalApps:
  - name: billing-postgres
    type: POSTGRES
    user: billing
    password: ${secret:billing-db}
  - name: billing
    environments:
      DB_PASSWORD: ${secret:billing-db}
      API_KEY: ${secret:billing-api-key}
```

## Значение в workspace — это умолчание

Настоящие значения namespace получает **один раз** — первая генерация, которая
сохраняет состояние, засевает все записи из `secrets:`, а не только те, на
которые уже есть ссылки, — и дальше хранит у себя. Правка умолчания в
workspace и даже удаление записи до уже существующего namespace **не доходят**.
Это единственное безопасное прочтение для пароля: база записывает его в свой
том при первой инициализации, и сервис, получивший изменённый пароль, просто не
подключился бы. У каждого namespace своя копия.

## Генерируемые значения

Запись с `id:` и блоком `generated:` не несёт значения: при первой генерации namespace
Launcher создаёт случайную строку из `[A-Za-z0-9]` (`crypto/rand`, равномерно)
длиной `generated.length` символов, сохраняет её и дальше использует только её. Это
способ выдать каждому стенду **свой** ключ: публичное умолчание в общем
workspace-репозитории одинаково у всех, кто его читает. Так объявлены ключи
S3-хранилища контента — `seaweedfs-s3-key` и `seaweedfs-jwt` (см.
[Хранение контента](content-storage.md#защита-хранилища)).

* Значение создаётся один раз и больше **никогда не создаётся заново** —
  ни при перезагрузке, ни при обновлении, ни после правки `length`.
* У каждого namespace своё значение, в том числе у namespace с тем же id в
  другом workspace.
* Значение не попадает в лог: в нём только строка `Namespace secret generated`
  с id секрета и namespace.
* **Пустое** сохранённое значение у генерируемого секрета значением не
  считается: пустой ключ у SeaweedFS означает «аутентификация выключена».
  Launcher заменяет его новым и пишет предупреждение.
* План перезагрузки (`citeck reload --dry-run`, `citeck diff`) ничего не
  сохраняет: значение, которого ещё нет, показывается заглушкой
  `<generated on reload>`, а приложение — изменением, а не исключением.

### Совместимость и смена вида

* Основной формат — `id: <id>` и `generated: {length: 48}`. Пустой блок
  `generated: {}` использует длину по умолчанию 40. Прежний формат
  `generated: <id>` с `length:` на верхнем уровне остаётся читаемым для уже
  сохранённых workspace-конфигураций; при YAML-сериализации Launcher выдаёт
  новый формат. Переход между этими двумя записями не меняет id или значение
  секрета namespace.
* Launcher без поддержки генерируемых секретов не понимает новый блок:
  он прочитает `id:` как константу с пустым значением. Поэтому конфигурация
  с новым форматом требует Launcher с поддержкой генерации; её нельзя
  применять на старой версии для сервиса, которому нужен непустой ключ.
  Для прежнего scalar-формата поведение старой версии другое: у записи нет
  `id:`, она пропускается и ссылка остаётся неразрешённой.
* **Не меняйте вид существующего id** (константа ↔ генерируемое), не понимая
  последствий: сохранённое значение namespace всегда важнее записи в
  workspace. Namespace, который уже засеял константу, так и останется с ней;
  только новые namespace получат сгенерированное значение. Если константа
  была пустой (`value: ""`), смена вида на `generated:` заменит её при
  следующей генерации — сервис получит новый ключ, и всё, что хранило старый,
  перестанет подключаться. Чтобы новый вид получили **все** namespace,
  объявите секрет под новым id и переставьте на него ссылки `${secret:}`:
  так ключ S3 хранилища контента стал `seaweedfs-s3-key` вместо постоянного
  `seaweedfs-s3`.

### Ошибки в записи

Запись, которую Launcher не может прочитать однозначно, **отбрасывается** с
одним предупреждением в логе (`Workspace secret entry is unusable; ignoring it`
с причиной); остальная конфигурация workspace продолжает работать, а
приложения, ссылающиеся на этот секрет, не генерируются. Так обрабатываются:

* `generated:` вместе с `value:`, даже если значение пустое или `null`;
* блок `generated:` без `id:`, неизвестные параметры блока или не-mapping
  значение `generated:` рядом с `id:`;
* `length:` вне блока `generated:` в новом формате или у константы;
* id не по грамматике `${secret:<id>}` — буквы, цифры, `.`, `_`, `-`;
* `length` не целое число или вне 16..128;
* запись без id (в основном формате `id:` обязателен).

Если id объявлен дважды, действует **первая** запись, о второй пишется
предупреждение.

## Где работает ссылка

`${secret:<id>}` подставляется везде, где подставляются `${JWT_SECRET}` и
`${ZK_HOST}`: env веб-приложений из конфигурации workspace (`defaultWebappProps`,
`webapps[].defaultProps`; env из `namespace.yml` не подставляется); env, cmd,
init-контейнеры, init-действия и `cloudConfig:` записей `additionalApps`; ключ
`password:` у `type: POSTGRES`; `secretKey` блока `contentStorage.s3` — его
значение генератор передаёт в штатное окружение ecos-content для S3
(см. [Хранение контента](content-storage.md)).

## Если значения нет

Приложение, которое ссылается на секрет без значения, **не генерируется** — и
вместе с ним всё, что от него зависит; в логе строка
`App excluded from the namespace: a secret it references has no value in this namespace`
с именем приложения и id секрета. Остальной стенд поднимается как обычно.
Явно пустое значение константы (`value: ""`) — значение, оно подставляется.

Значения засевают только генерации, после которых стартуют контейнеры:
загрузка namespace и перезагрузка. Временные контейнеры миграции зависимостей
вне этой генерации только
**читают**: константу без сохранённой копии получают как умолчание, а
генерируемое значение, которого ещё нет, не получают вовсе — ключ, который
никто не сохранил, не был выдан ни одному контейнеру.

## Где хранятся значения

В хранилище секретов лаунчера (`SecretService`) — строками типа `NAMESPACE`,
которые не показываются на странице секретов и не предлагаются как учётка
реестра или git. Константы и генерируемые значения хранятся одинаково.

* **Мастер-пароль задан** (сервер — всегда, по умолчанию `citeck`) — значения
  зашифрованы, как любой секрет.
* **Мастер-пароля ещё нет** (desktop при первом запуске) — значения хранятся
  открытым текстом: стенд должен подниматься без вопроса о мастер-пароле. Как
  только пароль появляется, они шифруются вместе со всем остальным.
* **Хранилище заперто** (desktop со своим мастер-паролем, ещё не введённым) —
  прочитать значения нельзя (и записать новое сгенерированное тоже), поэтому
  старт namespace откладывается, а после разблокировки namespace
  перегенерируется и стартует. Запертое хранилище никогда не считается пустым:
  значение не генерируется заново из-за того, что его нельзя прочитать.

Удаление namespace (или workspace целиком) удаляет и его значения. Сброс
секретов на desktop (забытый мастер-пароль) удаляет все значения: следующая
генерация засеет константы заново и создаст **новые** генерируемые значения —
а всё, что запомнило старое значение (например, база, проинициализированная со
старым паролем), с новым работать не будет. Исключение — ключ S3-хранилища
контента: новый ключ генератор передаёт в окружение провайдера и ecos-content (см.
[Хранение контента](content-storage.md#ключ-s3-в-ecos)).

## Чего здесь нет

* Команды или UI для смены значения у существующего namespace: смена пароля у
  инициализированной базы — это миграция, а не правка поля.
* Паролей самого стенда (`postgres`, базы веб-приложений, alfresco): эти
  приложения в конфигурации не объявлены, и их пароли остаются в лаунчере.

## Перенос со снапшотом

Snapshot ZIP с `--include-secrets` содержит `secrets.json` с сохранёнными NAMESPACE
значениями и системными JWT/OIDC/SA/admin. Без параметра секреты не экспортируются. При
восстановлении они записываются в целевой namespace до первой генерации и
шифруются его vault; новый generated key вместо импортированного не создаётся.
Подробности, совместимость старых архивов и границы полноты:
[снапшоты](snapshots.md), [аудит](reviews/snapshots-audit.md).
