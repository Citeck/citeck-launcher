# Что стартует на стенде, а что нет

Приложение в namespace может быть **сгенерировано**, но не **запущено**. Это два
разных состояния, и путать их не стоит: у неотцепленного приложения есть спека,
конфиг, тома и кнопка Play — нет только работающего контейнера.

Источников «не запускать» ровно три, и все три пишут в **один и тот же набор** —
операторский (`manualStoppedApps`). Отдельного «системного detach» в Launcher нет.

| Источник | Когда применяется | Что записывает |
|---|---|---|
| `citeck stop <app>` | в любой момент | `manualStoppedApps`, сохраняется |
| `namespaceTemplates[].detachedApps` шаблона workspace | при первом запуске namespace, у которого ещё нет сохранённого состояния | то же самое |
| Правило для приложений, впервые появившихся с новым релизом бандла | на загрузке и на `citeck reload` / Update & Start | то же самое |

Вернуть приложение в работу всегда одинаково:

```bash
citeck start <app>
```

## Отцепленное приложение и его зависимости

Отцепленное приложение **не удаляется** из namespace: его спека генерируется,
том сохраняется, конфиг доступен через `citeck edit <app>`. Именно это делает
рабочим сценарий «остановить в лаунчере — запустить из IDE»: локально поднятое
приложение обращается к тем же контейнерам стенда.

Важное следствие: **явный старт не поднимает остановленные зависимости**.

```bash
citeck stop qdrant
citeck start rag          # rag НЕ запустится
```

`rag` уйдёт в `DEPS_WAITING`, а namespace — в `STALLED`. Это честное состояние, а
не сбой: Launcher показывает, чего именно ждёт приложение (`citeck status`,
колонка статуса; в UI — та же информация в таблице приложений). Лечится стартом
зависимости — дальше цепочка разворачивается сама:

```bash
citeck start qdrant       # rag сам перейдёт из DEPS_WAITING в RUNNING
```

Либо поднять namespace целиком (`citeck stop && citeck start`) — полный старт
поднимает всё, что не отцеплено, в правильном порядке.

Обратного каскада нет: `citeck stop qdrant` **не останавливает** уже работающий
`rag`. Ограничение вступит в силу при следующем старте `rag`.

## Приложения, появившиеся с новым релизом бандла

Обновление бандла может добавить в namespace приложение, которого там раньше не
было. Опциональное приложение не должно стартовать само только потому, что оно
новое — иначе стенд после обновления получает сервис, о котором никто не просил
(и его память).

Правило: **приложение, которого этот namespace раньше не видел, приезжает
отцепленным, если шаблон workspace, из которого namespace создан, перечисляет
его в `detachedApps`.**

Как это устроено:

1. В состоянии namespace хранится список **уже виденных** приложений
   (`knownApps` в `state-<ns>.json`, на десктопе — в колонке `state_json`).
   Список только растёт: приложение, временно выпавшее из генерации (бандл
   отрезолвился в ноль, откат на кэш, выключение в `namespace.yml`), не считается
   новым, когда вернётся.
2. Если в состоянии списка нет (namespace создан раньше, чем появился сам
   механизм), подставляется **встроенный базовый список** — всё, что Launcher
   генерировал до появления первых компаньонов (`qdrant`, `rag`, `stt-sidecar`).
   Это важно: без него первое же обновление сочло бы новым *каждое* приложение.
3. Список `detachedApps` перечитывается из workspace-репозитория
   **принудительным pull'ом**, но только когда состав действительно вырос.
   Обычная загрузка и обычный reload не платят за это ни git-запросом, ни
   обращением к Docker.
4. Прежде чем отцепить, Launcher проверяет, **нет ли приложения на стенде уже**:
   доказательством считается контейнер. Приложение, которое оператор запускал,
   записывается как известное и не трогается.
5. Если ответ получить не удалось — Docker недоступен или workspace-репозиторий
   не синхронизировался — решение **откладывается**: приложение не отцепляется и
   не записывается как известное, вопрос задаётся снова на следующей загрузке.
   При несинхронизированном workspace откладываются только приложения, которых
   нет в имеющемся списке `detachedApps`; перечисленные в нём отцепляются как
   обычно.

В логе это видно явно:

```
INFO New apps arrived with this bundle and the workspace template has them
     detached; they will not start by themselves apps=[rag] template=default
```

В UI и в `citeck status` такое приложение выглядит как обычное отцепленное — с
кнопкой Play. `citeck start <app>` включает его навсегда: приложение уже
записано как известное, и правило к нему больше не применяется.

### Server и desktop

В server-режиме Launcher **не дёргает git самостоятельно** — актуальность
шаблона определяется последним `citeck update`, и конфиг с диска
считается текущим. На десктопе перечитывание делается принудительным pull'ом.

### Что нужно сделать автору релиза

Если новый релиз добавляет опциональное приложение, которое не должно стартовать
у всех, оно должно быть перечислено в `detachedApps` шаблона в
workspace-репозитории. **Компаньон добавляется вместе с владельцем**: `qdrant`
рядом с `rag`, `stt-sidecar` рядом с `ai` — иначе на стенде с выключенным
владельцем поднимется одно только хранилище или один только сайдкар.

## Компаньоны: qdrant рядом с rag, stt-sidecar рядом с ai, база рядом с observer

Компаньон — это приложение, которое обслуживает другое: `qdrant` (векторное
хранилище) для `rag`, `stt-sidecar` (распознавание речи) для `ai`,
`observer-postgres` для `observer`.

Правила у них те же, что у остальных приложений:

* спека генерируется **независимо от состояния владельца** — это и есть то, к
  чему обращается владелец, запущенный локально из IDE;
* приложение **стартует вместе с namespace**, как любое другое;
* чтобы стенд за него не платил — `citeck stop <app>` или запись в
  `detachedApps` шаблона.

Специфика `qdrant`, которая не выводится из общих правил:

* он генерируется, **только если образ qdrant есть в бандле** — наличие `rag`
  условием не является. На community-стендах хранилища нет вообще;
* том берётся из счётчика поколений (`qdrant2` для первого поколения), а версия
  образа проходит через реестр зависимостей: совместимость хранилища у Qdrant —
  **одна минорная версия**, поэтому бандл, поднимающий минор через одну, будет
  придержан с предложением промежуточного шага (см. `citeck deps`);
* публикуются оба порта — 6333 (HTTP, там же проба `/healthz`) и 6334 (gRPC,
  именно по нему обращается `rag`), чтобы локально запущенный `rag` находил
  хранилище на localhost (в server-режиме порты наружу публикует только прокси);
* зависимость `rag` → `qdrant` безусловна: `rag` без хранилища стартовал бы
  «зелёным», но молча не умел бы ни искать, ни индексировать.

Специфика `stt-sidecar`: он генерируется только при наличии `ai` и образа —
из бандла или из workspace (`sttSidecar.image` или `dependencies:`), лимит памяти по умолчанию 2 ГБ (модель gigaam), и обвязка `ai` → STT
появляется только когда сам сайдкар не отцеплен — `ai` без распознавания речи
работоспособен, поэтому блокировать его не за чем.

Обвязку владельца — его переменные окружения и зависимости — пишет **сам
владелец**, а не генератор компаньона: генераторы `stt-sidecar` и `qdrant`
создают только сам компаньон, а `ai` и `rag` после них смотрят, что получилось
(и отцеплен ли сайдкар), и настраивают себя сами. Поэтому всё, что говорится
`ai` (`CITECK_AI_RAG_ENABLED`, `CITECK_AI_CALLRECORDING_STT_SIDECARURL`),
собрано в одном месте — `internal/namespace/generator_owner_wiring.go`.

Специфика `observer`: он и его база — не код лаунчера, а объявление в
конфигурации workspace; как и `qdrant`, они существуют только там, где бандл
называет их образы (флага в `namespace.yml` нет), а база — зависимость со своим
пином, своим поколением тома и своей миграцией. Подробности — в
[Observer](observer.md).

## Где что хранится

| Что | Где |
|---|---|
| Отцепленные приложения | `manualStoppedApps` в состоянии namespace |
| Уже виденные приложения | `knownApps` там же |
| `detachedApps` шаблона | workspace-репозиторий, `workspace-v1.yml` |
| Правки конфигурации приложения | `editedAppPatches` / `editedFileEdits` там же |

Состояние namespace живёт в `state-<ns>.json` (server) или в колонке
`namespaces.state_json` SQLite (desktop).

## История: почему нет «системного detach»

До сентября 2026 у Launcher было второе, отдельное состояние — вердикт
генератора `AutoDetachedApps`: компаньон отцепленного владельца генерировался, но
рантайм не запускал его сам. Механизм убран, потому что выигрыш оказался узким, а
цена — постоянной.

Выигрыш: вердикт **не** освобождал память в момент остановки владельца
(работающий компаньон он намеренно не трогал) и **не** запускал компаньона при
старте владельца — то есть срабатывал только на следующем старте namespace, у
того, кто выключил владельца, забыл про компаньона и перезапустил стенд. Тот,
кому память была нужна сразу, останавливал компаньон руками — и вердикт для его
стенда становился пустым действием.

Цена: второй сорт «отцепленности», который снаружи нельзя было отличить от
решения оператора, пересчёт на каждой генерации и проброс через демон.

Всё, что вердикт закрывал, закрывается данными — `detachedApps` шаблона и
правилом для новых приложений выше. Подробности решения — в `AGENTS.md`.
