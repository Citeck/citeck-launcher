# Версии формата workspace

Launcher 2.16.1 и новее выбирает первый доступный файл в репозитории workspace:

1. `workspace-v2.yml`
2. `workspace-v2.yaml`
3. `workspace-v1.yml`
4. `workspace-v1.yaml`
5. `workspace.yml`

Файлы не объединяются: v2 содержит полную конфигурацию. Если v2 отсутствует,
используется прежняя конфигурация v1. Выбор одинаков для клона git, локального
импорта и редактора workspace. Редактор показывает выбранный YAML и сохраняет
локальную дельту поверх него; существующие дельты v1 сохраняются и применяются
к v2 при появлении нового файла. Reset возвращает выбранный git-эталон.

Launcher 2.16.0 и более ранние версии не выбирают v2. В публичном workspace
`workspace-v1.yml` сохранён совместимым с прежней конфигурацией; generated secrets,
managed `type: SEAWEEDFS`, S3-провайдер и его ссылка находятся только в v2.
Это предотвращает чтение generated secrets старыми лаунчерами как констант с
пустыми значениями и чтение неизвестного типа SEAWEEDFS как сырого контейнера.

Бандл Enterprise RC6 с SeaweedFS требует `minLauncherVersion: "2.16.1"`.
Ограничение версии бандла и разделение файлов решают разные задачи: первое
защищает выбор нового бандла, второе — чтение общей конфигурации workspace.
Старые версии, поддерживающие minLauncherVersion, пропускают несовместимый RC6.
Для версий без этой проверки разделение файлов само по себе не добавляет
поддержку нового бандла.

Стенды, уже использующие S3 из экспериментальной ветки с v1, нужно сначала
обновить до Launcher 2.16.1, а затем переводить на репозиторий с разделёнными
v1/v2. Старый бинарник не прочитает S3-настройки после их переноса в v2.

При сопровождении публичного workspace общие совместимые изменения нужно
вносить в оба файла; возможности нового формата — только в v2. Не удаляйте v1,
пока поддерживаются старые лаунчеры.

## Обновление после смены версии Launcher

Начиная с 2.16.2 существующий git-клон workspace обновляется при загрузке
новой версии Launcher, не дожидаясь `repoPullPeriod`. Это работает и на desktop,
и на сервере. Успешная версия записывается атомарно в
`.git/citeck-sync-version` каждого клона. Первый запуск нового механизма с
существующим клоном без отметки тоже обновляет его один раз. Откат версии
также считается сменой версии.

Повторные desktop-запуски той же версии используют обычный таймер. На сервере
дальнейшая синхронизация остаётся ручной (`citeck update`); автоматическое
исключение касается только workspace, а не отдельных bundle-репозиториев.
При отсутствии установленного клона сервер сам его не создаёт.

`--offline` полностью отключает этот pull. Локальный импорт workspace без
`.git` сохраняет приоритет и не заменяется git-клоном. Пользовательский Skip
для git-хоста тоже сохраняется. Ошибка pull или Skip не записывают новую
версию: сохраняется доступная конфигурация из кэша, а следующая разрешённая
попытка не ждёт таймера. Сам файл конфигурации по-прежнему выбирается по
приоритету v2/v1, и локальные overrides применяются после обновления.

## Ошибки ручного обновления Git

«Принудительное обновление», «Обновить и запустить» и обновление списка бандлов
сообщают об ошибке Git даже при наличии старой локальной копии. Запуск без
обновления при загрузке Launcher и работа offline сохраняют использование кэша.
При неудачном явном обновлении работающий namespace не перегенерируется молча
по старым данным.

Окно ошибки предлагает три действия:

* **Использовать кэш** — только если есть пригодная локальная копия нужного
  репозитория. Клон с другим origin не подходит. Выбор относится к текущей
  операции и её повторным попыткам: если недоступны несколько репозиториев,
  уже выбранные копии сохраняются в этой цепочке. Следующее независимое
  обновление снова обращается к Git; глобального пропуска для всего хоста нет.
* **Повторить** — повторить ту же операцию. Повтор обновления workspace не
  подменяется его активацией.
* **Выбрать другой секрет** — сохранить привязку к репозиторию, который
  действительно сообщил ошибку, и повторить попытку. Для бандлов это не
  меняет токен самого workspace: ссылка `authType: secret:<id>` записывается
  в локальную дельту workspace. Явная ссылка не заменяется другим токеном,
  если выбранный секрет удалён или недоступен.

В окне показано время последнего **успешного** Git sync из сохранённого состояния.
Неудачная попытка или использование кэша не обновляют эту дату. Если достоверной
отметки нет, отображается «время неизвестно»; время изменения файлов не используется.

Диагностические логи содержат id workspace и выбранного секрета, доступность
учётных данных, факт замены значения и неоднозначный выбор среди нескольких
Git-токенов. Значения токенов и паролей в этих записях отсутствуют. При восстановлении
после миграции 1.x → 2.x нужно различать URL репозитория, `authType` и привязку
секрета: создание нового секрета само по себе ещё не выбирает его для репозитория.
