# Мажорное обновление PostgreSQL в Citeck Launcher

В Citeck Launcher мажорное обновление PostgreSQL выполняется через полный
SQL-дамп (`pg_dumpall`) и восстановление в новый volume. Например, при переходе
17 → 18 создаётся новый кластер, а старый volume сохраняется для отката.
На время миграции останавливается весь namespace.

## Запуск обновления

```bash
# Посмотреть текущую и предлагаемую версии зависимостей
citeck deps

# Запустить обновление PostgreSQL
citeck deps upgrade postgres

# Посмотреть результат
citeck deps
```

Целевая версия берётся из bundle. Команда сначала показывает результаты
предварительных проверок и запрашивает подтверждение. Для автоматического запуска:

```bash
citeck deps upgrade postgres --yes
```

Миграция выполняется в daemon: закрытие терминала или `Ctrl+C` прекращает показ
прогресса, но не саму миграцию. Чтобы сразу вернуть управление терминалу:

```bash
citeck deps upgrade postgres --detach
```

## Порядок миграции

### 1. Предварительные проверки

Launcher сверяет версию исходного кластера по `PG_VERSION`, проверяет направление
обновления, свободное место и наличие целевого volume. Поддерживается переход
на большую мажорную версию; версия назначения определяется bundle.

Для дампа и нового кластера проверяется наличие свободного места по формуле
`размер исходных данных + 512 MiB` для каждого. Если они находятся на одном
диске, требуется суммарно **`2 × размер данных + 1 GiB` свободного места**,
сверх уже занятого старым кластером. Это предварительная оценка, а не резервирование
дискового пространства.

Дамп снимается сжатым (см. шаг 4), но эта оценка по-прежнему считается от
размера **несжатых** данных: заранее неизвестно, во сколько раз сожмётся
конкретный кластер, поэтому требование не понижается. Реальный расход места
из-за сжатия дампа обычно меньше оценки, а не больше — это единственное
допустимое направление ошибки.

Существующий целевой volume не удаляется без явного разрешения. Если проверка
показала оставшийся от прошлой попытки volume и его действительно можно удалить:

```bash
citeck deps upgrade postgres --replace-existing
```

Этот флаг разрешает удаление существующего целевого volume; он не нужен
для обычного обновления в новый volume.

### 2. Остановка namespace и загрузка нового образа

Launcher останавливает namespace, затем загружает образ целевой версии PostgreSQL.

### 3. Запуск временного контейнера старой версии

Временный контейнер запускается со старым образом и исходным volume.
Launcher ждёт готовности PostgreSQL через TCP:

```bash
pg_isready -h 127.0.0.1 -U postgres

psql -h 127.0.0.1 -U postgres -d postgres -q -At -c 'select 1'
```

Здесь и далее приведены команды, которые Launcher выполняет **внутри временных
контейнеров**. Вручную запускать их для штатного обновления не требуется.
Временные контейнеры используют конфигурацию PostgreSQL namespace и не публикуют
его порты на хосте.

### 4. Снятие полного SQL-дампа

Перед дампом запоминаются список БД, роли и количество пользовательских таблиц
в каждой БД.

```bash
bash -c "set -o pipefail; pg_dumpall -h 127.0.0.1 -U postgres | gzip -1 > '/citeck/depsmig/dump.sql.gz'"
```

Это именно `bash -c` с `set -o pipefail`, а не `sh -c`: в конвейере без `pipefail`
код возврата берётся только у **последней** команды, поэтому упавший на середине
`pg_dumpall`, за которым идёт успешно отработавший `gzip`, выглядел бы как успех —
Launcher восстановил бы и признал проверенным обрезанный кластер. `/bin/sh` в
образе postgres — это dash, а `pipefail` появился в нём только в версии 0.5.12;
bash в образе есть всегда и поддерживает `pipefail` с любой версии, поэтому
выбран именно он.

Файл находится в общей директории, подключаемой к исходному и целевому временным
контейнерам. На хосте это `deps-migration/postgres/dump.sql.gz` под базовым
каталогом volumes namespace. Дамп снимается сжатым: SQL-текст дампа сжимается в
несколько раз даже при `gzip -1` — низкий уровень сжатия выбран ради скорости, а
не ради лучшего коэффициента, поскольку namespace на это время уже остановлен.

### 5. Создание нового кластера

Launcher удаляет временный исходный контейнер, создаёт новый volume и запускает
в нём временный контейнер PostgreSQL целевой версии. Поколение volume увеличивается
при каждой миграции. Launcher снова ждёт готовности сервера.

Старый volume сохраняется и не преобразуется в формат новой версии. При этом
исходный PostgreSQL запускается с обычным доступом к нему на запись: это не
read-only mount и не побайтово неизменяемый снимок.

### 6. Восстановление дампа

```bash
bash -c "set -o pipefail; gunzip -c '/citeck/depsmig/dump.sql.gz' | psql -h 127.0.0.1 -U postgres -d postgres -q -o /dev/null"
```

Здесь `pipefail` защищает и в обратную сторону: без него повреждённый архив,
на котором упадёт `gunzip`, оставил бы `psql` читать пустой ввод и завершиться
кодом 0 — восстановление выглядело бы успешным. `psql` больше не получает
дамп через `-f <файл>`, а читает его из конвейера — это и есть причина, по
которой в логе больше нет команды с `-f`.

`ON_ERROR_STOP` намеренно не используется: допускается ошибка
`role "postgres" already exists`, поскольку роль уже создана при инициализации.
Launcher отдельно проверяет `stderr`: остальные строки `ERROR:` и ненулевой код
завершения означают неуспех восстановления.

### 7. Проверка результата и сбор статистики

Сравниваются списки БД, роли и количество пользовательских таблиц в каждой БД.
Построчного сравнения данных нет. Затем выполняется:

```bash
vacuumdb -h 127.0.0.1 -U postgres --all --analyze -q
```

Эта команда собирает статистику для планировщика запросов нового кластера.

### 8. Переключение на новую версию

После успешных проверок удаляется временный целевой контейнер и фиксируются
новый образ и поколение volume. Временный дамп удаляется. Namespace запускается,
если до миграции он работал. **Старый volume остаётся для отката.**

Ошибки финальной очистки или перезапуска после фиксации результата сообщаются
как предупреждения: переключение на новые данные уже состоялось.

### Переход через несколько версий одной миграцией

Если версия, которую называет bundle, отстоит от текущей больше чем на один
мажор, Launcher не ограничивается одним шагом: bundle называет весь путь по
промежуточным версиям, и Launcher проходит его целиком в рамках **одной**
миграции — с одним журналом и одним увеличением поколения volume, а не по
одному на каждую промежуточную версию.

Шаг 3 (запуск временного контейнера со старой версией на исходном томе)
выполняется только один раз, в начале миграции. Шаги 4–6 (снятие дампа,
создание нового кластера и восстановление) в этом случае повторяются по разу
на каждую промежуточную версию пути. Самый первый дамп снимается с исходного
тома, как описано выше; каждый следующий — уже с временного кластера, в
который был восстановлен предыдущий дамп (он уже запущен и снятие дампа не
требует отдельного запуска контейнера), а не заново с исходных данных. Все
промежуточные кластеры используют один и тот же временный (scratch) volume:
он пересоздаётся перед восстановлением очередной версии и удаляется сразу
после того, как с него снят следующий дамп. Поэтому на диске никогда не
существует больше одного временного кластера и одного дампа одновременно, а
требование к свободному месту (шаг 1) не растёт с числом промежуточных
версий. Отдельного поколения volume промежуточные кластеры не занимают:
новое поколение получает только кластер последней версии пути.

Шаги 1, 2, 7 и 8 (предварительные проверки, остановка namespace, проверка
результата и переключение) выполняются один раз для всей цепочки, а не для
каждой промежуточной версии; в частности, шаг 2 заранее загружает образы
**всех** версий пути, а не только конечной. При ошибке на любом шаге цепочки
откатывается вся миграция целиком, к исходному, до-миграционному состоянию —
независимо от того, сколько промежуточных версий уже было пройдено успешно:
до самого конца ничего не фиксируется частично.

## Ошибки и откат

При ошибке до фиксации результата Launcher по журналу миграции удаляет временные
контейнеры, созданный целевой volume и дамп, затем возвращает прежний namespace.
При переходе через несколько версий откат дополнительно удаляет временный
(scratch) volume промежуточных кластеров, если журнал успел его записать —
это отдельная запись журнала (`ScratchVolume`), не совпадающая с записью
целевого volume (`CreatedVolume`), и удаление обеих идемпотентно: попытка
удалить уже отсутствующий scratch volume (он мог быть переиспользован и
удалён ещё до ошибки) не считается неудачей отката. Если очистка не
завершилась, namespace остаётся остановленным, чтобы не запустить два
PostgreSQL на одном исходном volume. Журнал также используется для
восстановления после прерывания работы daemon.

После успешного обновления можно явно вернуться на предыдущую версию:

```bash
citeck deps rollback postgres
```

Доступность отката показывает `citeck deps`. Он возможен, если Launcher сохранил
результат предыдущей миграции и старый volume ещё существует.

Откат переключает namespace на **старый образ и старые данные**. Записи, сделанные
после обновления, остаются в новом volume, но после отката приложению недоступны;
обратно в старую БД они не переносятся. Оба volume сохраняются.
Автоматического возврата на оставленный новый volume нет: повторное обновление
выполняется новой миграцией из старого кластера в очередной новый volume.
