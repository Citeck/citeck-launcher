# Экспериментальные (beta) модули

Релиз платформы может поставлять новые микросервисы как **экспериментальные**: они
входят в bundle, но запускаются только на тех стендах, где их включили явно, и
везде помечены как **BETA**. Так новый сервис сканирования или новый движок
резервного копирования можно отдать пользователям уже в `2026.4-RC1`, оставить
экспериментальным в `2026.4`, а в `2026.5` сделать постоянным модулем — не меняя Launcher.
Конфигурация сервиса в workspace нужна на обеих стадиях.

Секцию `experimental:` понимает **Launcher 2.18.0 и новее**; более ранние версии её
не читают (см. «Совместимость» ниже).

Три уровня, как и везде в Launcher: **bundle (релиз)** решает, что модуль существует и
что он beta; **workspace** решает, как модуль сконфигурирован; **namespace (стенд)**
решает, включён ли он.

## Bundle: секция `experimental:`

```yaml
# community/2026.4-RC1.yaml
EcosModelApp:
  image: core/ecos-model:4.1.0

experimental:
  documentScanner:                        # id функции — то, что хранит namespace.yml
    title:                                # название в диалоге: строка или по языкам
      ru: Сканирование документов
      en: Document scanning
    description:
      ru: Новый микросервис распознавания. Beta — формат данных может измениться.
      en: New document recognition service. Beta — the data format may change.
    apps:                                 # контейнеры, которые включает одна галочка
      citeck-scanner:
        image: core/citeck-scanner:1.0.0    # те же формы, что у обычной записи
      scanner-postgres:
        image: postgres:17.11
  backupEngineV2:
    title: Новый движок резервного копирования   # одна строка — для всех языков
    apps:
      backup-engine:
        image: core/backup-engine:0.3.0
```

Секция — набор **функций**, по ключу на функцию. Ключ — id функции
(`^[A-Za-z0-9][A-Za-z0-9_.-]*$`); именно его хранит `namespace.yml` и показывает
UI, когда названия нет. У функции три ключа:

| Ключ | Назначение |
|---|---|
| `apps` | Записи приложений в той же форме, что на верхнем уровне bundle (`image:` строкой, парой `{repository, tag}` или списком, из которого берётся первый элемент). Все записи функции включаются и выключаются вместе. Обязателен. |
| `title` | Название функции в диалоге и в `citeck features`. Строка или карта по языкам (см. ниже). Без него показывается id. |
| `description` | Пояснение под названием. Строка или карта по языкам. |

Bundle остаётся списком версий: секция добавляет к нему только то, какие из
этих версий в данном релизе beta и под какой общей галочкой. Конфигурация модуля
(окружение, тома, пробы) по‑прежнему живёт в workspace — см. ниже.

### Текст на нескольких языках

`title` и `description` принимают либо одну строку — она показывается всем, —
либо карту «язык → текст» в форме `MLText` платформы (`ru`, `en`, `de`, …).
Язык выбирает демон при ответе на запрос: тот, что запросил клиент (UI и CLI
передают свою локаль с каждым запросом; без неё — `locale` из `daemon.yml`),
иначе `en`, иначе первый язык по алфавиту. Клиенты получают готовую строку.
Ключ языка — только код языка: `ru-RU` и `ru_RU` читаются как `ru`. Мастер
`citeck install` читает bundle сам, минуя демон, и выбирает язык по локали CLI.

Что пропускается с предупреждением в логе и не ломает bundle: приложение без
читаемого `image:`; приложение, имя которого уже занято обычной записью bundle
(побеждает обычная запись: одно имя, одно определение); приложение, которое
назвали две функции (остаётся у первой по порядку в файле: один контейнер — один
переключатель); функция без `apps:`, с недопустимым id или оставшаяся без единого
приложения; `title`/`description` нечитаемой формы — тогда их просто нет.

### Совместимость

Секция **безопасна для старых лаунчеров по построению**, как `dependencies:`.
Парсер bundle отдаёт каждый ключ верхнего уровня как приложение и молча пропускает
запись без прямого ключа `image:`; у `experimental:` его нет — её дети не
приложения, а функции. Любой Launcher старше 2.18.0 поэтому не видит beta‑модулей вовсе, и
bundle с этой секцией не требует `minLauncherVersion`. Поведение Kotlin‑лаунчера 1.x на такой
секции отдельно не проверялось; если 1.x всё ещё читает эти bundle — проверить.

## Workspace: конфигурация модуля

Модуль конфигурируется как любой другой сервис. Явное включение beta-функции
не обходит конфигурацию workspace: если задан непустой список `webapps:`,
webapp должен быть в нём и до, и после перехода в stable. Пустой список сохраняет
обычное поведение генератора без фильтра, одинаковое для beta и stable.
Запись также задаёт alias (`CiteckScannerApp` → `citeck-scanner`) и `defaultProps`.
Для произвольного контейнера нужна запись в `additionalApps:` **без `image:`**:
образ называет bundle, а запись описывает окружение, тома и пробы:

```yaml
webapps:
  - id: citeck-scanner
    aliases: [CiteckScannerApp]

additionalApps:
  - name: backup-engine          # образ придёт из секции experimental: bundle
    environments:
      ZK_HOSTS: ${ZK_HOST}:${ZK_PORT}
    volumes:
      - backup_engine_data:/data
```

Пока функция на стенде выключена, bundle с точки зрения генерации «не называет
образ» модуля — и срабатывают обычные правила: запись `additionalApps` без образа не
генерируется, webapp без записи в bundle не генерируется, зависящие от них
приложения выпадают через стандартную проверку `dependsOn`.

## Namespace: включение

Пользователь включает функции в диалоге создания или редактирования стенда — секция
«Экспериментальные функции» появляется, когда выбранный bundle предлагает хотя бы
одну; каждая строка несёт бейдж **BETA**, название, описание и список контейнеров.
Выбор хранится в `namespace.yml`:

```yaml
experimentalFeatures: [documentScanner]
```

Включённые модули генерируются и запускаются вместе со стендом и помечены **BETA** в
таблице приложений (поле `experimental` в `AppDto`) и в `citeck status`. Выключение
убирает контейнеры при следующем применении конфигурации (reload); **тома с данными
остаются** — как при выключении MongoDB.

Что важно знать о хранимом списке:

* **Неизвестный id инертен и сохраняется.** Если bundle не предлагает функцию
  (модуль стал постоянным, ещё не выпущен или bundle другой) — ничего не
  генерируется и ничего не отклоняется. Это принципиально: обновление на релиз,
  где модуль «повзрослел», не должно отклоняться, а откат bundle — терять выбор.
* Проверяются только **добавляемые** id: при создании — все (хранимого списка ещё
  нет), при редактировании — те, что появились в запросе. Неизвестный выбранному
  bundle id отклоняется с `EXPERIMENTAL_FEATURE_UNKNOWN` (400); изменение при
  bundle, которого нет на диске, — тем же кодом (409).
* Значение `experimentalFeatures` из шаблона workspace **игнорируется** при создании,
  как и `contentStorage`: beta‑модуль — выбор оператора в диалоге.
* Явно включённый модуль **никогда не задерживается** шаблонным `detachedApps` и
  сразу записывается в `KnownApps` стенда.

## Серверный режим: `citeck features`

В серверном режиме диалога нет; те же действия выполняет CLI поверх того же API.

```bash
citeck features                      # = citeck features list
citeck features enable <id>
citeck features disable <id>
citeck features --format json        # DTO GET /experimental-features как есть
```

`citeck features` показывает функции, которые предлагает bundle **активного**
стенда — по строке на функцию: id, название, контейнеры, `ON`/`OFF` — и
подпись `[beta]`. Если bundle нет на диске (`reason: BUNDLE_UNRESOLVED`),
команда так и говорит и предлагает `citeck update`. Описания функций печатаются
под таблицей.

`enable`/`disable` читают текущее состояние предлагаемых функций, переключают
одну и отправляют `PUT /api/v1/namespaces/{id}/edit` с полем
`enabledExperimentalFeatures` — состоянием **всех предлагаемых** функций (и
только их: инертные хранимые id демон сохраняет сам). Неизвестный id
отклоняется локально со списком предлагаемых; функцию в уже запрошенном
состоянии команда не трогает и ничего не отправляет. Демон перезагружает
конфигурацию активного стенда: на запущенном стенде контейнеры модуля
создаются или удаляются сразу, на остановленном — при следующем
`citeck start`. Тома с данными выключенного модуля остаются. С `--format json`
`enable`/`disable` печатают один объект-вердикт:
`{id, enabled, changed, namespaceStatus, apps}`.

Включённые модули видны в `citeck status` с пометкой `[beta]` и легендой под
таблицей.

### `citeck install`

Если выбранный релиз предлагает экспериментальные функции, мастер установки после
шага о хранении контента задаёт вопрос «Экспериментальные (beta) модули» — список с
отметками (пробел отмечает, Enter подтверждает), по умолчанию **ничего не выбрано**.
Выбор записывается в `namespace.yml` как `experimentalFeatures:`; релиз без секции
`experimental:` вопроса не задаёт.

### Для агентов

Каталог `citeck agent` описывает три операции: `features.list`
(`GET /api/v1/experimental-features`), `features.enable` и `features.disable`
(обе — `PUT /api/v1/namespaces/{id}/edit` с полем `enabledExperimentalFeatures`;
маршрут ссылается на первую из них, в каталоге перечислены обе). См.
[agent-api.md](agent-api.md).

## API

* `GET /api/v1/experimental-features?bundleRepo=&bundleKey=[&workspaceId=]` — функции,
  которые предлагает bundle (резолв offline, как у `/content-storage/options`);
  `reason: BUNDLE_UNRESOLVED`, если bundle нет на диске.
* `POST /api/v1/namespaces` — поле `experimentalFeatures: [ids]`.
* `GET /api/v1/namespaces/{id}/edit` — `experimentalFeatures: [{id, title, description, apps, enabled}]`
  для хранимого bundle и `storedExperimentalFeatures: [ids]` — все сохранённые
  включённые ID, включая инертные. Форма инициализирует выбор из полного списка,
  поэтому при возврате к beta-bundle ранее включённые функции снова отмечены.
* `PUT` — `enabledExperimentalFeatures: [ids]`: состояние **предлагаемых** функций
  (отсутствие поля = не менять). Форма отправляет его только после явного изменения
  переключателя; одна смена bundle не заменяет сохранённый выбор.

## Жизненный цикл: от beta к постоянному модулю

Feature ID стабилен на протяжении beta, stable и поддерживаемых откатов: не
переиспользуйте его для другой функции. Инертный ID хранится без автоматического
срока удаления, чтобы откат bundle восстановил выбор. Удаление/миграция таких ID
требует отдельной политики совместимости; молчаливая очистка при обновлении запрещена.
Конфигурация workspace должна поддерживать сервис на всех этих стадиях.

1. `2026.4-RC1`, `2026.4` — модуль в секции `experimental:`. Стенды включают его по
   желанию; остальные его не видят.
2. `2026.5` — записи из `apps:` функции **переносятся** на верхний уровень bundle,
   сама функция из секции удаляется. Дальше работают существующие механизмы:
   * стенд, где функция была включена, уже записал модуль в `KnownApps` — он
     продолжает работать без пауз;
   * стенд, где функцию не включали, видит «новое приложение» → решение принимает
     `namespaceTemplates[].detachedApps` шаблона (см.
     [app-startup-and-detach.md](app-startup-and-detach.md)). Чтобы постоянный
     модуль **не стартовал по умолчанию**, сопровождающий workspace добавляет его в
     `detachedApps`.
3. Хранимый id функции на таких стендах остаётся инертным; удалять его не нужно.
