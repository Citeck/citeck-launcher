# Приоритет образов приложений

Бандл задаёт версию релиза и имеет приоритет над образами из `namespace.yml`
и workspace. Это правило действует для веб-приложений, pgAdmin, stt-sidecar,
proxy, MongoDB и записей `additionalApps` (в том числе observer); исключения для
pgAdmin нет.

Порядок выбора образа при генерации, от высшего приоритета к низшему:

1. `dependencies` бандла.
2. Образ приложения в основном разделе бандла.
3. Образ в конфигурации namespace, если у приложения есть такое поле.
4. `dependencies` workspace.
5. Типизированные настройки workspace. У веб-приложений настройки конкретного
   приложения имеют приоритет над общими `defaultWebappProps`.
6. Встроенный образ по умолчанию, если он предусмотрен генератором.

Если бандл не задаёт образ, нижние уровни используются как fallback.
Если образ из namespace или из `dependencies` workspace отличается от заданного
бандлом, Launcher выбирает образ бандла и пишет предупреждение в лог.

Чтобы явно изменить образ на конкретном стенде, используется правка приложения:

```bash
citeck edit pgadmin
```

Сохранённый patch применяется после генерации и имеет приоритет над образом бандла.
Для возврата к сгенерированным настройкам:

```bash
citeck edit pgadmin --reset
```

Например, при `pgadmin.image: dpage/pgadmin4:9.12` в namespace и
`dpage/pgadmin4:9.17` в бандле будет выбран `9.17`. При отсутствии образа pgAdmin
в бандле используется настройка namespace.

Этот порядок относится к выбору образов, а не ко всем полям конфигурации:
настройки памяти, портов, окружения и включения приложений сохраняют свои правила.
Изменение образа меняет конфигурацию контейнера и при её применении приводит
к его пересозданию.

Верхнеуровневый ключ бандла `minLauncherVersion` в этот порядок не входит: он не
участвует в выборе образа, а только определяет, можно ли вообще ЗАПИСАТЬ конфигурацию
namespace с этим бандлом на данном лаунчере. Кроме того, `LATEST` разрешается в
самый новый бандл, который этот лаунчер может запустить.

## Образ-список: лестница только в `dependencies:`

Значение `image:` может быть не только строкой или `{repository, tag}`, но и
списком версий — но только в `dependencies:`, в записях бандла, в
типизированных блоках workspace и в типизированных записях `additionalApps`
(`type: POSTGRES` / `type: QDRANT`). Правило чтения списка зависит от уровня.

* В секции `dependencies:` (бандла или workspace) список — это **лестница**:
  последний элемент — цель, а промежуточные версии описывают путь, которым
  миграция поднимает данные к цели за один проход, шаг за шагом. Именно эта
  секция участвует в защите данных зависимостей ниже.
* В остальных местах, где список допустим — в записях приложений бандла
  (его верхнеуровневых ключах), в типизированных блоках workspace
  (`postgres:`, `zookeeper:` и т. д.) и в типизированных записях
  `additionalApps`, — берётся **первый** элемент списка. У этих уровней нет
  пина, нет удержания и нет миграции, поэтому единственное безопасное чтение —
  самая консервативная ступень.
* Обычная (нетипизированная) запись `additionalApps`, `webapps[].defaultProps`,
  `defaultWebappProps` и `namespace.yml` принимают только строку. Список там —
  ошибка YAML; в конфигурации workspace она отбрасывает конфигурацию workspace
  целиком.

Обоснование и формат лестницы — в спецификации
[«Многошаговое обновление зависимостей»](specs/2026-09-15-multi-hop-dependency-upgrade-design.md).

## Защита данных зависимостей

Для PostgreSQL, RabbitMQ, ZooKeeper, Qdrant, Keycloak, MongoDB и кластеров,
объявленных workspace в `additionalApps` (`type: POSTGRES` / `type: QDRANT`,
например `observer-postgres`), после выбора образа отдельно проверяется
совместимость с сохранённой версией данных. При несовместимом обновлении бандл
задаёт целевую версию, но текущая остаётся закреплённой до миграции.
Это не приоритет `namespace.yml`, а защита существующего volume.

Защищать нечего, если данных нет: у зависимости нет контейнера, а её volume
(текущего поколения) удалён — например, со страницы томов. Тогда
закреплённая версия ничего не удерживает, применяется версия бандла, и
обновление не предлагается. Любая ошибка при проверке Docker, существующий
(даже пустой) volume или незавершённая миграция оставляют закрепление в силе.

```bash
citeck deps
citeck deps upgrade postgres
```

Подробности: [мажорное обновление PostgreSQL](postgres-major-upgrade.md).
