# Observer — наблюдаемость стенда

`citeck-observer` — собственный сервис наблюдаемости Citeck: приёмник логов и
OTLP-телеметрии со встроенным UI, плюс мониторинг инфраструктуры стенда
(RabbitMQ, PostgreSQL, ZooKeeper). Launcher поднимает его вместе с namespace —
если релиз, который стенд запускает, его поставляет.

## Когда observer появляется на стенде

Флага в конфигурации namespace больше нет. Observer генерируется тогда и только
тогда, когда **бандл называет его образ** — по тому же правилу, что и `qdrant`:
есть ли на стенде сервис, решает релиз, который стенд запускает, а не файл
конкретного стенда.

Бандл, который поставляет наблюдаемость, выглядит так:

```yaml
observer:
  image:
    repository: harbor.citeck.ru/public/citeck-observer
    tag: v1.5.2

dependencies:
  # Собственная база observer'а — в секции dependencies, потому что это
  # сторонний образ: лончеры без гейта версий её не видят (см. AGENTS.md).
  observer-postgres:
    image: postgres:18.6
```

Образ обсервера лежит в публичном проекте Harbor и тянется анонимно, поэтому
запись годится и для community-бандла.

База обсервера — отдельный кластер со своим пином и своим томом, поэтому её
версию можно вести независимо от основной базы стенда. На пустом томе бандл
применяется как есть; на существующих данных смена мажора проходит обычным
путём — гейт придерживает её и предлагает `citeck deps upgrade observer-postgres`
(см. [Обновление мажорной версии PostgreSQL](postgres-major-upgrade.md)).

Дальше действуют обычные правила: если шаблон workspace перечисляет `observer`
и `observer-postgres` в `detachedApps`, на стенде они приедут остановленными, и
включаются как любое другое приложение:

```bash
citeck start observer-postgres
citeck start observer
```

Запускать нужно оба — явный старт зависимости за собой не тянет
(см. [что стартует на стенде](app-startup-and-detach.md)). Компаньон и владелец
перечисляются в `detachedApps` **вместе**: иначе на стенде с выключенным
observer'ом поднимется одна его база.

Приоритет выбора образа — общий (см. [Приоритет образов приложений](config-layers.md)):
`dependencies` бандла → образ в бандле → `dependencies` workspace →
типизированные настройки workspace. Встроенного дефолта у самого observer'а
**нет**: без образа в бандле сервиса просто не существует.

## Что поднимается

Два контейнера.

**`observer`** — сам сервис:

| Порт | Назначение |
|---|---|
| 17014/udp | приём логов |
| 17015 | OTLP HTTP/protobuf |
| 17016 | HTTP API и встроенный UI |
| 17017 | OTLP gRPC |

Проба готовности и liveness — HTTP `/health` на 17016, лимит памяти 512 МБ,
зависит от ZooKeeper (через него же регистрируется в discovery) и от своей БД.
Аутентификация — тот же JWT-секрет, что у веб-приложений namespace.

**`observer-postgres`** — отдельный кластер PostgreSQL под нагрузку
наблюдаемости (много записи, агрегирующие запросы, JSONB-индексы): свои
`shared_buffers`, `work_mem`, настройки WAL, порт наружу 14524 для локальной
отладки, лимит памяти 512 МБ.

Она **объявлена в конфигурации** (секция `databases:` workspace-конфига, см.
[Дополнительные базы данных](databases.md)) — лончер держит её настройки как
умолчания, а workspace может переопределить их по полям. Добавление базы для
другого сервиса правок в лончере не требует.

Это **полноценная зарегистрированная зависимость** — всё, что есть у основной
базы стенда, есть и у неё:

* **пин версии**: бандл, поднимающий мажор на существующем кластере, придерживается
  и показывается как предложение обновиться, а не применяется молча;
* **счётчик поколений тома**: первое поколение — `obs_postgres2`, следующее после
  миграции — `obs_postgres3`;
* **раскладка данных по мажору образа**: явный `PGDATA` до 17, родительский
  монтаж по умолчанию образа с 18 — то же правило, что у основной базы;
* **миграция и откат** тем же планом «дамп в новый том»:

```bash
citeck deps                              # observer-postgres в общем списке
citeck deps upgrade observer-postgres    # дамп → новый том → проверка → коммит
citeck deps rollback observer-postgres   # вернуться на сохранённый том
```

Две базы независимы: у каждой свой пин, своё поколение тома, свой каталог
дампа. Миграция одной не трогает данные другой.

> Разовое последствие регистрации: том переименован с `obs_postgres` на
> `obs_postgres2` (первое поколение счётчика). Том вне счётчика мигрировать
> нельзя в принципе — копирующее обновление строит следующее поколение рядом с
> текущим, — поэтому старые данные наблюдаемости остаются на диске в старом
> томе и не подхватываются. Для истории метрик и логов это приемлемая цена;
> старый том можно удалить (`citeck clean --volumes`).

## Мониторинг инфраструктуры

Включён из коробки и не требует настройки:

* **RabbitMQ** — через Management API, под сервисной учётной записью `citeck`
  (тег `monitoring`), чтобы ротация пароля администратора не ломала доступ;
* **PostgreSQL** — основной кластер стенда через представления `pg_stat`;
* **ZooKeeper** — командой `mntr`.

## Локальная отладка

Для сценария «остановить в лончере — запустить из IDE» Launcher кладёт в
CloudConfigServer конфигурацию observer'а с localhost-адресами (порты БД, ZK,
RabbitMQ, свои порты). То есть контейнер можно остановить и поднять сервис
локально, не переписывая конфигурацию руками.

## Чего Launcher не делает

Он **не прописывает веб-приложениям адрес OTLP-приёмника**. Observer поднимается
и мониторит инфраструктуру, но телеметрию приложений сам по себе не получает —
если она нужна, приложения настраиваются отдельно.

Имена `observer` и `observer-postgres` зарезервированы: их нельзя занять
`additionalApps` в конфигурации workspace.
