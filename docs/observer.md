# Observer — наблюдаемость стенда

`citeck-observer` — собственный сервис наблюдаемости Citeck: приёмник логов и
OTLP-телеметрии со встроенным UI, плюс мониторинг инфраструктуры стенда
(RabbitMQ, PostgreSQL, ZooKeeper). Launcher поднимает его вместе с namespace —
если релиз, который стенд запускает, его поставляет, а конфигурация workspace
его объявляет.

## Observer — это конфигурация

С 2.15 в лаунчере **нет кода под observer**. Сервис и его база объявлены в
конфигурации workspace — записями `additionalApps:` и секретом в `secrets:`, —
а лаунчер исполняет объявление так же, как любой другой кастомный сервис.
Эталонная копия блока лежит в репозитории лаунчера,
`internal/namespace/testdata/observer-workspace.yml`; тот же блок стоит в обоих
workspace (`launcher-workspaces` и `launcher-public-workspace`), и держать их
нужно одинаковыми. Тесты генератора читают именно эталонную копию.

Коротко, что в блоке:

```yaml
secrets:
  - id: observer-db          # умолчание пароля базы observer'а
    value: observer
additionalApps:
  - name: observer-postgres  # база: type POSTGRES, том obs_postgres, порт 14524
    type: POSTGRES
    password: ${secret:observer-db}
    # … user/db/port/volumeBase/memoryLimit/settings
  - name: observer           # сам сервис: без image — образ называет бандл
    kind: CITECK_ADDITIONAL   # в списке приложений — среди «Citeck Additional», не «Сторонних»
    dependsOn: [observer-postgres, zookeeper]
    # … environments/ports/probes/resources/cloudConfig
```

Контейнеры, которые получаются из этого блока, **совпадают байт в байт** с
теми, что поднимал встроенный код 2.14 (сверено по входу хэша развёртывания
на настоящих файлах обоих workspace), поэтому обновление лаунчера их не
пересоздаёт; том, пин и данные базы остаются прежними.

Лаунчеры до 2.15 этот блок не понимают: они отбрасывают `additionalApps`
целиком (с предупреждением в логе) и поднимают свой встроенный observer, как
раньше: 2.14 — по образу в бандле, более ранние — только по флагу
`observer.enabled` в `namespace.yml`, выключенному по умолчанию. Лаунчер 2.15+
с конфигурацией workspace **без** блока observer не поднимает вовсе.

## Когда observer появляется на стенде

Флага в конфигурации namespace нет. Observer генерируется тогда и только тогда,
когда **бандл называет его образ** — запись `observer` без собственного
`image:` берёт образ из бандла, а бандл, который его не называет, сервиса не
получает. Это то же правило, что у `qdrant`: есть ли на стенде сервис, решает
релиз, который стенд запускает, а не файл конкретного стенда.

Бандл, который поставляет наблюдаемость, выглядит так:

```yaml
observer:
  image:
    repository: harbor.citeck.ru/public/citeck-observer
    tag: v1.5.2

dependencies:
  # Собственная база observer'а — в секции dependencies, потому что это
  # сторонний образ: лаунчеры без гейта версий её не видят (см. AGENTS.md).
  observer-postgres:
    image: postgres:18.6
```

Образ обсервера лежит в публичном проекте Harbor и тянется анонимно, поэтому
запись годится и для community-бандла.

Бандл, назвавший observer без его базы, observer не получает: сервис зависит от
базы, и зависимость, которой нет, исключает зависимого (в логе — строка
`App excluded from the namespace … missingDep=observer-postgres`). То же, если у
namespace нет значения секрета `observer-db`: без пароля не поднимется ни база,
ни observer.

База обсервера — отдельный кластер со своим пином и своим томом, поэтому её
версию можно вести независимо от основной базы стенда. На пустом томе бандл
применяется как есть; на существующих данных смена мажора проходит обычным
путём — гейт придерживает её и предлагает `citeck deps upgrade observer-postgres`
(см. [Обновление мажорной версии PostgreSQL](postgres-major-upgrade.md)).

Дальше действуют обычные правила: если шаблон workspace перечисляет `observer`
и `observer-postgres` в `detachedApps`, на стенде они приедут остановленными, и
включаются как любое другое приложение:

```bash
citeck start observer-postgres
citeck start observer
```

Запускать нужно оба — явный старт зависимости за собой не тянет
(см. [что стартует на стенде](app-startup-and-detach.md)). Компаньон и владелец
перечисляются в `detachedApps` **вместе**: иначе на стенде с выключенным
observer'ом поднимется одна его база.

## Что поднимается

Два контейнера.

**`observer`** — сам сервис:

| Порт | Назначение |
|---|---|
| 17014/udp | приём логов |
| 17015 | OTLP HTTP/protobuf |
| 17016 | HTTP API и встроенный UI |
| 17017 | OTLP gRPC |

Проба готовности и liveness — HTTP `/health` на 17016, лимит памяти 512 МБ,
зависит от ZooKeeper (через него же регистрируется в discovery) и от своей БД.
Аутентификация — тот же JWT-секрет, что у веб-приложений namespace.

**`observer-postgres`** — отдельный кластер PostgreSQL под нагрузку
наблюдаемости (много записи, агрегирующие запросы, JSONB-индексы): свои
`shared_buffers`, `work_mem`, настройки WAL, порт 14524 для локальной отладки
(публикуется только в desktop-режиме и только на 127.0.0.1), лимит памяти 512 МБ.

Все её настройки — из объявления в workspace (см.
[Дополнительные базы данных и хранилища](databases.md)), пароль — секрет
namespace `observer-db` (см. [Секреты workspace](workspace-secrets.md)).

Это **полноценная зарегистрированная зависимость** — всё, что есть у основной
базы стенда, есть и у неё:

* **пин версии**: бандл, поднимающий мажор на существующем кластере, придерживается
  и показывается как предложение обновиться, а не применяется молча;
* **счётчик поколений тома**: первое поколение — `obs_postgres2`, следующее после
  миграции — `obs_postgres3`;
* **раскладка данных по мажору образа**: явный `PGDATA` до 17, родительский
  монтаж по умолчанию образа с 18 — то же правило, что у основной базы;
* **миграция и откат** тем же планом «дамп в новый том»:

```bash
citeck deps                              # observer-postgres в общем списке
citeck deps upgrade observer-postgres    # дамп → новый том → проверка → коммит
citeck deps rollback observer-postgres   # вернуться на сохранённый том
```

Две базы независимы: у каждой свой пин, своё поколение тома, свой каталог
дампа. Миграция одной не трогает данные другой.

> Разовое последствие регистрации: том переименован с `obs_postgres` на
> `obs_postgres2` (первое поколение счётчика). Том вне счётчика мигрировать
> нельзя в принципе — копирующее обновление строит следующее поколение рядом с
> текущим, — поэтому старые данные наблюдаемости остаются на диске в старом
> томе и не подхватываются. Для истории метрик и логов это приемлемая цена;
> старый том удаляется вручную: `citeck clean --volumes` его не находит, потому
> что namespace жив. В desktop-режиме — `docker volume rm` (полное имя тома
> видно в `docker volume ls`), в server-режиме — удалить каталог `obs_postgres`
> в каталоге volumes namespace.

## Мониторинг инфраструктуры

Включён из коробки и не требует настройки:

* **RabbitMQ** — через Management API, под сервисной учётной записью `citeck`
  (тег `monitoring`), чтобы ротация пароля администратора не ломала доступ;
* **PostgreSQL** — основной кластер стенда через представления `pg_stat`;
* **ZooKeeper** — командой `mntr`.

## Локальная отладка

Для сценария «остановить в лаунчере — запустить из IDE» объявление observer'а
несёт `cloudConfig:` с localhost-адресами (порты БД, ZK, RabbitMQ, свои порты),
и Launcher кладёт его в CloudConfigServer. То есть контейнер можно остановить и
поднять сервис локально, не переписывая конфигурацию руками.

## Чего Launcher не делает

Он **не прописывает веб-приложениям адрес OTLP-приёмника**. Observer поднимается
и мониторит инфраструктуру, но телеметрию приложений сам по себе не получает —
если она нужна, приложения настраиваются отдельно.

Имена `observer` и `observer-postgres` больше не зарезервированы — их занимает
объявление в workspace.

Он **не ограничивает объём данных observer'а**. Метрики пишутся почасовыми
партициями (`metric_samples_<YYYYMMDDHH>`), и срок их хранения — забота самого
сервиса. Измерено на тестовом стенде community (22 приложения, 2026-09-23):
около **180 МБ в час, 4.7 ГБ за сутки**, и 30-гигабайтный диск стенда
заполнился целиком — сначала отказала запись у самой базы observer'а, затем
liveness-пробы начали падать у веб-приложений. Если на стенде мало места,
observer стоит держать в `detachedApps` или чистить старые партиции
(`TRUNCATE metric_samples_<час>` в базе `observer`).
