# Секреты в конфиге workspace и observer как конфигурация

Дата: 2026-09-23. Решения приняты пользователем в переписке; этот документ
фиксирует итог, а не варианты.

## Цель

1. Реквизиты сервисов, которые объявлены в конфиге workspace, задаются там же —
   разделом `secrets:` и ссылками `${secret:<id>}`, а не зашиваются в лаунчер.
2. `observer` и его база перестают быть встроенными приложениями лаунчера и
   становятся записями `additionalApps` в конфиге workspace.

## Что НЕ делаем

- Генерируемых секретов нет — только константы. Формат раздела оставляет для
  них место (список записей, а не словарь).
- Пароли самого стенда (`postgres/postgres`, datasource webapp'ов = имя базы,
  alfresco) остаются в Go: эти приложения в конфиге не объявлены, и workspace
  без раздела `secrets:` (старый коммит, чужой workspace) не должен оставить
  основную базу без пароля.
- У Qdrant пароля нет: образ его не требует, а ключ пришлось бы передавать в
  `rag` и в чтение коллекций при миграции тома.
- Команды или UI для смены значения в namespace нет: смена пароля у уже
  инициализированной базы — это миграция, а не правка поля.
- Существующая ссылка `secret:<key>` (пароль почты, ключ S3) не меняется.

## Секреты

### Формат в workspace

```yaml
secrets:
  - id: observer-db
    value: observer
```

Значения в workspace — **умолчания**. Настоящее значение namespace получает
один раз и дальше хранит у себя: пароль базы записывается в том при первой
инициализации, и правка конфига workspace после этого базу бы сломала.

### Хранение

- Строки `storage.SecretService` типа `NAMESPACE`, scope `ns:<wsId>/<nsId>`,
  имя — id секрета.
- Шифрование настроено → строка шифруется, как любой секрет.
- Шифрование НЕ настроено (desktop, первый запуск) → строка этого типа пишется
  открытым текстом; для пользовательских токенов по-прежнему действует отказ
  `ErrEncryptionNotSetUp`. Мастер-пароль для работы стенда не нужен.
- Появился мастер-пароль → существующий `SetMasterPassword` шифрует все строки,
  включая эти.
- Тип `NAMESPACE` не показывается на странице секретов и не предлагается как
  учётка реестра/git.
- Удаление namespace — и workspace целиком — удаляет его строки.
- id строки — хэш от (workspace, namespace, id секрета): файловое хранилище
  сервера использует id как имя файла, а id namespace уникален только внутри
  workspace.

### Засев и чтение

Перед генерацией демон:

1. для каждой записи `secrets:` workspace, которой ещё нет у namespace,
   сохраняет её значение (засев);
2. читает все строки namespace и передаёт карту `id → значение` в генератор.

Сохранённое значение не меняется никогда — ни при смене умолчания, ни при
удалении записи из workspace. Предпросмотр перезагрузки (`reloadplan`) ничего
не пишет: он подставляет умолчание вместо недостающего значения.

### Резолв

`${secret:<id>}` работает везде, где уже работают `${JWT_SECRET}`/`${ZK_HOST}`:
env webapp'ов; env, cmd, init-контейнеры и init-действия сырых `additionalApps`;
новый `cloudConfig:` сырых записей; новый ключ `password:` у `type: POSTGRES`.

**Секрет не найден → приложение не генерируется.** После всех генераторов
проход по сгенерированным приложениям ищет оставшиеся `${secret:...}`; такое
приложение исключается с ERROR в логе (имя приложения и id), а зависимые от
него отпадают через обычную чистку зависимостей. Явное `value: ""`
подставляется как есть.

### Запертое хранилище (desktop со своим мастер-паролем)

Прочитать значения нельзя. Существующий гейт `shouldDeferStartForSecrets`
откладывает старт namespace, если workspace объявляет `secrets:`; после
разблокировки namespace **перегенерируется** и стартует (а не стартует со
старыми определениями, в которых приложений с секретами нет).

## Observer как конфигурация

Для этого сырой записи `additionalApps` добавляется два умения:

1. **Образ бандла под именем записи главнее её собственного `image:`**, а
   собственный — лишь умолчание; без `image:` и без образа в бандле записи
   нет. Это то же правило, что у типизированных записей и встроенных
   сервисов: существование сервиса решает бандл (решение пользователя —
   правило едино для всех записей).
2. **`cloudConfig:`** — ключи для CloudConfigServer (сценарий «остановил в
   лаунчере, запустил из IDE»), строки проходят ту же подстановку, что env.

Кроме того, приложение из бандла, которое называет запись `additionalApps`,
не считается webapp'ом — **кроме webapp'а из списка `webapps:` workspace**:
это коробочный сервис, он остаётся webapp'ом, а запись пропускается с ошибкой
в логе, так что через `additionalApps` нельзя переопределить конфигурацию
коробочного приложения (пользователь: защиту сохранить;
`TestGenerateAdditionalApps_DoesNotOverwriteBundleWebapp`). Базовые имена
(`reservedAppNames`) отклоняются уже при загрузке.
Типизированные записи (`POSTGRES`, `QDRANT`) генератор сырых записей
пропускает явно — найдено на живом стенде: иначе они отсекались как коллизия
с кластером, который только что создал их собственный генератор, и давали
ERROR в каждом логе.

Из лаунчера удаляется: `generateObserver`, `WillGenerateObserver`, встроенные
умолчания `observer-postgres` (`builtinDatabases`), встроенная регистрация
`observer-postgres` в `internal/deps` и в таблицах миграций, имена `observer` и
`observer-postgres` в списке зарезервированных. Объявленный кластер получает
мигратор и откат по своему виду (дефект, исправленный в том же релизе: до
него объявленный кластер показывался как обновляемый, а `citeck deps upgrade`
падал внутренней ошибкой).

Данные сохраняются: id `observer-postgres` и `volumeBase: obs_postgres`
прежние, поэтому пин, поколение тома и сам том остаются теми же.

Последствия:

- на 2.15+ observer есть только там, где его объявляет workspace — записи
  добавляются в оба наших workspace;
- проверка «observer без базы» становится общей строкой чистки зависимостей
  (`App excluded… missingDep=observer-postgres`);
- лаунчеры ≤2.14 на таком конфиге отбрасывают `additionalApps` целиком с
  предупреждением и оставляют свой встроенный observer; других записей в наших
  workspace нет.

## Проверка

- Тесты на засев, неизменность сохранённого значения, открытый текст без
  мастер-пароля и шифрование после его появления, исключение приложения без
  секрета, образ из бандла, `cloudConfig:`.
- Генерация на настоящих файлах обоих workspace: определение observer и его
  базы совпадает с прежним (env, порты, тома, пробы, ресурсы).
- Живой стенд 45.15.158.227: после обновления observer работает на прежнем томе
  с прежними данными.
- `make check`.

## Итог проверки (2026-09-23)

- Генерация на настоящих файлах (публичный workspace + community/enterprise
  RC3, внутренний + enterprise RC3, server и desktop): вход хэша observer'а и
  его базы совпал со встроенным кодом 2.14 во всех четырёх сочетаниях,
  cloud config идентичен. Отличие одно и вне хэша: пробы, прочитанные из YAML,

  секрет засеян и хранится зашифрованным.
