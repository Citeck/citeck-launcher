# Многошаговое обновление зависимостей: лестница образов в секции `dependencies:`

Дата: 2026-09-15. Статус: дизайн согласован пользователем, ожидает реализации.

## 1. Проблема

Обновление зависимости делает **ровно один шаг**: `citeck deps upgrade <dep>` ведёт из пина
в кандидата, которого предлагает бандл. Промежуточные версии взять неоткуда — бандл называет
одну.

Это ломается на вендорах, которые не обещают читать данные через несколько минорных версий.
Замерено прогоном (2026-09-15):

| зависимость | пара | вердикт |
|---|---|---|
| qdrant | 1.14.1 → 1.19.1 | **не поддержана**, `via 1.15` |
| qdrant | 1.14.1 → 1.15.5 | поддержана |
| rabbitmq | 4.1.2 → 4.3.5 | **не поддержана**, `via 4.2` |
| postgres | 17.11 → 18.6 | поддержана |

Совет, который лончер даёт вместо пути, **неисполним**. `deps.msg.pair.vendorPath` (все 8
локалей) говорит: «Point the namespace at a {via} image (`citeck edit {dep}`, or a bundle that
offers it), migrate, then come back». Прогон `putAppConfig(mux, "rabbitmq", image: 4.2.9)` при
пине 4.1.2 отвечает **400 `DEPENDENCY_VERSION_LOCKED`** с текстом «run `citeck deps upgrade`».
Сообщение шлёт в `citeck edit`, а гейт редактирования шлёт обратно в `deps upgrade`, который
и отказал. Это рецидив дефекта, который уже ловили для rabbitmq и убирали из преflight'а.

Практический вес: для qdrant сегодня теоретический (RAG не выпущен, стендов с данными нет).
Для **rabbitmq реальный**: стенды на 4.1.2 существуют, RC3 даёт 4.2.9 — один хоп, проходит;
следующий бандл с 4.3 загонит их в тупик.

## 2. Решение в одной фразе

Значение образа может быть **списком**. В секции `dependencies:` список — это лестница:
цель — последний элемент, а миграция поднимается по каждой ступени отдельно. Везде остальное
из списка берётся первый элемент.

```yaml
dependencies:
  qdrant:
    image:
      - qdrant/qdrant:v1.15.5
      - qdrant/qdrant:v1.16.1
      - qdrant/qdrant:v1.19.1
```

## 3. Формат

### 3.1 Один декодер значения образа

В `internal/bundle` появляется общая функция, принимающая `*yaml.Node` и отдающая
упорядоченный `[]string`. Она понимает три формы:

* скаляр — `"postgres:18.6"`;
* карта — `{repository: postgres, tag: "18.6"}`;
* **последовательность** элементов любой из первых двух форм.

Форма, которую прочитать нельзя, даёт пустой список — и стоит ровно себе, как сегодня
(`DependencyEntry.UnmarshalYAML` намеренно тотален: ошибка YAML роняет весь workspace-конфиг,
поэтому одна нечитаемая запись не имеет права стоить остальных).

Декодер один, потому что правило разбора тега уже однажды разъезжалось по двум местам
(см. `trimVersionTagV` в решениях c05), и второе написание того же правила — это способ
получить спеллинг, который работает в бандле и не работает в воркспейсе.

### 3.2 Два правила потребления, прибитые гвоздями

| где | правило |
|---|---|
| `dependencies:` бандла и workspace-конфига | весь список; цель — **последний** элемент |
| всё остальное | **`[0]`** |

«Всё остальное» — это `applications:` бандла, `ecosAppsImages`, типизированные блоки
воркспейса (`postgres`, `keycloak`, `zookeeper`, `onlyoffice`, `pgadmin`, `sttSidecar`,
`qdrant`), `additionalApps`, оверрайды образа в `namespace.yml`.

**Почему первый, а не последний.** Читатель вне `dependencies:` не умеет двигать данные:
у него нет ни пина, ни удержания, ни отчёта, ни миграции. Значит из предложенного списка
он обязан брать **самую консервативную ступень** — ту, которая скорее всего совпадает с тем,
что уже лежит в томе. Это тот же принцип, по которому `LegacyImage()` qdrant оставлен на
v1.14.1, хотя поставляется 1.19.1: ошибиться в сторону удержания дёшево, в обратную — нет.

Типизированные блоки сегодня объявлены как `Image string`. Они меняют тип на `ImageRef`
(именованный строковый тип с собственным `UnmarshalYAML`, берущим первый элемент); места
использования конвертируются `string(...)` — 12 не-тестовых точек.

### 3.3 Что видят выпущенные лончеры — замерено

Сегодняшний парсер понимает в `image:` только скаляр и `{repository, tag}`. На
последовательность он отвечает так (прогон, 2026-09-15):

```
WARN Bundle dependency entry names no image; ignoring it app=qdrant
deps=map[string]bundle.AppDef{"rabbitmq":{Image:"rabbitmq:4.2.9-management"}}
```

То есть **массив делает запись `dependencies:` невидимой для 2.12.0–2.12.2**, и зависимость
откатывается к встроенному дефолту лончера.

* Для qdrant это безопасно: у выпущенных лончеров его в бандле и так не было.
* Для **rabbitmq — нет**: 2.12.0–2.12.2 вернутся с 4.2.9 на встроенный `4.1.2-management`,
  то есть понижение через минор на данных с включённым Khepri. **Пока эти версии в поле,
  лестницу для rabbitmq в бандлы писать нельзя.** Это ограничение, а не дефект: секция
  `dependencies:` и существует затем, чтобы незнакомое содержимое игнорировалось.

## 4. Гейт версий

`resolveDependencyImage` получает не один кандидат, а лестницу.

* **Кандидат** = последний элемент. Поведение на свежем стенде и на непрерывающей паре не
  меняется.
* `DependencyUpgrade` получает поле **`Path []string`** — маршрут: ступени лестницы строго
  новее пина, по порядку, заканчивая целью. Если пин не совпадает ни с одной ступенью,
  маршрут начинается **от пина**: лестница — это перила, а не расписание, и оператор
  встаёт на неё со своей ступени.
* `vendorVerdict` спрашивает вендора про **каждую смежную пару** маршрута (`пин→p₁`,
  `p₁→p₂`, …), а не про пару (пин, цель). `VendorBlocked` — если запрещён хотя бы один
  переход; `VendorVia` называет **разрыв**, то есть версию, которой в лестнице не хватает.

Следствие: qdrant 1.14.1 при лестнице до 1.19.1 перестаёт быть `vendorBlocked`, и совет
`citeck edit`, который гейт редактирования всё равно запрещает, для этого случая исчезает
сам. Дефект из §1 закрывается не переписыванием сообщения, а тем, что случай, ради которого
оно писалось, становится проходимым.

Ступень с нечитаемым тегом не молча пропускается: маршрут через неё построить нельзя,
потому что «строго новее пина» для неё не определено. Такая лестница целиком считается
нечитаемой — как сегодня нечитаемая запись `dependencies:`, — и зависимость остаётся на
пине с сообщением преflight'а про тег. Тихий пропуск ступени означал бы переход, который
вендор не разрешал.

Список зависимостей (`GET /api/v1/dependencies`) показывает целью **последний** элемент:
это и есть то, куда стенд едет. Маршрут виден на экране миграции — по одному шагу на
ступень.

Случаи, которые обязаны остаться как есть: лестница без разрывов, но ведущая назад
(`BundleOlder` проверяется первым и маршрут не строит); нечитаемый тег на любой ступени
(вердикт пуст, пин удержан, сообщение даёт преflight).

## 5. Интерфейс мигратора

`from, to string` заменяется на `migrate.Path`:

```go
// Path — маршрут одной миграции. Path[0] — то, на чём данные работают сейчас,
// каждый следующий элемент — ступень, последний — цель.
type Path []string
func (p Path) From() string
func (p Path) To() string
func (p Path) Hops() [][2]string   // смежные пары
```

* `Preflight(ctx, env, path Path) PreflightResult`
* `Plan(ctx, env, path Path, opts PlanOptions) (*Plan, deps.MigrationJournal, error)`
* `SupportsPair(from, to deps.Version)` **остаётся попарным** — это вопрос про пару, а не про
  маршрут; общий преflight прогоняет его по всем смежным парам.

## 6. Движок: одна копия, N подъёмов на ней

Многошаговость живёт **внутри одной копии тома**, а не в цепочке copy-upgrade'ов.

Отвергнутая альтернатива — N последовательных copy-upgrade'ов — даёт N томов, N поколений
и откат только на одну ступень назад. Принятая форма: копия исходного тома снимается один
раз, и все подъёмы происходят на ней.

```
stop-namespace
pull-image            ← каждая ступень маршрута, не только цель
create-volume
copy-volume
start-old(v₀) → pre-upgrade → stop-old
для i = 1..N:
    start-new(vᵢ) → post-upgrade → [pre-upgrade, если i < N] → stop-new
verify                ← инвентарь v₀ против vₙ
```

Что это даёт структурно:

* исходный том не тронут ни на одной ступени — свойство «оригинал только читается» остаётся
  тотальным, как и сегодня (`tempDef` по-прежнему единственное место, где контейнер узнаёт
  свой том, и всегда отвечает копией);
* поколение тома растёт **на 1** независимо от длины лестницы;
* откат не меняется вовсе: `SourceVolume` в журнале — исходный том, `RollbackCopyUpgrade`
  удаляет копию;
* при N = 1 план совпадает с сегодняшним шаг в шаг.

**Почему `pre-upgrade` повторяется на каждой ступени, кроме последней.** Это не симметрия:
у rabbitmq `PreUpgrade` включает feature flags, которых требует **следующий** узел. На
лестнице 4.1 → 4.2 → 4.3 их надо включить дважды — перед 4.2 и перед 4.3, каждый раз на
тогда-текущем образе. У qdrant `PreUpgrade` = nil, и конструкция схлопывается.

Инвентарь «до» снимается там же, где сегодня — в `pre-upgrade` на v₀; «после» — на vₙ.
Промежуточные ступени не сверяются: инвентарь сравнивает данные, а не то, что вправе
переписать новая версия, и промежуточная сверка добавила бы ровно те ложные срабатывания,
ради исключения которых из него убраны `status` и `config`.

**Идентификаторы шагов повторяются.** Они же локальные ключи, поэтому оператор увидел бы
«Starting the new version» N раз без указания ступени. `startTemp` открывает шаг
прогресс-сообщением с образом — **один новый ключ × 8 локалей**.

Журнал получает `Path []string` — запись о том, каким маршрутом шли. `From`/`To` остаются
первым и последним элементом, чтобы всё, что читает журнал (в том числе лончер другой
версии, нашедший его при загрузке), продолжало работать.

## 7. PostgreSQL

Его вендорное правило — `forwardOnlySupport`: разрешён любой шаг вперёд. Его план — не
copy-upgrade, а логический дамп (`pg_dumpall` со старого узла, `psql` в новый), и он уже
сегодня обещает 15 → 18 одним движением.

Поэтому `PostgresMigrator` **использует `Path.From()` и `Path.To()` и игнорирует
промежуточные ступени**, записав в лог, что лестница ему не понадобилась. Не отказ: лестница
для postgres — безобидная лишняя настройка, а отказ на ней был бы враждебностью к
опечатке. Не обобщение плана на N дампов: это N-кратная работа без выигрыша, и каждый
лишний дамп-восстановление — лишний способ потерять данные.

Никакого нового переключателя в интерфейсе `Migrator` для этого не нужно: это просто то,
что конкретный мигратор делает с выданным ему маршрутом.

## 8. Лончер 1.x

1.x **учится не ломаться об массив**: там, где он читает образ, список даёт первый элемент.
Секцию `dependencies:` он по-прежнему не читает и читать не будет — у него нет dependency
gate, и любой внешний источник версии для него это канал молчаливого переноса данных
(решение пользователя от 2026-09-15, зафиксировано в `AGENTS.md`).

Речь только про `applications:` и прочие места, где 1.x читает образ из тех же файлов:
сегодня массив там даст пустой образ. Первый элемент — ровно то консервативное чтение,
которое лончеру без гейта и положено.

## 9. Проверка

Юнит-тесты:

* декодер: скаляр, карта, массив скаляров, массив карт, смешанный массив, пустой массив,
  мусор; и то, что нечитаемая запись стоит только себя;
* оба правила потребления: `dependencies:` берёт весь список, остальные — `[0]`;
* вычисление маршрута: пин совпал со ступенью; пин ниже всей лестницы; пин между ступенями;
  пин уже на цели; лестница из одного элемента;
* вендорный вердикт по цепочке: сплошная лестница; лестница с разрывом (и что `Via` называет
  именно разрыв); лестница назад;
* форма плана при N = 1 (обязана совпасть с сегодняшней) и при N = 3;
* postgres игнорирует промежуточные ступени.

Мутационная проверка каждого нового правила — по правилу проекта: правило, мутацию которого
не ловит ни один тест, либо не проверено, либо не нужно.

**Интеграционный тест на реальном Docker** (тег `integration`): qdrant 1.14.1 → 1.15.x →
1.16.x на одной копии. Проверяется: коллекции, точки и алиас целы; исходный том побайтово
не изменён; поколение выросло на 1; создан ровно один новый том; оба temp-контейнера убраны;
журнал закрыт.

Голдены `internal/namespace` при N = 1 не должны сдвинуться.

## 10. Что этот дизайн НЕ делает

* Не даёт лончеру искать промежуточные версии самому (в реестре образов). Лестницу пишет
  автор бандла — лончер не изобретает версий, которых ему не назвали.
* Не меняет правило «перелом формата удерживается»: лестница даёт путь, а не разрешение
  применить перелом без копии.
* Не чинит `deps.msg.pair.vendorPath` для случаев, где лестницы нет. Разрыв в лестнице и
  отсутствие лестницы по-прежнему дают вендорный отказ; сообщение остаётся тем же, и оно
  по-прежнему советует `citeck edit`, который гейт запретит. Это **остаётся открытым** —
  см. §1; закрывать его отдельно, когда станет ясно, остались ли случаи без лестницы.
