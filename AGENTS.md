Guidance for AI coding agents working in this repository. Claude Code reads it through

## Project Overview

Citeck Launcher manages Citeck namespaces and Docker containers. It is a single Go binary (~24 MB) that serves as both CLI and daemon. The embedded React Web UI is **not offered in server mode** — the CLI/TUI is the supported server interface. The `daemon.yml` `server.webui.enabled` flag is still parsed but is **inert in server mode**: the runtime gate ignores it and the TCP listener binds in server mode only via the explicit `CITECK_SERVER_WEBUI=1` dev/E2E hatch (never through config). Desktop mode renders the same Web UI through a Wails webview that talks to the daemon over the Unix socket (its TCP listener is off too, except the `CITECK_DESKTOP_TCP=1` hatch).

The repo also keeps the legacy Kotlin/JVM launcher under git tags `v1.0.0`–`v1.3.9` for reference and rollback (`git show v1.3.8:path/to/file`). The desktop migrator opens its H2 `storage.db` read-only on first start.

### Desktop installers

Packaging configs live in `packaging/` (nfpm → deb/rpm, WiX → msi, macOS scripts → dmg).

**macOS signing is load-bearing, and its step ORDER is a contract.** An app that is not
Developer ID signed AND notarized is rejected by Gatekeeper after any browser download with
the misleading Finder dialog *"citeck-launcher is damaged and can't be opened"* — the word
"damaged" means "not notarized", not "corrupt file". `packaging/macos/release.sh` therefore
runs `make-app.sh` → `sign-app.sh` → `make-dmg.sh` → `notarize-dmg.sh`: signing must come
after `make-app.sh` (which rewrites `Info.plist` via PlistBuddy — the last mutation of the
bundle) and before the dmg is built from it. `make-dmg.sh` uses `ditto`, not `cp -R`, because
`cp` drops the extended attributes that carry the seal. Hardened-runtime entitlements
(`entitlements.plist`) grant JIT + unsigned executable memory — notarization passes without
them but the embedded WebKit view crashes on first render. Signing is driven by
`MACOS_SIGN_IDENTITY` + the `MACOS_NOTARY_*` secrets; with none configured the scripts fall
back to an **ad-hoc** signature. Set the repo variable `MACOS_REQUIRE_SIGNED=1` once a
certificate exists to make an unsigned macOS build fail the release instead of shipping.

**Ad-hoc is not a no-op — it is 1.x parity.** Verified by inspecting the shipped artifacts:
the 1.x jpackage bundle had `Contents/_CodeSignature` (`CS_ADHOC`, empty CMS blob — no
certificate), while the 2.9.0 bundle had no `_CodeSignature` at all. Both were equally
un-notarized, so the regression was purely the missing **bundle-level** seal, and it changes
which dialog the user gets: an ad-hoc signed bundle yields *"the developer cannot be verified"*
(bypassable with right-click → Open), an unsigned one yields *"is damaged and can't be opened"*
(hard block, no in-UI recovery). Go's linker ad-hoc signs the arm64 Mach-O automatically, but
Gatekeeper assesses the BUNDLE, so that never helped. Note the distinction `sign-app.sh` draws:
a **missing certificate** is a routine state (warn, ad-hoc, continue), but **codesign itself
failing** is fatal — on a macOS runner that means a broken toolchain or a malformed bundle, and
continuing would publish the very "is damaged" artifact the script exists to prevent. Do not
"soften" that into a warning: a green release that silently contains the bug is worse than a red
one, and nobody reads `::warning::` on a passing build.

**Windows: the wrapper is GUI-subsystem and the daemon child gets `CREATE_NO_WINDOW`.**
These two are one decision, and dropping either brings back the same symptom — a second,
black console window next to the launcher (reported on 2.11.0). Windows takes the decision
from a single byte in the PE optional header: Go emits `IMAGE_SUBSYSTEM_WINDOWS_CUI` (3)
by default and only `-H windowsgui` in `packaging/windows/release.sh` flips it to GUI (2).
But a GUI parent has no console, and `CreateProcess` answers that by allocating a **brand
new console, window and all**, for any console-subsystem child — which the daemon is. So
`sysProcAttrSetsid` (`internal/desktop/supervisor_proc_windows.go`) must pass
`CREATE_NO_WINDOW`; redirecting the child's stdout/stderr does not help, since the window
is created before anything is written to it. The same applies to anything the *daemon*
execs (today only `explorer.exe`, which is GUI-subsystem, so nothing else needs it yet).
`TestWindowsDesktopReleaseLinksAGUISubsystemBinary` does not grep for the flag — it
extracts the real link flags out of the release script, links a stub with them and reads
the subsystem byte back, so a typo or a quoting slip fails too. Since the wrapper then has
no stderr at all, it writes `config.LauncherLogPath()` (`<LogDir>/launcher.log`, teed to
stderr only when `stderrUsable()`); Wails' own logger is pointed at the same handler via
`application.Options.Logger`. Without that file a failed startup — a held instance lock, a
daemon binary that will not spawn — would be an app that does nothing, silently, with no
trace anywhere. Windows-tagged sources compile nowhere else in the test job, so `make
check` / test.yml run `GOOS=windows go vet ./internal/...`.

A `v*.*.*` tag builds all installers via `.github/workflows/release-go.yml` and attaches
them to the GitHub Release alongside the server tarballs. Release artifacts are named
`citeck-desktop_<version>_<os>_<arch>.<ext>` (the package/app *identity* stays `citeck-launcher`
for the upgrade contract). Clean upgrade over the legacy
1.* installer: same deb/rpm package name `citeck-launcher`, shared Windows `UpgradeCode`,
and a `citeck-launcher.app` bundle name matching 1.*'s path. Run the local clean-upgrade
e2e with `./scripts/test/test-deb-upgrade.sh` (needs Docker + GTK3 dev libs).

**Components (`web/src/components/`)** — notable:

- `AppTable.tsx`, `BottomPanel.tsx`, `RightDrawer.tsx`, `LogViewer.tsx`, `DaemonLogsViewer.tsx`, `AppDrawerContent.tsx`, `AppConfigEditor.tsx`, `RestartEvents.tsx` — dashboard surfaces
- `LogViewport.tsx` — virtualized log list (tanstack-virtual). Follow model: **breaking** follow happens on user intent (wheel-up) so a bursty stream can't swallow it via the programmatic-scroll gate; the ≤50px bottom heuristic only re-arms it. Rows are keyed by `LogEntry.id` (`getItemKey`). **Wrap OFF = fixed-row fast path**: per-row `measureElement` is NOT attached (rows are uniform; height probed once from the first rendered row) — attaching it caused a measure/adjust storm that stuttered upward scrolling at the edge of the measured window; wrap ON re-enables measurement + `shouldAdjustScrollPositionOnItemSizeChange` (an *instance* property, not a constructor option, in the pinned virtual-core), and toggling wrap resets the measurement cache (`virtualizer.measure()`). Content mousedown pauses stream flushes (via `LogViewer`'s `selecting` state) so text selection survives, and puts the `log-select-drag` guard class on `<body>` (`index.css`) so a drag past the viewport edge cannot pull the toolbar/window chrome into the selection; Ctrl+A select-all auto-clears on Escape/`selectionchange` (stale flag used to re-select the container on every scroll — the "scroll got slow" bug). **Copy is buffer-backed, not DOM-backed**: the native selection only spans mounted rows (rows past overscan unmount and silently leave it), so the copy handler serves Ctrl+A from the full filtered list and a drag selection from tracked logical bounds — entry id + char offset per endpoint, recorded on `selectionchange` during the drag (`web/src/lib/logSelection.ts`); copies from editable elements are never hijacked. Tracked bounds are invalidated by USER ACTIONS (click outside the viewer, Escape, select-all, fresh drag), never by DOM state — engines collapse/detach the selection when rows unmount, and a detached anchor is not a "foreign selection". WebKitGTK (desktop webview) extras: rows positioned via `top` not `transform` (its caret hit-test is transform-unaware in places), blank lines render an NBSP (an empty div has no caret position), and a focus clamp re-extends the selection to the row under the pointer when the engine's hit-test lands >1 row away (the "selection jumps to the top of the list" bug). The clamp runs on `selectionchange` — NOT mousemove — because past the container edge the engine extends via its own drag-autoscroll timer with no mouse events; mousemove only records the pointer Y. Drag starts on the LEFT button only (a right-click's mouseup never arrives — the "drag" stayed armed, the selection followed the bare cursor and per-selectionchange clamp work made wheel scrolling crawl); missed-mouseup nets are `blur`/`visibilitychange`, NOT `ev.buttons===0` (scroll-synthesized mousemoves can carry stale buttons)

## Localization (i18n)

8 locales: **en** (source of truth), **ru, zh, es, de, fr, pt, ja**. There are **three independent localization assets** — they do NOT share strings:

| Asset | Path | Consumed by | Format |
|---|---|---|---|
| CLI / TUI strings | `internal/i18n/locales/<loc>.json` | Go binary (`internal/i18n/i18n.go`, `//go:embed locales/*.json`) | flat JSON, **dotted keys** (`"setup.s3.access_key"`) |
| Web UI strings | `web/src/locales/<loc>.ts` | React UI (`web/src/lib/i18n.ts`, static imports) | flat TS object (`'key': 'value'`), single-quoted |
| Changelog notes | `changelog/<version>/<loc>.md` | in-app update dialog (fetched at runtime via `changelog/index.json`) | markdown |

**The CLI JSON asset also carries every sentence the DAEMON builds.** Preflight problems and warnings, the rollback consequences, the dependency edit-gate refusals, per-step migration progress, the busy refusals — none of them is a UI label, and all of them used to be English in all eight languages because they were `fmt.Sprintf`ed deep inside pure packages that have no locale, no request, and no business acquiring one. They are now `msg.Message` values (a key plus `{param}` args, prefix `deps.msg.<area>.<name>`, 77 of them) and the **locale is applied at the HTTP boundary**, where the reader is finally known: `internal/daemon/deps_render.go` renders with the per-request `d.translatorFor(r)`. Three consequences worth knowing. (1) **The wire is unchanged** — plain rendered strings in the same JSON fields — so neither the web UI nor the CLI grew a rendering path, and the sentence lives in ONE asset instead of being maintained twice. (2) **Locale transport is `X-Citeck-Locale`, falling back to `?locale=`, then `daemon.yml`.** Not `Accept-Language`: the browser sends that one on its own with the OS language, which is not the language the operator picked in the launcher. The query parameter exists because `EventSource` cannot set a header and the SSE stream carries the migration's per-step messages; the ring buffer therefore stores the `Message`, never a rendered sentence, and `writeSSEEvent` renders **per subscriber** — one broadcast, a desktop UI reading it in Russian and a CLI in German. The `daemon.yml` fallback is what makes **server mode** right with no client change at all: the CLI reads its own strings from that same setting, so an unmarked request gets the language the CLI would have printed. (3) An unusable locale (`ru-RU`, `klingon`, empty) degrades to English rather than failing the request — the sentence is the point, the language is a preference. Deliberately still English: `slog` lines (they are for us), `Inventory.Diff`'s per-dependency findings (no key set exists for them), and `MigrationResult.Error`, which is persisted — the structured verdict rides beside it in `ErrorMsg` (`omitzero`, because `omitempty` is a no-op on a struct and would put `"errorMsg":{"Key":""}` into every record) and readers prefer it, falling back to the English string an older launcher wrote.

**The DEPS_WAITING hold is the one operator sentence the daemon deliberately does NOT build.** It is the counter-example worth knowing before reaching for `msg.Message` again: `AppDto.WaitingFor` carries `{app, status}` pairs and `web/src/lib/waitingForDeps.ts` words them (`app.status.waitingForDeps` + the `status.*` labels every `StatusBadge` already renders). Rendering it in the daemon would have cost a second copy of all thirteen status labels in the CLI JSON — the web asset has them, and a sentence whose every component the reader already owns is one the reader should assemble. The rule it does share with `msg.Message` is the one that matters: **the runtime never renders and never calls the package-level `i18n.T`** (`unmetDeps` runs on the runtimeLoop goroutine, which has no reader, and that `T` holds ONE global locale from `daemon.yml` and is not goroutine-safe), and the list is DERIVED at the DTO boundary (`appWaitingForDeps`, `runtime_dto.go`) rather than stamped on the app — what an app waits on changes while its own status does not, so a stored copy would need refreshing on every tick and clearing on every path out. Use `msg.Message` when the daemon owns the wording (the migration and dependency-gate sentences: no client has those strings); use a structured field when the client already has every word.

**The CLI JSON and Web TS sets are INDEPENDENT — two assets, both of which must be edited.** The web UI does **not** read `internal/i18n`; it has its own ~620-key TS files (the CLI JSONs are ~453 keys). A string shown in the web UI must be added to `web/src/locales/`, not the JSON, and a string the CLI prints must be added to the JSON, not the TS. The two sets were content-disjoint until the dependency-migration feature; today **38 `deps.*` key NAMES appear in both** (the step titles of all three plans, the preflight lines, the status labels, the table headers), because the CLI and the dialog describe the same migration and naming the same thing twice differently is worse. That overlap is a **convention, nothing more** — no tooling reads one from the other, **12 of the 38 shared values deliberately differ and 4 of those differ in placeholder arity** (two of the CLI's `deps.status.*` end in the command to type, which a dialog with a button does not need, and its `deps.rollback.title` takes `{from}`/`{to}` where the dialog takes `{id}`), so a change to one asset does NOT propagate. Change both by hand, or check the sibling deliberately.

Rules when changing strings:
- Add/rename/remove a key in **all 8 files** of the relevant asset. Key parity is enforced for both assets: the web UI via `web/src/locales/locales.test.ts` (`missing keys` / `extra keys` tests), the CLI JSON via `internal/cli/i18n_test.go` (`TestLocaleCompleteness`). Note: *value*-completeness (English left untranslated in non-en files) is only tested for the web TS files — for the CLI JSONs, keep values translated by hand.
- **Translate the VALUE, don't leave English.** `locales.test.ts` also has a value-completeness test that fails on any *multi-word* value left identical to `en` (the "key exists but never translated" gap) — single-word loanwords/cognates (Name, Status, Port, Bundle, Namespace…) are allowed; brand/format-string exceptions live in its `IDENTICAL_OK` allowlist.

## Key Technical Decisions

- **SSE** (not WebSocket) for real-time events
- **Daemon transports**: Unix socket (chmod 0600) for the local CLI; the Web UI over TCP is **not offered in server mode** — the runtime gate (`daemon.webUITCPAllowed`, `bootstrap.go` `startWebUI`) ignores `server.webui.enabled` and binds the listener in server mode only via the `CITECK_SERVER_WEBUI=1` dev/E2E hatch. When the hatch binds it, a localhost bind gets the full API gated by the `X-Citeck-CSRF` header (plus bearer-token auth when `api_auth` is enabled) and non-localhost binds require mTLS (`setupMTLS`). `--no-ui` also force-disables.
- **Security model — why the server Web UI is code-disabled**: the localhost Web UI TCP port serves the **full privileged API** (incl. `citeck exec` into containers ⇒ effectively root on the host). The `X-Citeck-CSRF` header defeats browser-based CSRF but is **not authentication** — any local OS user/process that can reach the port would have full control. So rather than ship it as an opt-in config toggle, the server-mode Web UI is **hard-disabled in code**: `server.webui.enabled: true` in `daemon.yml` is inert, and the only way to bind it in server mode is the explicit `CITECK_SERVER_WEBUI=1` dev/E2E hatch (used by the Playwright e2e in `web/`). `citeck ui` refuses in server mode unless that hatch is set. The infrastructure behind it stays in place but unreachable via config: **API token auth** (`daemon.yml` `api_auth.enabled: true`) gates every `/api/*` TCP request with `Authorization: Bearer <token>` or the session cookie from the `GET /auth/session?token=…` handshake (constant-time compare, HttpOnly SameSite=Strict cookie, 24h TTL), else 401 `AUTH_REQUIRED`; token = `api_auth.token` or auto-generated 32-byte `conf/api-token` (0600); the Unix socket, desktop wrapper, and mTLS-authenticated requests bypass, static UI assets stay public. See `internal/daemon/apiauth.go`.
- **A configured `dependsOn` target that does not exist is REPORTED, not pruned.** `pruneAppsWithMissingDeps` answers a missing dependency by deleting the app that named it (and, transitively, its dependents), which is right for generator-emitted wiring — naming an app this mode does not produce, e.g. keycloak under BASIC auth, is normal — and badly wrong for an operator's typo: `webapps.emodel.dependsOn: [sidcar]` made emodel vanish from the namespace with nothing but an `slog.Error`. `ctx.ConfiguredDependsOn` records what THIS operator wrote — the **namespace.yml** layer only — and `checkConfiguredDependsOnTargets` validates it against the generated set **before** the prune, appending to `ctx.DependencyErrors`, the same channel the self-dependency case already used. The **workspace** layer keeps the prune on purpose: that file lives in a git repo the local operator usually cannot edit and is shared by every namespace on the workspace, so a hard generation failure there would take all of them down over a line none of them can change, and over a target that is legitimately absent on some of them (an app turned off in namespace.yml, keycloak under BASIC auth).
- **Configuration layering**: `workspace defaults < namespace.yml < bundle < citeck edit`. The bundle pins release image versions, so it outranks both config files; the only sanctioned way to deviate on one stand is the explicit `citeck edit <app>` patch (marked `*` in `citeck status`). See `docs/config-layers.md`.
- **Smart regenerate** via deployment hash comparison (like `docker-compose up`) — unchanged containers keep running
- **The proxy is recreated whenever the gateway is** (`proxyMustFollowGatewayRecreate`, `internal/namespace/runtime_orchestration.go`), even though its own hash has not moved. nginx resolves its upstreams once at startup, so a proxy left running against a recreated gateway keeps sending traffic to a container IP that no longer exists: every gateway-backed page 502s **while the launcher reports both apps RUNNING, both probes passing and the namespace green** — invisible from inside, indistinguishable from a mass product regression outside. The rule lived only in `doStart` until 2026-08-13, so the routine case — edit an app's config and reload, i.e. `citeck reload` / the gear-icon editor / `citeck edit <app>`, all of which take `doRegenerate` — was precisely the one that opened the silent window (measured on a live stack: gateway recreated twice through the edit path at 03:01:18Z and 03:04:43Z while the proxy stayed on its 00:02:55Z container for the next 33 minutes). `doRegenerate` computes `gatewayRecreated` **under `r.mu` before the per-app loop** — it reads `r.apps`, and the desired set has no guaranteed order, so deciding it lazily when the loop happens to reach the proxy would depend on map iteration order. Keep the rule **narrow**: recreating the proxy on every reload would discard its writable layer (the generated basic-auth htpasswd among other things) for nothing. Pinned from both sides by `TestDoRegenerate_ProxyFollowsGatewayRecreate` and `TestDoRegenerate_ProxyIsLeftAloneWhenTheGatewayIsUnchanged`.
- **The proxy's OIDC handler decides an identity, so it must match the path nginx ROUTED — never `ngx.var.request_uri`.** `internal/appfiles/proxy/lua_oidc_full_access.lua` is the `access_by_lua_file` script the launcher copies over the image's own at container start (`generateProxy`'s init actions, KEYCLOAK auth only). It writes `X-ECOS-User` / `X-Alfresco-Remote-User`, which `ecos-gateway` trusts unconditionally, and its service exceptions (`/alfresco/monitoring`, the static-resource rule) grant that identity with no authentication at all — so a rule that matches more than the routed path IS an auth bypass, not a cosmetic looseness. It matched `$request_uri`, which is the **raw** URI: query string included, percent-escapes intact. Reported (2026-09-16) as `?probe=/healthcheck/` handing `service_healthcheck` to an unauthenticated client on any `/gateway/…` endpoint; reproduced here in three shapes — the query string, the marker as a MIDDLE path segment (`/gateway/emodel/alfresco/monitoring/heartbeat`), and traversal (`/alfresco/monitoring/x/..%2f..%2fgateway/emodel/api/records/query`), where nginx resolves the encoded `..` and routes to an arbitrary gateway endpoint while the handler still sees the marker. Once `userName` is set the OIDC branch is skipped entirely. The fix is `getRequestPath()` — query string dropped, `%XX` decoded as nginx decodes a path, `.`/`..`/duplicate slashes resolved — with every remaining rule anchored at `^` against it. **`ngx.var.uri` is not the answer**: the rewrite phase runs before the access phase, so by then `$uri` is already rewritten (`/gateway/emodel/api/records/query` arrives as `/emodel/api/records/query`, `/v2/dashboard` as `/index.html`). The `/healthcheck/`, `/rabbitmq`, `/node-exporter`, `/postgres-exporter` and `/cadvisor/` rules were **deleted rather than anchored**: those locations carry their own authentication and the proxy config has had no server-level `access_by_lua_file` since config v4, so the rules granted nothing and only widened the set of smuggleable markers — `/healthcheck/`'s `service_healthcheck` worst of all, since the gateway auto-creates that person with `GROUP_EVERYONE` + `ROLE_USER`. Two consequences. The lua is a bind mount and feeds `computeVolumesContentHash`, so the release carrying this **recreates the proxy container once**; and a static resource with a cache-busting query (`/main.js?v=1.2.3`) is now recognised as static, where before the `.3` of the query was read as its extension and it fell through to OIDC. Guarded from both sides: `internal/appfiles/proxy_lua_test.go` (Docker-free source guards — one read of `ngx.var.request_uri`, every `reqPath` marker anchored, no infrastructure identity — in `make check`) and `tests/proxy-lua/` (the real access decisions under LuaJIT with a stubbed `ngx`, vendored from citeck-devops, which owns the upstream copies; run it when touching this file and keep the two in sync).
- **Namespace runtime is a single-threaded state machine with signal-queue wake-ups.** One `runtimeLoop` goroutine owns every mutation to `r.apps`, per-app status, namespace status, and persistence. External commands enqueue via `cmdQueue` (typed, coalescing, 500ms back-pressure); workers (pull / start / stop / probe / stats / reconcile / liveness) run off-loop on the dispatcher, post typed Results back on `resultCh`; `applyWorkerResult` applies state-machine transitions under lock. Per-iteration `stepAllApps` walks all non-detached apps driving transitions T1–T33. See the `internal/namespace/runtime.go` package header for the concurrency rules and architecture diagram.
- **`r.dirty` means "there are unwritten changes", and a failed write must not clear it.** Every persist site in `internal/namespace` used to do `persistState(); r.dirty.Store(false)` — the flag was cleared whether or not the write landed, so a refused write silently dropped the debt. That is mild for most fields (the next transition rewrites the whole record) and NOT mild for a dependency pin: after `SetDependencyState` the in-memory pin already equals the running container's image, so `syncDependencyPinsUnderLock` hits its `continue` and never re-marks dirty — the debt could survive until the image changed or the process restarted, which is the state that reappears as "the namespace lost its pin" and hands 17 data to 18. One helper, `persistUnderLock(mutation)` (`runtime_state.go`), now owns the flag (`r.dirty.Store(err != nil)`) and the reporting; `persistState` is pure write-or-say-why. Three consequences are deliberate. (1) The **loop tail** keeps the debt and retries until a write lands — which is what makes the inline mutators' "the tail will collect it" true rather than aspirational. (2) That retry is **backed off** (`persist_retry.go`, 1s doubling to 60s, cleared by the first success) because `persistState` runs synchronously under `r.mu`: measured against the real loop, a store failing in 100ms drew 24 attempts in 3.7s and spent ~65% of the loop's wall clock inside the dead store, with a reader's `Status()` blocked for a full 100ms. Inline mutators are never gated — they carry fresh user intent and return their own error. (3) Reporting is **per streak**, not per attempt: WARN on the first failure, DEBUG on repeats, INFO with the refused-write count when a write succeeds again; the streak is a `Runtime` field, so namespaces cannot pollute each other's report. `doDetach` is the one site that deliberately does NOT mark the debt: measured, the loop grants it exactly one more tail pass after `Detach()`, so a flag there would buy one retry and then be abandoned — its failure is an ERROR naming what the next daemon will adopt instead. Pinned by `persist_debt_test.go` / `persist_debt_mutators_test.go` (nine inline mutators, the backoff gate, the streak, the detach rule), all mutation-checked. **The retry fixes the WRITE, not the operator's awareness**, so the condition is also a state on the namespace: `Runtime.StateWriteError()` answers the streak's error (empty as soon as a write lands) and rides in `NamespaceDto.StateWriteError`. It is deliberately NOT the return value of the mutators — the container really did stop, and turning a dispatched action into a failure would be a lie — so `citeck stop/start/restart <app>` and `citeck edit <app>` print an "applied, but not saved" warning **on stderr** with exit code 0 (stdout stays valid JSON), `citeck status` gains a `State:` line beside `Deps:`, and the web UI raises the non-dismissible `StateWriteBanner`. Without it the operator learned nothing until the next daemon start, where the app is un-detached again and the edit is gone.
- **A detach that could not save its state stops the binary upgrade.** After `Detach()` there is no loop left to retry (measured: exactly one more tail pass), so the final write is the last chance — `persistOnDetach` retries it **3 times, 200ms then 400ms**. The ceiling is set by what already waits on that shutdown: the desktop supervisor force-kills 5s after the POST and `doDetach` has already spent up to 5s draining workers, so a multi-second retry turns "state not saved" into "daemon killed"; and a retry can only fix a TRANSIENT refusal (SQLITE_BUSY, EAGAIN, an NFS hiccup) — a full disk answers identically at attempt 3 and at attempt 300. The verdict reaches the caller (`ShutdownDetached`/`DetachStateError` → the shutdown response's `StateSaveError`), which required splitting `doShutdown`: the namespace phases now run synchronously in the handler and only the server phases stay in the goroutine that drains the listener the response travels on. That synchronous shape is **opt-in via `?wait_state=true`**, not implied by `leave_running`: `internal/desktop/supervisor.go` caps the whole shutdown POST at 2s, so making every detach synchronous would time out an ordinary desktop quit and log a misleading kill warning while still not delivering the verdict (`TestADetachWithoutWaitStateStillAnswersImmediately`). Only the CLI opts in. `lifecycleUpgrade` then **aborts before the binary swap** — the containers keep running but the record of them (detached apps, per-app patches, edited files, dependency pins) is as of the last successful save, and layering a version change on top of that is how a stale record becomes a silent downgrade of behaviour; the message names the cause, what is stale, and that the binary was NOT changed so restarting the same version re-adopts the containers. `runRollback` only WARNs: refusing there would remove the escape hatch off a broken binary.
- **3-phase doStart**: I/O outside lock → prepare plans → atomic state commit under lock. Detached apps get STOPPED status in the commit phase (not pulled/started). Stale containers (existing && !reuse) enter as STOPPING+initialSweep+desiredNext=READY_TO_PULL so the state machine drives the recreate; no parallel inline Docker stops.
- **`:snapshot` pre-pull is Update & Start only**: images whose tag contains "snapshot" are pulled from the registry before the hash diff, but only when `refreshImages=true` — threaded `doReloadEx`→`Runtime.Start`/`Regenerate`→`doStart`/`doRegenerate` and set true only by the explicit Update & Start / Force Update action. A config-edit reload and boot auto-start pass `refreshImages=false` and diff against cached digests, recreating only apps whose config actually changed (an app's image string change via the gear still recreates it, since `GetHashInput` includes the image). Deliberate tradeoff: without the gate, a same-tag dev re-push would be silently missed (hash computed from stale local digest matches running container → adoption) — but re-pulling on every reload also meant hidden re-pulls of unrelated apps on a plain config edit. Update & Start pays that cost explicitly; a config edit does not. This gate is **mode-agnostic** (not desktop-only): in server mode too, `citeck reload` (→ `handleReloadNamespace` → `doReload` → `refreshImages=false`) reconciles config only and does NOT re-pull `:snapshot` digests, while `citeck start` / `citeck start --force` (→ `handleStartNamespace` → `updateAndStartAsync` → `refreshImages=true`) is the way to pick up a new same-tag image. Release-tag deployments are unaffected either way (only `:snapshot` images refresh).
- **The Update&Start button ALWAYS posts `/namespace/start`, whatever the namespace status.** It used to pick the endpoint client-side — `primaryAction = isRunning ? 'reload' : 'start'` in `NamespaceControls.tsx`, justified by a comment claiming 1.x "used reload semantics when running". 1.x did no such thing: `NamespaceRuntime.runtimeThreadAction()` handles `StartNsCmd` with **no branch on `nsStatus`** (`v1.3.9`), mapping `forceUpdate` to the git policy only (`REQUIRED` vs `ALLOWED`) and then re-driving every non-detached app. Routing the running case to `/namespace/reload` meant `refreshImages=false`, so the `:snapshot` digest refresh was skipped, every hash was recomputed from the stale local digest and matched, and `doRegenerate` no-op'd on every app — the button did nothing but blip RUNNING→STARTING→RUNNING. `handleStartNamespace` derives Start-vs-Regenerate from the live status server-side, so one endpoint covers both states; do not reintroduce the client-side branch. Pinned by `web/src/components/NamespaceControls.test.tsx`.
- **Update&Start waits for `reloadMu`; it must never be TryLock-dropped.** Every other async reload path may fold into an in-flight reload, but this one may not: that reload nearly always carries `refreshImages=false`, so folding silently discards the digest refresh that *is* the action, while HTTP already answered 200. `updateAndStartAsync` keeps a single-slot queue (`updatePending` / `updatePendingForce` on `Daemon`) — one pass waits on the lock, extra clicks fold into it (it starts after they arrive, so it satisfies them), and the force flag is OR-ed so a Force click can't be downgraded to a throttled pull. It also **re-samples the namespace status after acquiring the lock**, because waiting can outlast the sample and a wrong `startNotRegenerate` makes `Runtime.Start` early-return ("Runtime already running") and lose the command. `updateStartActionFor` maps that status three ways, and the two non-obvious arms are load-bearing: **STARTING → Regenerate** (the loop is alive, so `Start`'s CAS would drop the command — and since the queue lets a click land during an in-flight pass, STARTING is exactly what a second click samples on a bundle that takes minutes to come up), and **STOPPING → skip**. `Start` looks right for STOPPING because it calls `awaitStoppedLoopExit`, but that only waits once `shutdownComplete` is *closed*, and `signalShutdown` fires at the tail of the stop chain — i.e. only when the status is already STOPPED. Through the whole real STOPPING window the channel is open, the wait returns immediately and the CAS fails, so the pass would pay for a git pull whose result nothing consumes. It bails with a Warn instead; the click is refused, not silently absorbed. **Known limitation:** a click during STOPPING is not honored — the user must retry once the namespace has stopped. Pinned by `internal/daemon/update_and_start_queue_test.go`.
- **`NamespaceDto.Updating` covers the pre-runtime stretch so a click is never silent.** Between the accepted `/namespace/start` and the runtime handoff — the `reloadMu` wait, the git pull, the bundle resolve, the file generation — nothing touches namespace or app status by design, so the UI had no way to show the click was being acted on. `Daemon.updateInFlight` is raised **synchronously in the handler**, before the 200 and before the worker goroutine is spawned (raising it afterwards could race a fast pass that clears it first, leaving it stuck on), and lowered in the worker's defer. What actually keeps it correct across chained updates is that the worker **re-asserts `setUpdateInFlight(true)` right after it acquires `reloadMu`**: the raise path and the CAS both run on the *request* goroutine, which never takes `reloadMu`, so holding the lock orders nothing against them and a previous pass can lower the flag in the gap between its own `updatePending` check and a new click's CAS. The re-assert is self-healing and idempotent (`setUpdateInFlight` broadcasts only on a real transition); the end-of-pass `updatePending` check is a best-effort narrowing, not a guarantee. The same "hand your intent to the pass that will run for you" rule covers the other two folded-click fields — `updatePendingForce` and `updatePendingNsID` — both recorded *before* the CAS and consumed *after* `updatePending` is cleared, so no interleaving can strand a force or drop a folding click's target namespace. `setUpdateInFlight` broadcasts a `namespace_updating` SSE event only on a real transition, and the flag also rides in the DTO so a client that connects or reloads mid-update still sees it. It is **not** a namespace status — the state machine owns those, and faking STARTING here would lie about the runtime. The flag is daemon-global but each pass is namespace-pinned, so `updateInFlightNsID` records which namespace it belongs to and `handleGetNamespace` reports `Updating` only when it matches — otherwise switching namespace while a pass sat queued would show "Updating…" on, and disable the button of, a namespace the pass has nothing to do with. On the client the flag is OR-ed with a short-lived local click echo, and **the echo is released by the post-click refetch, not merely by its 30s backstop**: the skip paths and a fast `doReloadEx` error finish in microseconds, after which nothing else would ever clear it and the button would sit spinning for the full timeout. That refetch is a **tracked, cancellable timer** (`refetchTimer` in `NamespaceControls.tsx`, cleared on unmount alongside the echo backstop): half a second is easily long enough to click Update & Start and then navigate away, and an untracked timer then fires into a component that no longer exists. And it must never be scheduled as `void fetchData().finally(stopEcho)` — `.finally` returns a NEW promise that rejects with whatever the refetch rejected with, so voiding it turns a best-effort refresh into an **unhandled rejection**: a console error in the browser, and in vitest a run that goes red with every single test in it passing (which is exactly how the long-standing `NamespaceControls.test.tsx` flake presented). Swallow the refetch error explicitly and release the echo unconditionally; both halves are pinned by mutation-checked cases in that file.
- **A failed pass is reported, not just logged.** Success and failure used to look identical to the user — the spinner stops and nothing changed — which is the same "my click went nowhere" the Updating flag exists to prevent. `NamespaceDto.UpdateError` + `UpdateErrorAt` carry why the last pass did not happen (a `doReloadEx` error, or the STOPPING refusal), pinned to the target namespace by the same rule as the flag, and cleared the moment a new click is accepted so a stale verdict never sits beside a running update. The web UI raises it on the **same error modal as the synchronous failure path** (`exec`'s catch) — one action, one surface — and de-dupes on `UpdateErrorAt` via a **module-scope** marker, not a ref: the failure stays in the DTO until the next click, so a component-scoped marker would re-raise the modal on every remount. Pinned by `TestUpdateAndStart_ReportsFailureToTheUI` / `TestUpdateAndStart_StoppingRefusalIsReported` / `TestUpdateFailure_IsScopedAndClearedByANewClick` and a vitest case, all mutation-checked.
- **The Update&Start button shows progress by swapping only its ICON, never its label.** Replacing the text resizes the control: RU measures 53px for the wrapped "Обновить и запустить" against 26px for "Обновление…", so the toolbar row jumped on every click; and at the RU width (~95px) "Обновление…" is a single unbreakable word that overflows and clips the spinner, so an overlaid progress label is not an option either. `Play` → spinning `Loader2` plus the disabled styling carries the signal, and `ns.updating` is the tooltip. Verified idle-vs-busy heights identical in all 8 locales. The button ORs the daemon flag with a short-lived local click echo (`CLICK_ECHO_TIMEOUT_MS`) so it reacts on the first frame rather than after an SSE round-trip; the echo is handed off during render (not in an effect — `react-hooks/set-state-in-effect`) and must not touch the timer ref there (`react-hooks/refs`).
- **Start publishes app state BEFORE phase-1 I/O.** `applyCommand` runs inline on the single-threaded `runtimeLoop`, so for the whole of `doStart` there is no `stepAllApps`, no `updateNsStatus` and no `flushEvents` — and `Runtime.Start` has already blanked `r.apps`, which makes the daemon backfill the entire catalog as STOPPED (`appDefsToStoppedApps`). Every service therefore read "Остановлен" until the phase-3 commit, a window dominated by the `:snapshot` pre-pull (concurrency 4, 2-min per-image cap) and reaching tens of seconds on a real bundle. `doStart` now seeds `r.apps` (non-detached → READY_TO_PULL, detached → STOPPED) and calls `flushEvents` before that I/O; `doRegenerate` likewise sets `NsStatusStarting` **before** the pre-pull rather than in its lock phase. Seeded statuses are provisional — the commit phase replaces `r.apps` wholesale — and cannot race the state machine, since the loop is blocked inside `doStart`. `flushEvents` takes `r.mu`, so call it outside the lock. Pinned by `internal/namespace/runtime_start_visibility_test.go`.
- **Graceful shutdown**: phased stop groups (proxy → webapps → keycloak → infra)
- **The daemon answers as soon as the PROCESS is alive, not when its boot has finished.** The Unix socket is bound right after `guardSingleDaemonInstance` (`bindBootSocket`, `internal/daemon/boot_socket.go`) and serves a tiny boot handler until `installRealRoutes` swaps the real mux in — atomically, on the SAME listener and socket file, so nothing reconnects and no second bind can race the first. It used to be bound at the very END of `Start`, after the namespace load (git pull + bundle resolve), the desktop orphan sweep, the migration crash recovery and the namespace start, which meant every asker of "is this daemon alive?" was really measuring "how long did this whole boot take, including Docker I/O, git I/O and namespace startup". One of those askers is the desktop update health gate: measured on a Windows host whose Docker Desktop named pipe was dead (2026-09-08), the sweep burned its full 90 s budget, readiness arrived 90 s in, the 60 s gate failed and a perfectly good 2.11.7 was rolled back to 2.11.5 — the new binary was never the problem. The boot handler touches NOTHING (no Docker, no store, no runtime: the real `handleHealth` pings Docker with a 10 s timeout, which is one of the things that can hang): `GET /health` answers 200 with `status: "starting"` (`api.HealthStatusStarting`), and every other path is 503 `DAEMON_STARTING` with a `Retry-After`. Deliberately NOT a synthetic "running" answer for `/daemon/status` — a client told the daemon is up and then handed a 503 on its next call is worse off than one told plainly to wait. Server mode gets the same treatment on purpose (a `citeck status` that says "still starting" beats a connection refused, and one boot order is easier to keep correct than two), and every error return between the bind and the end of boot closes the listener and unlinks the socket file. The consequence is that "alive" and "booted" are now two questions with two askers: `desktop.DaemonBooted()` (health `status != starting`) gates the wrapper's webview proxy and the CLI's `waitForDaemon`, because the boot handler cannot serve the UI or an install wizard, while `defaultReadyCheck` — the health gate — must keep passing during the boot, which is the entire fix. A daemon too old to know `HealthStatusStarting` never reports it, so both readers treat an older rolled-back binary as booted the moment it answers. Pinned by `internal/daemon/boot_socket_test.go`, which drives the REAL `Start` with the slow boot phase (`constructDaemonFn`) held open — moving the bind back behind it fails all six cases.
- **The startup orphan sweep removes CONTAINERS and nothing else — no named volumes, no networks.** It exists to free the published host ports a leftover namespace squats before the active one starts; reclaiming disk was never its job, and doing it unasked is how a running stand lost its data (measured: `ns=default ws=` at `2026-09-14T03:17:44Z`, a server-mode stand wiped by an unrelated desktop start). `docker.RemoveOrphanContainers` force-removes the pair's containers with **`RemoveVolumes: false`** — an anonymous volume is still the container's data — and leaves the named volumes and the network in place; the log line says so and points at `citeck clean`. Data is removed only by something the operator typed: deleting the namespace or the workspace (both still go through `PurgeNamespace`, which is unchanged), or `citeck clean --volumes --force`, which is dry-run and confirmed. Pinned against real Docker by `make test-integration-sweep` (a labeled orphan with a file in its named volume: container gone, volume and file intact) — a unit test cannot see the difference, since it is one bool plus the absence of a `VolumeRemove` call. **Two phases, two budgets, and it must not be given one:** DECIDING (`docker.FindOrphans`) removes nothing and its failure is already fail-safe, so it is capped at 10 s — it runs before the namespace starts, and on the Windows host above its label enumerations hung on a dead Docker pipe and ate the sweep's single 90 s deadline. It enumerates **containers only**, and that follows from the above rather than being a separate optimisation: containers are all the removing phase acts on, so a pair whose containers are already gone would yield a target that removes nothing and logs nothing, at the price of two more host-wide Docker calls on every desktop start. REMOVING keeps the 90 s, because stopping a stuck container is still the slow part. `runOrphanSweep` also skips the removal phase entirely when the deciding phase answered nothing.
- **Detach mode** (binary upgrade): `Runtime.Detach()` exits without stopping containers for zero-downtime binary upgrades; Docker owns containers, not the launcher (same principle as kubelet restarts)
- **Per-app detach**: `citeck stop <app>` marks app as `manualStoppedApps` (desired-state-first, like k8s) and stops container. Detached apps are excluded from start/reload/regenerate, skipped by reconciler and liveness probes. A dependent whose dependency is detached does NOT proceed past `DEPS_WAITING` — `appsDepsSatisfied` requires the dependency RUNNING (or absent from the current generation); the dependent reports what it is waiting on in `AppDto.WaitingFor` (`unmetDeps`), and generators that can run without a given app (onlyoffice, ai, alfresco) simply omit it from `DependsOn` when detached rather than relying on this fallback. `citeck start <app>` re-attaches, which releases any dependent parked in `DEPS_WAITING`. **An app held that way STALLS its namespace, and every wait has to end on it** (`Runtime.heldByDetachedDepsUnderLock` → `AppDto.Held` → `output.FormatAppTable`'s count): `checkStatus` counted a non-RUNNING app as "not there yet" and only a FAILED one as a reason to go STALLED, so an app that is neither pinned the namespace in STARTING **forever** — which silently disabled the reconciler AND every app's liveness probe for the WHOLE namespace (both are gated on NS RUNNING/STALLED) and left `citeck start` polling with nothing to wait for. One `citeck stop postgres` was enough. The status rule is the owner's, and it is a definition, not a detail: **RUNNING means the namespace is whole and usable; STALLED means a problem arose that will not resolve itself** — which a hold is, exactly like a failed app. So `anyStuck` (failed OR held) drives STALLED, and clearing either one returns the namespace to STARTING and from there to RUNNING; the settled-ness is reported to clients as `AppDto.Held` so their wait loops can end without the namespace having to lie about being usable. The rule is narrow on purpose: EVERY unmet dependency must be detached — **or itself held by the same rule**, because a one-level rule only moves the hang one link up (every webapp depends on zookeeper and rabbitmq and the proxy depends on the gateway, so `citeck stop zookeeper` leaves gateway held while proxy waits on gateway, which is in DEPS_WAITING and not in `manualStoppedApps`). The walk is depth-first with a visiting set: a cycle is rejected at generation, but a hand-edited state file must not spin the runtime loop. A dependency that is merely slow can still come up on its own, so it settles nothing. **The verdict travels as `AppDto.Held`, not as something each reader re-derives** — answering it needs `manualStoppedApps` (a detached app and an app that is merely STOPPED are different) plus the graph walk, and a second implementation in the CLI was a second chance to get it subtly wrong. `citeck status` also names what a DEPS_WAITING app waits on (the dependency ids, appended to the STATUS cell — their statuses are not translated in the CLI asset, and a raw constant beside a translated status reads worse than the app name alone). The runtime does NOT evict a dependent that is already RUNNING when its dependency is detached: `StopApp` never cascades, so the hold takes effect at the dependent's next start. State persisted in `state-{nsID}.json` (server mode; desktop mirrors it in the SQLite `namespaces.state_json` column).
- **Template detachedApps**: workspace `namespaceTemplates[].detachedApps` applied on first start (no persisted state). Install wizard sets `template: "default"` in namespace.yml.
- **Custom workspace links**: workspace-config `links:` (`bundle.WorkspaceLink`: name/url/icon/order/category/description + `dependsOn: [appId]`) surface in the launcher sidebar alongside the built-ins. Flow: `Generate` copies them into `GenResp.CustomLinks` → `runtime.SetCustomLinks` (refreshed each load/reload) → `generateLinks` (in `ToNamespaceDto`, recomputed every SSE tick) gates each by dependency status: **hidden** (omitted from `Links`) when any dep is absent from the namespace (`generatedDefs`), **disabled** (`LinkDto.Disabled`) when a present dep is not RUNNING, enabled otherwise; no deps ⇒ always enabled. Custom links carry `LinkDto.Custom=true`; `Dashboard.tsx` gates them on `!disabled` only (NOT the namespace-wide running flag, unlike built-ins). They are pinned to the bottom of the sidebar (`customLinkOrderBase=1000` + configured order; built-ins span ~ -100..101).
- **`r.config` is published SYNCHRONOUSLY on reload; anything read from `r.apps` needs a `generatedDefs` fallback.** These are the two shapes of the same defect — a UI surface reading the runtime's lagging view instead of the authoritative one — and both bite hardest on a STOPPED namespace, where the runtime loop is not running and `r.apps` is empty. (1) `r.config` used to be refreshed only by the async `cmdRegenerate`, so the sidebar links' proxy host/scheme, the Keycloak link's auth type, `AppliedConfig` and the DTO's name/bundle all kept the pre-edit value until re-activation; `doReloadEx` now calls `Runtime.SetConfig` next to `SetGeneratedDefs`/`SetCustomLinks`. That is safe precisely because `r.config` is read **only** in `runtime_dto.go` — nothing in the state machine, workers or orchestration touches it — so an out-of-band refresh cannot race a transition. Keep it that way: a state-machine read of `r.config` would make the synchronous setter a hazard. (2) `r.apps` is EMPTY until the namespace has been started once, so `StartableAppImages` reported no images and the pre-start registry check (`/registry-bindings/missing`, which the UI blocks Start on) answered "nothing missing" for exactly the namespace it exists for — freshly loaded, or withheld by the secrets gate — after which the pulls failed on auth anyway. Same for the built-in PgAdmin link. Both now use live-OR-configured, the rule the custom links already followed (`r.apps[dep]` OR `r.generatedDefs[dep]`), and `handleGetNamespace` had long been backfilling its app list from `act.appDefs` for the same reason. When adding a surface, ask which of the two it reads.
- **The namespace DTO's config-derived fields must come from `act.nsConfig`, never from the runtime's copy.** `ToNamespaceDto` reads `r.config`, which is refreshed ONLY by the async `cmdRegenerate` (`runtime_loop.go` `applyCommand`) — and on a STOPPED namespace the runtime loop is not running at all, so that command is never applied. `handlePutNamespaceEdit` persists the YAML and calls `doReload`, which sets `a.nsConfig` synchronously and then *enqueues* the same config for the runtime; the header therefore kept the pre-edit value while the namespaces dialog (which reads the store) showed the new one. This was found once for `Name` and fixed for `Name` alone; `BundleRef` is the other field derived from that lagging copy and was left behind — switching a namespace's bundle left the header on the old one indefinitely. `handleGetNamespace` now overrides both from `act.nsConfig`, with `ResolveDisplayBundleRef(..., act.bundleDef)` so a symbolic `LATEST` still renders as the concrete resolved version. Those two are the only config-derived fields in the DTO; keep them reading from the same authoritative place. Pinned by `TestNamespaceHeaderShowsTheEditedBundle` (stopped AND running) and `TestNamespaceHeaderResolvesLatestToTheConcreteVersion`.
- **`app.Def` is the record of what the RUNNING container was built from — the gear-save path must not overwrite it.** `doRegenerate`'s entire diff is `existing.Def.GetHash() != newHash`, so whoever writes `app.Def` before a reload decides the reload's answer. `Runtime.UpdateAppDef` (the only production caller is `handlePutAppConfig`, i.e. the gear editor and `citeck edit <app>`) used to write the edited def straight into the live app and then let the daemon run the reload — which then compared the new def against itself, found no change, and left the container alone. The user saw the new version in the editor and in the app table, and the container kept running the old image until they stopped and started the app by hand. It *appeared* to work whenever the new tag was already in the local image cache, because `handlePutAppConfig` clears `ImageDigest` on save and `doRegenerate` re-resolves it from Docker: the digest then carried the difference the image string should have carried. For a version not pulled yet — every real bump — `GetImageDigest` returns `""` on both sides and the hashes match exactly. `UpdateAppDef` now propagates into the live def only when `app.ContainerID == ""` (nothing deployed to protect; also the stopped-namespace case, where no reload follows and the app table's version column would otherwise go stale) — while a container exists, the caller's reload re-derives the live def on both the changed and unchanged paths anyway. Note none of the pre-existing regenerate tests could catch this: they all call `Regenerate` WITHOUT the `UpdateAppDef` step, which is precisely the step that destroys the baseline. Pinned by `TestGearEditOfTheImageRecreatesTheContainer`, which sets the bumped tag's local digest to `""` so the accident cannot mask the defect.
- **`namespace.yml` has a config GENERATION (`apiVersion`), and it is stamped at CREATE time only.** `namespace.ConfigVersionCurrent` (2 today) is written as `apiVersion: v2` by the two create paths — `buildNamespaceConfigFromCreate` and the `citeck install` wizard — and by nothing else. It answers exactly one question: was this namespace created before or after a given launcher release? That is what lets a DEFAULT change without changing what an existing namespace runs. Three rules keep it honest. (1) It must **never** be seeded in `DefaultNamespaceConfig()`: `ParseNamespaceConfig` starts from those defaults, so a version set there would silently promote every namespace on load and hand it the new defaults — the exact opposite of the point. (2) `Config.Version()` degrades **to the OLD generation** on anything unparsable (absent, `"banana"`, `v0`), because guessing "new" means applying new defaults to a namespace we failed to understand. (3) `MarshalNamespaceConfig` still stamps an empty `apiVersion` as `v1`, so an old namespace that gets re-saved records what it is rather than drifting.
- **MongoDB is now generation-scoped, and the flag is a `*bool` for one specific reason.** Only `eproc` ever used mongo (`main-mongodb` in the workspace config is the sole `mongodb:` datasource in both community and enterprise), and it no longer needs it: it kept process definitions and instances there until the `mongo-to-ecos-data-migration2` patch moved them into PostgreSQL, after which the container is dead weight. **eproc 2.33.0** is the floor — that release added `ecos-process.mongo.enabled` (`MongoDisabledEnvironmentPostProcessor`, which excludes the Spring mongo auto-configurations) plus a `MongoDisabledStartupGuard` that REFUSES to start when the switch is off, the migration patch has not run and Camunda has deployments, because the old data would silently become invisible. Two consequences for us: eproc defaults that property to **true**, so saying nothing is not the same as saying false; and an eproc older than 2.33.0 ignores the property entirely, so a namespace pinned to an older bundle must keep the container. So namespaces created at generation 2+ run without it. `MongoDbProps.Enabled` is a POINTER because "absent" is a third, load-bearing state: no existing `namespace.yml` has the key, and a plain bool would read every one of them as "disabled" and delete a running stand's database container on the first reload after an upgrade. `Config.MongoEnabled()` therefore answers: explicit flag if present, otherwise `Version() < 2`. Turning it off has to remove the datasource **whole** — a leftover `depends_on` parks eproc in `waitForDeps` forever and a leftover URL (env or cloud config) points Spring at a host that no longer resolves — and additionally write `ecos-process.mongo.enabled: false` into eproc's `application-launcher.yml`, because eproc opens its mongo client from its own switch, not from the datasource list. That key is written AFTER the three-level cloudConfig merge on purpose: with no container in the namespace there is no configuration layer that could legitimately turn it back on. The web UI offers the toggle (Advanced tab of the namespace dialog) only for `configVersion < 2` — on a newer namespace it would be a switch with nothing behind it — and omits `mongoEnabled` from the PUT when it was never offered, so saving a form that never asked the question cannot answer it. The mongo VOLUME is left alone either way; only the container goes.
- **A bundle AND a workspace config name their third-party images in a `dependencies:` section, and that section is a COMPATIBILITY CONTRACT with the launchers in the field, not a tidier layout.** The dependency gate arrived in 2.12.0; **no older launcher has any of it** — Kotlin 1.x and every Go release up to 2.11.7 apply whatever image the bundle names straight onto the existing data volume. So a top-level `postgres:` entry raised 17 → 18 crash-loops their stand (`The data directory was initialized by PostgreSQL version 17…`) with the whole namespace down, and a RabbitMQ 4.1 → 4.2 bump upgrades the Mnesia data **in place, silently and irreversibly**, with no retained volume and no way back. Both parsers ignore keys they do not know, so an image moved into `dependencies:` is invisible to them: one bundle raises an infra version for 2.12+ users while everyone else keeps running what they run today. **Teaching an older launcher to read the section is the wrong fix, and it was tried**: 1.4.2 briefly read it, because qdrant's image was the one infra version Kotlin 1.x took from the bundle (`rag` there would otherwise come up with no vector store at all). That reversed the property the section exists for — a launcher with no dependency gate applies whatever image it is handed STRAIGHT onto the existing volume, so reading a raised minor is exactly the silent data move the gate was built to stop. The fix went the other way: 1.x now pins `QDRANT_IMAGE` as a literal, like its rabbitmq, and takes every other infra version from its workspace config, whose built-in defaults no public workspace overrides. The rule that generalises: a launcher without the gate must read NO dependency version from a bundle, and a version it should move onto is moved by editing that launcher's own constant, deliberately. Four rules hold it up. (1) It is parsed into **`Def.Dependencies`, never merged into `Def.Applications`** (`parseBundleDependencies`, `internal/bundle/resolver.go`): `IsEmpty()` must keep meaning "this bundle has no CITECK apps", or a dependencies-only bundle would silence the non-dismissible `BundleErrorBanner` on exactly the namespace that needs it — seven third-party containers reporting RUNNING with none of the product in them — and the webapp loop admits `Applications`, which infra must never reach. (2) The `image:` accepts **both** forms, the plain string the section was specified with (`postgres:17.11`) and the `{repository, tag}` map every top-level entry uses, both through the same imageRepos rewriting — `ResolveImageRef`'s body was factored out as `resolveImageRefWithRepos` so the parser (which holds the repo map and never sees a `WorkspaceConfig`) shares the rule instead of growing a second copy of it. `resolveImageRefWithRepos` has a **hand-kept Kotlin mirror**, `getImageUrl` in `citeck-launcher-1x`'s `BundleUtils.kt` (`src/main/kotlin/ru/citeck/launcher/core/bundle/BundleUtils.kt`, which says so in its own comment) — the two are not shared code and nothing tests them against each other, so editing the Go function's repo-rewriting rule without updating that Kotlin function silently breaks parity between the two launchers reading the same workspace repo. Every OTHER image in the bundle goes through that same decoder now: `parseBundleFile` walks the YAML **node tree** and reads each `image:` and each `ecosAppsImages` element through `decodeImageValues` + `resolveImageRefWithRepos`, exactly as this section does. It used to walk a generic `map[string]any` instead, and there an unquoted `tag: 17.10` had already become `float64(17.1)`: the string type-assertion in the old `strVal` failed, the tag came out empty, and the APPLICATION left the bundle — no image, no container, no log line. What differs between this section and everywhere else is only what a LIST means (see (6)), never how a tag is read. Two consequences of the node walk are load-bearing and each has its own test: YAML's own indirection must be resolved by hand (`followAlias`), because yaml.v3 hands an alias through verbatim when the destination is a `yaml.Node` — its node short-circuit sits BEFORE its alias case — and a merge key (`<<`) has to keep working, which `mappingEntries` does with YAML's own precedence (a key written in the mapping beats the same key merged in, wherever the merge sits), while an entry's own fields are read with `Decode`, which applies merges itself. An entry that NAMES an image the launcher cannot read is now logged; an entry with no `image:` at all is not an application and stays silent. (3) `resolveAppImage` resolves **bundle `Dependencies` → bundle `Applications` → namespace image → workspace `dependencies:` → typed workspace defaults → launcher default**. `bundleImageOr` delegates to it without a namespace image. This order also applies to MongoDB, pgAdmin, observer, stt-sidecar and webapps; no namespace image may override a bundle release. Explicit `citeck edit` patches apply after generation, and dependency data pins still gate incompatible image changes. (4) The main parse loop **skips the section by name**, and that skip is structural rather than cosmetic: the loop hands every top-level key to `processApp`, so without it an entry id colliding with the entry schema's own key (`dependencies.image`) is read as an application named `dependencies`. An unknown id inside the section is kept and simply never asked for — a future launcher may know it, and failing the bundle over it would defeat the point. (5) The **WORKSPACE config has the same section**, because the hole was still open one level up: `workspace-v1.yml`'s typed blocks `postgres:`, `keycloak:`, `zookeeper:`, `pgadmin:`, `onlyoffice:`, `alfresco:` and `sttSidecar:` each carry an `image:` that Kotlin 1.x and every Go release reads, so a version raised there reaches an ungated launcher exactly as a top-level bundle entry would — and raising a dependency for every namespace of a workspace at once is useful in its own right. The workspace section remains below the bundle and namespace fallback in the shared image resolver. Three details are load-bearing. `WorkspaceConfig` is a TYPED struct, not the bundle's generic map, so the dual `image:` form needs a deliberate `UnmarshalYAML` on `DependencyEntry`; it is **total and never returns an error**, because `parseWorkspaceConfig` drops the ENTIRE workspace config on a YAML error (imageRepos, webapps, bundleRepos and all), so one entry this launcher cannot read must cost nothing but itself. The imageRepos rewriting happens at **read** time, in `WorkspaceConfig.DependencyImage`, since `ResolveImageRef` is a method on the config that owns `ImageRepos` and an entry has no way to reach that map from inside its own unmarshal. `generatePgAdmin` uses the same bundle-first resolver, including conflicts with `namespace.yml`. Existing namespace/workspace image values that conflict with a bundle no longer select the running release; a differing **namespace** image and a differing **workspace `dependencies:`** image both produce a warning directing the operator to `citeck edit` (`discardedWorkspaceImage`). The typed workspace blocks reach `resolveAppImage` as its `fallback` argument, which also carries the launcher's own built-in default — warning on that argument would fire for every app of every namespace, since a bundle naming a release image differs from the default by construction — so those stay silent. (6) **An image value may be a LIST, and in the `dependencies:` section that list is a LADDER.** Its last rung is the target; the rungs between it and the pin are what make a hop the vendor forbids in one step reachable in several. Everywhere else — `applications:`, `ecosAppsImages`, the typed workspace blocks, `additionalApps`, a `namespace.yml` override — a list resolves to its **FIRST** element, because a reader outside the gate has no pin, no hold and no migration, and the only honest reading there is the most conservative rung (the same principle as `LegacyImage()`). **A rung is never skipped**: `UpgradeSupport` may REFUSE a hop the ladder does not name, but it may not authorize collapsing a ladder the author wrote — the table is this release's belief about a vendor and can go stale in the permissive direction, while the ladder is the author's statement about their own vendor and is older than any of our tables. A rung the version parser cannot read invalidates the WHOLE ladder (the dependency stays on its pin), because dropping it would produce exactly the jump the ladder exists to forbid. **A ladder is invisible to launchers 2.12.0–2.12.2** — they read `image:` as a scalar or a `{repository, tag}` map only, skip a sequence with a warning and fall back to their own default — which is safe for a dependency they never carried and is NOT safe for `rabbitmq`, where that default is `4.1.2-management`, i.e. a through-minor downgrade onto Khepri data. See [configuration image precedence](docs/config-layers.md) and `TestGeneratedImagesRespectBundleAndExplicitEdit`. **`citeck-launcher-1x`'s typed workspace blocks now take the same first-element reading, and it had to be added by hand.** Its `postgres`/`keycloak`/`zookeeper`/`onlyoffice`/`pgadmin`/`sttSidecar` blocks (`WorkspaceConfig.kt`) are plain `image: String` fields read through Jackson (`Yaml.read` → `Json.convert` → `ObjectMapper.convertValue`, `FAIL_ON_UNKNOWN_PROPERTIES` off, `UNWRAP_SINGLE_VALUE_ARRAYS` off), so before this a YAML sequence there did not degrade to "one entry ignored" the way a bundle's `dependencies:` entry does — it threw a Jackson type-mismatch exception that `Yaml.read`'s caller does not catch, which failed the WHOLE workspace config (measured: `imageRepos`, `webapps`, everything) and left the workspace unable to open at all. `TypedBlockImageDeserializer` (`ru.citeck.launcher.core.utils.json.serialization`) fixes it, applied per field via `@param:JsonDeserialize(using = ...)`, mirroring `bundle.ImageRef` shape-for-shape (scalar, `{repository, tag}` map, or a list of either — taking the list's first element). Nothing ties the two together structurally: a NEW typed image field added to either launcher's config, or a new shape added to one `ImageRef`/`ImageRefDeserializer`-equivalent, has to be ported to the other by hand.
- **A bundle can declare the launcher it needs with a top-level `minLauncherVersion` string, and that key is the other half of the `dependencies:` story above: where `dependencies:` HIDES a new requirement from an old launcher that cannot see it, `minLauncherVersion` REFUSES a bundle that needs an old launcher to actively do something it cannot — walk an image ladder, run a migration, honour a field it does not know.** It is read from the YAML **node tree** (`parseBundleMinLauncherVersion`, `internal/bundle/resolver.go`, through the same second parse `parseBundleDependencies` uses), never from a decoded `map[string]any`, for the same reason as every other version in a bundle: an unquoted `2.10` in a generic map has already become `float64(2.1)` by the time anything reads it, so a two-part floor would silently lose its patch digit. Absent or blank means no requirement — this has to be explicit, because the comparator below treats an unparseable string as newer than everything, and a blank value would otherwise refuse every bundle it appears in. **The gate is on the config WRITE, never on load** — `persistNamespaceConfig` (`internal/daemon/ns_config_store.go`), the daemon's single write path (create, edit, upgrade, raw PUT), plus `citeck install`, which writes the namespace config itself and bypasses the daemon entirely. Refused as HTTP 409 `LAUNCHER_TOO_OLD`, localized in all 8 locales. Nothing on load, reload, activate, reload-plan or `handleGetNamespaceEdit` consults the key, and that is deliberate, not an oversight: the gate asks what the config BEING WRITTEN names, not whether the bundle ref changed, so an edit that KEEPS a too-new bundle is refused while an edit that MOVES OFF one is allowed — that is the way back to a namespace stuck on a bundle this launcher can no longer write, and it falls out of asking about the result rather than the diff. A namespace already running such a bundle keeps loading, starting and reconciling; only creating or editing INTO that state is refused. `LATEST` resolves to the newest bundle THIS launcher can run (`bundle.LatestRunnableBundle`): it walks the version list newest-first and takes the first one that clears the floor, logging every skip, and it never fails for a floor reason on the load/create path — only a PINNED version that fails to clear the floor refuses, at the write gate. The comparison is `update.Greater(floor, current)` via `bundle.NeedsNewerLauncher` and nothing else — no second comparator — and it inherits two behaviors from that function's "invalid sorts highest" clause: a dev build (`make` stamps a non-semver `dev-<date>`) is never refused by any floor, and an UNREADABLE floor (a typo, garbage text) refuses a released launcher, fail-closed, because a requirement this launcher cannot understand is exactly what the key exists to stop. **Launchers that predate the check — Go 2.12.x and earlier, Kotlin 1.x — ignore the key by construction** (a scalar top-level entry has no `image:`, so the app walk skips it silently), which means it protects nobody retroactively: publishing `minLauncherVersion` today only starts protecting operators once they are running a launcher that enforces it.
- **A bundle can no longer move a dependency's DATA onto a version that would break it — the launcher pins, reports, and (for PostgreSQL, RabbitMQ, ZooKeeper and Qdrant) migrates.** `internal/deps` is a pure registry — no Docker, no I/O, so every rule is unit-testable and the generator can consult it: the six dependencies (postgres, rabbitmq, zookeeper, keycloak, mongodb, qdrant), how a version is read out of an image tag, which moves are significant, and which this launcher can migrate. `Migratable()` is true for **postgres, rabbitmq, zookeeper and qdrant** (`TestEveryMigratableDependencyHasAMigratorAndARollback` pins the count at 4 and demands an entry in both registry tables); keycloak and mongodb are reported and held, never migrated. RabbitMQ, ZooKeeper and Qdrant are **minor-breaking** where postgres/keycloak/mongo are major-breaking, because that is where each vendor puts its format break. `deps.Breaking` asks two questions before the descriptor's: **the same image on both sides is never breaking**, whatever the tag says — it is the image the data already runs on, and without that arm a namespace pinned to an unparsable tag (`:latest`) would report a permanent, un-actionable "held back" upgrade from X to X — and **an unparsable tag on either side IS breaking**, because the alternative is a silent swap onto data we do not understand (`TestBreakingRules`). Pins live on the **Runtime**, not in the state JSON, for a structural reason: `persistState` rebuilds the whole record from Runtime fields, so anything the migration engine wrote into the file directly would be erased by the next unrelated persist; every mutation in `deps_state.go` therefore persists inline — the one exception is `syncDependencyPinsUnderLock`, which marks `r.dirty` instead so the loop tail coalesces its write with everything else the iteration changed. There are **two ongoing pin writers** (plus seeding, which writes through `SetDependencyState` on the reload path and after a snapshot import). (1) `syncDependencyPinsUnderLock` re-pins any dependency whose app is RUNNING on an image other than its pin — running is the proof the data accepted that version, which is how a non-breaking `17.5 → 17.11` becomes the new baseline — and it lives in the **loop tail** so it covers a fresh start and container adoption in one place. (2) `CommitMigration`, which moves the pin, clears the journal and records the verdict in **one write** and is atomic **in memory** as well: a failed persist restores all three previous values, because a runtime that believed the pin had moved while `failAndRollback` deletes the new volume would emit the new version's layout onto a volume that no longer exists — an empty cluster standing beside the intact old data (`TestCommitMigrationIsOneWrite`, `TestCommitMigrationDoesNotMoveMemoryWhenThePersistFails`). Writer (1) **stands aside while a journal is open** (`TestSyncPinsStandsAsideForAnOpenMigration`): the precondition is that a migration commits only while the namespace is STOPPED under the long-op lock, and the journal guard is defense in depth for it. The generator gate is one function, `resolveDependencyImage`, that every infra generator passes its image through; a held-back candidate becomes a `DependencyUpgrade` the DTO/CLI report. Hash stability is the release-safety property here — a pinned 17 def must be **byte-identical** to what the previous launcher emitted, or the feature recreates every user's postgres container on upgrade — and it is pinned against a golden file, `internal/namespace/testdata/postgres17.hashinput.golden` (`TestPostgres17PinnedDefIsByteStable`). The **18 layout is `/var/lib/postgresql` with NO `PGDATA`** (the image defaults it to `/var/lib/postgresql/<major>/docker`) against 17's `/var/lib/postgresql/data` plus an explicit `PGDATA`; the parent mount is also what a future in-place `pg_upgrade` needs. **Which VOLUME that is stopped being a version question** when the generation counter arrived (see “The volume name comes from a persistent COUNTER” below): `PostgresLayout` carries only `MountPath`, `PGData` and `PGVersionRel`, and the volume comes from the pin. What has not changed is that the migration builds the new cluster **next to** the old data — that is what makes the rollback a deletion and leaves the old version bootable. The layout follows the major of the image that will **RUN**, never the candidate, and an unparsable effective tag falls back to the **legacy** layout, since guessing 18 would start a brand-new empty cluster beside existing data (`TestUnparsableTagKeepsTheLegacyLayout`). The webapp loop's collision guard is part of this contract, not cosmetics: it runs AFTER the gate, so a bundle application named `postgres` reaching `generateWebapp` through `GetOrCreateApp` would put the held-back candidate into the container while `GenResp` still reported the pin as effective (`TestPinSurvivesAWorkspaceConfigWithNoWebapps`). The same guard covers the three built-ins generated AFTER the loop — `stt-sidecar`, `proxy`, `onlyoffice` (`lateBuiltInApps`) — from the other side: there the built-in runs last and would overwrite only the fields it sets, leaving a HYBRID (an OnlyOffice document server carrying `SERVER_PORT`, a Spring props mount and a full JVM memory budget) plus the residue the discarded webapp had already written into `ctx.Files` and `ctx.CloudConfig`. Skipping the bundle entry in the loop leaves the generation byte-identical to one that never saw it (`TestLateBuiltInsAreNotRedefinedByABundleWebapp`); the three images still come from the bundle, which those generators read themselves. A pin the launcher DERIVED FROM DATA is a Docker Hub reference it invented (`postgres:<major>`, `LegacyImage()`), so on a private-registry or air-gapped stand the held-back dependency would be the one container that cannot be pulled: `rehomePin` therefore keeps the pin's TAG and adopts the CANDIDATE's repository when — and only when — the pin still carries the descriptor's default repository and the candidate's differs. A pin read off a real container names the real registry and is evidence, not a guess, so it is untouched; a same-repository namespace is byte-identical, which is what leaves the hash-stability golden alone. The reported upgrade's `From` is the effective (possibly rehomed) image, because that is what the migration's temp source container is built from. Seeding is scoped to the dependencies the namespace's CONFIG actually has (`namespaceDependencies`: mongo iff `MongoEnabled()`, keycloak iff the auth type is keycloak, the rest always), pinned against the real generator by `TestNamespaceDependenciesMatchesWhatTheGeneratorEmits` — without it a desktop namespace with a postgres container and no keycloak paid for a utils container on every single load, to read data for a dependency it does not run. Existing namespaces have no pin, so `deps_seed.go` derives one — **container image → `PG_VERSION` in the data → the descriptor's legacy image** — and the verdict is deliberately **tri-state**, because the two mistakes are not symmetric: a wrongly LEGACY pin only holds an upgrade back, while a wrongly ABSENT pin hands 17 data to 18, which starts an empty new-layout cluster beside it and lets the RUNNING hook settle the pin at 18. So a probe FAILURE that leaves the data question open ⇒ the legacy image with a WARN (which is why `RunUtilsContainer` reports a failed `docker inspect` as an ERROR rather than as exit code -1 with a nil error — otherwise “the probe failed” arrives dressed as “the file answered”), while a **successful "there is nothing here" ⇒ no pin even when the container probe failed** (a container cannot exist without its data volume, so an absent volume answered without error proves there is nothing to protect — this is the fresh namespace first loaded with Docker down, which must not be frozen at legacy with no way back), and a volume with no `PG_VERSION` holds no cluster and the search continues into the other layout. **Keycloak is keyed off the postgres data** — its state lives in that database, it has no volume of its own, and what the data proves is that the namespace has been running, i.e. on the legacy image. A snapshot import **re-seeds** the pins of the volumes it replaced (`reseedAfterSnapshotImport`), or a namespace already on 18 that imports a 17 snapshot would keep an 18 pin over 17 data. The load path seeds **without persisting** (`RestoreDependencyState`): persisting there writes `r.status`, still STOPPED before the caller has acted on `ShouldStart`; the reload path persists each seeded pin. `DEPENDENCY_VERSION_LOCKED` closes the last door **for the IMAGE** — `EditedAppPatches` land at the TAIL of `Generate`, after the gate, so `citeck edit postgres` (or the gear editor) setting `image: postgres:18` is the one way a breaking image could still reach a container; it is refused with a 400 (`TestBreakingImageEditOnADependencyIsRefused`). **The gate asks four questions, in this order, and only the first is free of Docker.** (1) Is the target below the dependency's **support floor** — the oldest version the platform has been tested on (`deps.SupportFloor`, one table in `internal/deps/support_floor.go`: postgres 17, rabbitmq 4.1, zookeeper 3.9, keycloak 26.4, mongodb 4.0)? Then refuse whatever is on disk; that refusal has to hold with Docker down, so it is decided before any volume check (pinned by a test that counts `VolumeExists` calls and requires zero). The floor is **strict** (the floor version itself is fine), it never applies to an unparsable tag (nothing to compare — `Breaking` already speaks about the tag), and it binds the EDIT gate ONLY: it limits what an operator may CHOOSE, never what may EXIST. A pin seeded from a `PG_VERSION` of 15 is a fact about a stand that is already running, and refusing it would leave the operator unable to touch that namespace at all — which is also why **an edit that names the same VERSION is not a choice of version** and short-circuits before the floor: the editor round-trips the whole def, so for a held-back dependency every save of a memory limit or a probe would otherwise come back 400. That test is `editKeepsVersion`, and it is deliberately NOT byte identity — the user's ruling is "compare the version in the tags, not the images byte for byte", so re-homing a below-floor pin to another registry at the same version (`postgres:15.6` → `myreg/postgres:15.6`) passes, and so does dropping a suffix the version parser ignores (`rabbitmq:4.2.9-management` → `rabbitmq:4.2.9`, a real change of image variant that moves no VERSION, which is the only thing this gate judges — the same class of operator surgery it already allows when a patch rewrites a dependency's `volumes:` or `PGDATA`). Two traps live in that one function: `deps.Version` carries `Raw`, the whole tag, so `==` on it would answer "different" for `4.2.9-management` vs `4.2.9` — equality is expressed as neither-older-than-the-other over `deps.MovesBackwards`, which also keeps it from drifting from the backwards rule beside it; and both tags must PARSE, or two unparsable references would read as the same version and walk past `Breaking` (a digest pin therefore still has only byte identity to save it). A bundle offering an older patch still applies silently (user's ruling); the floor may be RAISED by a future release, never lowered. (2) Does the edit move **backwards**? Then refuse while the data volume exists — **including a patch revert**, which the gate used to allow because `deps.Breaking` only calls a format change breaking. The honest position is that a patch downgrade is usually harmless and nowhere guaranteed (PostgreSQL documents only the forward direction and some minors need a `REINDEX`; a RabbitMQ patch that enabled a feature flag the older one does not know refuses to start), so on data that exists the launcher does not go backwards at all. The message differs from the breaking one on purpose: "cannot read that data" is FALSE for a patch revert, so that case says instead that the launcher does not move a dependency backwards on data that exists. (3) Is it a **breaking forward** move? Refuse while the data exists, naming the migration. (4) Otherwise pass. **Questions 2 and 3 stand only while there is DATA to protect** — `dependencyEditPinFollows` allows the edit when the volume provably does not exist and the pin then FOLLOWS the edit (image only; generation and rollback target untouched, the rule `syncDependencyPinsUnderLock` follows). The pin is written explicitly rather than left to the RUNNING re-pin hook, because the practical case is a STOPPED namespace — the volume has to be deleted, which means stopping first — where nothing else would ever write it. Three refusals guard that opening, each a test: **any error from the volume check fails CLOSED** (an unreachable Docker is not "there is no data"), a volume that EXISTS is data even if it holds nothing (the `Env` seam has no directory listing, and guessing "empty" risks a version landing on real data — deleting the volume is how the operator says there is nothing there), and a dependency with **no volume of its own** keeps the refusal (Keycloak's state is in the namespace's PostgreSQL database, so "no volume" there means the data is elsewhere). **A pin move forces a reload even on a STOPPED namespace.** The whole dependency surface — the list status, `deps upgrade`, the preflight — is computed from the generator's cached verdict, and an edit that moves the pin without regenerating leaves it describing the pre-edit world: measured on a live stand, `citeck deps` reported `4.2.9 → 4.2.9  upgrade available` and `citeck deps upgrade` then refused a move `4.1.2 → 4.2.9` whose source volume was gone. `POST /namespace/reload` on a stopped namespace costs 9 ms and fixes it at the root, so `handlePutAppConfig` reloads when `running || pinMove != nil` — while the success message stays keyed on `running`, because the containers really do only change on the next start. **The refusal is also where the launcher says how to go back, and it answers instead of hedging.** A backwards edit is the moment an operator is reaching for the old version, so `dependencyEditRefusal.wayBack` consults the same rollback offer the dependency list computes and picks one of three sentences: the offer is takeable (name the command AND the volume it returns to), its retained volume is gone (say so — reusing `migrate.RetainedVolumeGoneProblem`, so the two surfaces cannot word it differently), or there was never a migration to go back to. The old text said "the volume its migration retained, if it made one" in all three cases, including for a dependency that had never migrated, where the command it named would itself have been refused. One rule guards the degrade: only the exact sentence `RetainedVolumeGoneProblem` produces is read as "gone", so **"I could not ask Docker" can never be printed as "it is deleted"** — a `VolumeCheckFailedProblem`, an offer with no verdict, and a forward refusal all fall back to the old hedge. The RULE is untouched (`deps.Breaking`); only what the operator is told changed. It is deliberately not more than that: a patch that rewrites the `volumes:` or the `PGDATA` env of a dependency is out of scope and passes, because those are legitimate operator surgery and the launcher has no way to tell a repair from a mistake. The engine (`internal/deps/migrate`) is a **write-ahead journal**: persisted before the first step and after each one, and a step that CREATES something journals it **before** creating it (`createVolume`), so rollback is driven only by what the journal says exists and a crash between the two cannot orphan anything. Any step error, journal-write failure or cancellation runs `Plan.Rollback` on a `context.WithoutCancel` (a daemon shutdown must not skip the undo) and the pin never moves; a rollback that **succeeds** clears the journal, one that **FAILS keeps it** — the half-built volume and the temp containers are still on the host, so the record must survive: it is retried at every launcher start, the recovery does not hand the namespace back running, the pin is frozen (writer (1) stands aside), and every new migration is refused with the `rollbackPending` wording (`RecordRollbackFailure`, `rollbackPendingMessage`, `TestRecordRollbackFailureKeepsTheJournal`, `TestRecoveryKeepsTheJournalAndStaysStoppedWhenTheRollbackFails`). `NamespaceDto.DependencyRollbackPending` carries that same wording on the ORDINARY namespace fetch — namespace-scoped by construction, and empty while a migration is actually running — because the case that needs it emits nothing: a crash recovery whose rollback FAILED produces no event and no result, so before this the alarm appeared only on a remount, a namespace switch, or a poll that itself only ran once the alarm was already up. A post-commit `Finalize` failure is a `*FinalizeError` — a completion with a warning, never a rollback, since the data has moved and the pin says so. The PostgreSQL plan is **10 engine steps** for a SINGLE hop (stop-namespace, pull-image, start-source, dump, stop-source, create-volume, start-target, restore, verify, stop-target) plus the engine-level **commit**, which is the engine's and not the plan's — the spec's "11" counted it. That count is not a constant: a ladder walks the same per-rung loop once per rung rather than once total, so a 2-rung ladder is 16 steps and a 3-rung one 22 (10, plus 6 for every rung short of the top) — every rung repeats `create-volume`, `start-target`, `restore`, and every rung but the last also repeats `dump`, `stop-target`, `create-volume` to discard the cluster it was just dumped from before the next one is built. Every intermediate rung reuses the ONE scratch volume `deps.ScratchVolumeName` names (`<next generation>-hop`, journalled as `ScratchVolume` so the rollback removes it) rather than costing a generation of its own, and the dump itself is written and read COMPRESSED (`gzip -1` / `gunzip`, over a `bash -c` pipeline with `pipefail` set — see `DumpScript`/`RestoreScript` in `postgres_restore.go`); see [the PostgreSQL major-upgrade walkthrough](docs/postgres-major-upgrade.md) for the full per-rung shape. It is a logical dump (`pg_dumpall` → `psql`) into a NEW volume and the old volume is only ever READ, which is exactly why an in-place `pg_upgrade` is not what this does. Details that are each a measured trap: **readiness is two probes over TCP 127.0.0.1, not the socket**, because the official image's entrypoint runs a TEMPORARY init-time server that listens on the Unix socket only — a socket `pg_isready` succeeds there and then starts failing when that server is torn down (`TestReadinessWaitsForTheTCPServerNotJustPgIsready`); the restore runs psql **without `ON_ERROR_STOP`** and tolerates exactly `role "postgres" already exists` (pg_dumpall emits `CREATE ROLE postgres` for the bootstrap superuser and the documentation calls that failure harmless), every other `ERROR:` fails it and so does a non-zero exit with no ERROR line — `RestoreCommandPrefix` is exported so the integration test identifies the restore's own stderr by it rather than by a hand-copied literal that would silently stop matching; `verify` compares two LIVE inventories — databases, roles and the per-database count of USER TABLES, with row counts deliberately left out because they need a full scan of every table, which on a real stand costs more than the migration — and then `ANALYZE`s, because a freshly restored cluster has no statistics and its first hours would otherwise look like a regression the migration caused. `PostgresMigrator.SupportsPair` states the plan's own precondition once, and since the generation counter arrived there is exactly **one rule left: the move must go forwards** (`to.Major > from.Major`). The old second rule — the two majors had to land in different VOLUMES — is gone, because `migrationVolumes` always answers the NEXT generation and every migration lands in a fresh volume by construction; **18 → 19 and 16 → 17 are now supported like any other forward pair**, and `InPlaceUpgradeProblem` was deleted along with the state it described (it used to be offered as “upgrade available” and then refused with a message about volumes, sending the operator after a disk problem they do not have). The daemon still asks before it offers anything: a pair the registry calls migratable but a migrator refuses with a REASON is reported `requires-launcher-update` and refused by both routes with `this launcher cannot migrate X → Y yet; update the launcher`; a refusal with an **empty** reason means the shared preflight has already worded it better (every backwards pair does this) and the daemon must not overwrite it. An **unparsable** tag is deliberately not one of these — the preflight's message about the tag is the one the operator needs. **When a third layout is added, ONE place changes**: the layout table behind `deps.PostgresLayoutFor`. `deps.KnownPostgresDataPaths()` enumerates that table's `PG_VERSION` paths in probe order, newest first, and the seeding probe `postgresPinFromData` walks that enumeration instead of a hand-written list. The preflight's **same-volume refusal is gone** with the state it described. It still checks the on-disk `PG_VERSION` against the pin, and measures **both** filesystems (on a macOS/Windows desktop the dump lands on the host while the cluster is built inside the Docker VM) — and because the dump and the new cluster **coexist** until the post-commit `Finalize`, measuring them independently was not enough: on one filesystem each half passed at `size + SpaceMargin` while the real peak is both at once, so a disk with ~1.2x the data free let the migration die of ENOSPC mid-`restore` on an already-stopped namespace. The preflight therefore asks the Env whether the dump and the volumes share a filesystem (`DumpSharesFilesystemWithVolumes`) and demands the **sum** (`RequiredTotalBytes`, `SharedFilesystem`) when they do. Server mode compares the real `st_dev` (`fsutil.SameFilesystem`, unix/windows halves); a **Linux desktop is assumed shared** — it cannot be proven from outside the engine, and the safe direction is obvious: over-requiring refuses a migration that would have fit and says exactly what it wanted, under-requiring is the ENOSPC above — while a macOS/Windows desktop is two disks by construction. A seam that cannot answer is treated as shared **and** reported as a warning naming why. Both surfaces render ONE combined line instead of the host/volume pair (`deps.preflight.shared`), quoting the smaller of the two free numbers and skipping a zero, since a zero means that half's measurement failed and already produced its own problem line; an existing TARGET volume is a **warning needing explicit confirmation** (`ReplaceExistingVolume`, the dialog checkbox / `--replace-existing`) and `createVolume` re-checks it, refusing rather than deleting data nobody agreed to lose (`TestExistingTargetVolumeRequiresConfirmation`, `TestCreateVolumeRefusesAVolumeThatAppearedAfterThePreflight`). Temp containers are built from the namespace's **REAL generated def** for the image in question (`GenerateDefFor` forces the pin), under another name (an override equal to the app's OWN name is refused outright — the container-name collision only guards it while the app's container exists), with `docker.LabelTemp`, published ports and network aliases stripped and the hostname following the override — a temp container must never answer as `postgres` on the namespace network (`TestAnOverriddenContainerDoesNotAnswerToTheAppByHostnameEither`) — and with `NoRestart`, because inheriting the def's `unless-stopped` policy would have Docker restart the target container after a crash or a reboot and put a second server on the new PGDATA. It runs the CONTAINER and nothing around it: **no init actions, no probes** — the generated postgres def carries one `init_db_and_user.sh <db>` per webapp datasource plus Keycloak's, so running them would pre-create every role and database and fail 100% of real restores with `role "citeck_emodel" already exists` (`TestRunAppDefRunsTheContainerAndNothingAroundIt`). `Env.Exec` returns **stdout and stderr separately** as a contract: the inventory is parsed from stdout only (a stray notice would become part of the answer) while restore errors are scanned on stderr, where psql prints them even on an exit code of 0. The scratch dump directory is **1777** for the same reason `EnsureExportDir` is — the daemon is root while postgres is uid 999, and a daemon-owned directory makes `pg_dumpall -f` die with Permission denied *after* the namespace has been stopped — and its shared parent is removed only when empty. Concurrency: `longOpKind` names the holder so a refusal is truthful, and the migration claims `d.longOp.TryLock(longOpMigration)` **explicitly, never through `tryLongOp`**, which labels its holder `longOpRequest` — a member of `tolerateLifecycleWork`, so a mislabeled migration would let namespace Start/Stop and the per-app toggles run right beside the volume rewrite the lock exists to protect. 14 of the 19 gated routes tolerate nothing; the 5 lifecycle routes (namespace Start/Stop, per-app Start/Stop/Restart) tolerate `longOpUpdatePass` and `longOpRequest` — an ordinary start must not 409 the next click and Stop is the escape hatch from a slow git pull — and are refused by a snapshot and by a migration (`TestGatedRoutesRefuseLifecycleWorkExceptTheLifecycleRoutes`, `TestLifecycleRoutesAreStillRefusedByASnapshot`). A queued Update & Start pass that loses the lock is not lost silently: it reports through `recordUpdateFailure` → the DTO's `UpdateError`, on the same error modal as every other failed pass. The migrate route accepts only **RUNNING or STOPPED** (`migratableNsStatus`): the plan's first step stops the namespace, `Runtime.Stop` merely enqueues that command, and a runtime mid-transition may never be read — so a STALLED namespace has to be stopped first. Both dependency routes lift the socket write deadline (measuring a real data volume outlives 120s), and the preflight answers a journal blocker **without touching Docker**, since probing volumes mid-migration measures a world that is being rewritten. Both halves of the "second postmaster" class are closed by the same rule: `depsmig-src` mounts the namespace's OWN data volume read-write and the `postmaster.pid` interlock does not hold across PID/IPC namespaces, so nothing may start the namespace while that container might still exist. `RollbackPostgres` therefore restarts the namespace **only when its cleanup left nothing behind** (otherwise it appends `namespace left stopped: the rollback could not remove its temp containers`, and the journal stays open for the next start to retry), and every path that starts the namespace on the user's behalf consults `rollbackBlocker` or the long-op holder: `handleStartNamespace` and the queued Update & Start pass refuse with 409 while a journal is open that no running migration owns, `startNamespaceDeferredForSecrets` (the vault-unlock start, which does not go through the route) skips with a WARN under a snapshot or a migration and KEEPS its deferral flag, and the post-pull `reloadAfterImagePull` claims `longOpUpdatePass` — `reloadMu` is no substitute, since a migration recreates containers without holding it for its whole run. Between the click and the first step the daemon publishes a **`preparing`** state (`api.DependencyMigrationStepPreparing`, `StepCount: 0`) and broadcasts it as a progress event before it builds the plan: building one runs the whole preflight, `du` included, which on a real cluster is minutes of a visibly dead button — and `StepCount: 0` is the signal a client renders as a spinner rather than as a step list. It is cleared with the refusal it belongs to. One boot-sequence change came with it and is worth knowing about on its own: the boot auto-start used to sit near the top of `Start`, **before** `Runtime.SetEventCallback` was wired, and it now runs after it (`recoverThenStartLoadedNamespace`, extracted so both recovery entry points are testable). The recovery has to precede the start, and the start has to see the callback — so the events of the boot start now reach `handleRuntimeEvent`: they land in the SSE replay ring and drive the cloud-config lifecycle hook, where before they were emitted into a nil callback and lost. Crash recovery (`deps_recovery.go`) runs **synchronously before the runtime touches anything**: a journal surviving into a fresh process means one of the temp containers still has the namespace's OWN data volume mounted, and starting the namespace over it would put a second server on one PGDATA. The namespace is handed back running only when the journal says `WasRunning` **and the rollback actually succeeded** — `RollbackInterrupted`'s `rolledBack` means ATTEMPTED, not restored (`TestBootRollsBackBeforeItStartsAndInheritsTheRestart`, `TestBootDoesNotStartWhenTheRollbackFailed`); with no journal it only sweeps a stale scratch directory. The whole path is exercised against real PostgreSQL containers by `make test-integration-deps` (`TestIntegration_Postgres17To18`, `TestIntegration_RollbackOnBadTarget`, build tag `integration`) — under **rootless Docker** the container's uid 999 maps to a subuid the test process does not own, so it needs `unshare --user --map-auto --map-root-user`, and a rootful daemon reached as a docker-group user needs `sudo`; the test says both rather than letting EACCES surface as an unrelated preflight problem. Measured end to end on a real community stand (server mode, 21 apps, a 387 MB cluster with 11 databases and 12 roles): the whole migration is **~95-100 s** of wall clock — the namespace stop and the `postgres:18` pull dominate it, the dump is 175 MiB in ~10 s and the restore ~15 s — after which the stand comes back with its databases, roles, per-database table counts, extensions and row counts unchanged. A `SIGKILL` of the daemon during `restore` on the same stand is undone by the next start in **5 s**: the journal names `start-target` as the last completed step, both temp containers and `postgres3` go, `postgres2` and the pin are untouched, and the namespace is handed back on 17.5 with an inventory identical to the pre-migration capture — the retry that follows then migrates it normally.
- **The volume a dependency's data lives in comes from a persistent COUNTER on the pin, never from the version.** `DependencyState.VolumeGen` advances by exactly one on every completed migration, returns to the recorded previous generation on a rollback, and is otherwise established only by seeding — nothing else moves it.  `deps.VolumeName(d, gen)` is the one place a volume name is spelled: `d.VolumeBase() + itoa(gen + volumeGenOffset)` with `volumeGenOffset = 1`, so **generation 1 IS the strings already on disk** — `postgres2`, `rabbitmq2`, `zookeeper2`, `mongo2` (Keycloak's base is `""`: its state lives in the namespace's PostgreSQL database and it has no volume of its own). `"2"` was never a version; it is what the Kotlin launcher happened to call its second volume layout, and starting the counter there is what keeps generation 1 byte-identical to what every launcher before it emitted (`TestGenerationOneIsTodaysVolumeNames`, and `internal/namespace/testdata/postgres17.hashinput.golden` does not move). So **`rabbitmq3` means "this namespace has completed exactly one RabbitMQ migration"**, with `rabbitmq2` still on disk beside it holding the pre-migration data. `DependencyState.Gen()` is the single normalizer (`< 1 → 1`, which covers absent, 0 and a negative out of a corrupted state file); `deps.ParseVolumeName` is the inverse and is implemented by **round-tripping through `VolumeName`** rather than re-deriving the offset, so the formula stays in one function and `postgres02` is not accepted; a namespace with no pin gets its generation from a DESCENDING existence walk capped at `MaxProbedVolumeGen = 10` (more upgrades than any of these dependencies has shipped, and a generation moves only when an operator runs a migration). `PostgresLayout` consequently lost its `Volume` field and the `PostgresVolumeLegacy`/`PostgresVolumeV18` constants: what stays version-derived for PostgreSQL is only what the IMAGE dictates — the mount path, whether `PGDATA` is set, and where `PG_VERSION` sits (`KnownPostgresDataPaths`, newest first, walked by `postgresPinFromData`). Generators read the volume through one seam, `resolveDependencyVolume`; `Runtime.SetDependencyPin` became **`SetDependencyState`**, because a caller that could set the image alone would silently reset the generation to 1 and mount the pre-migration volume on the next start; and `syncDependencyPinsUnderLock` mutates `pin.Image` only — **the image follows the container, the generation does not**. User's ruling, and it is what removed PostgreSQL's same-volume precondition: one naming subsystem, not two.
- **What the VENDOR permits is a separate question from what this launcher can do, and it has its own table.** `Descriptor.UpgradeSupport(from, to) VendorSupport{Allowed, Via}` answers only "does this dependency's own vendor document moving the data across in ONE hop"; `Via` names the **next** hop of a longer path, spelled `major.minor`, and `""` means no documented path at all. It is deliberately neither `IsBreaking` (a pair can be breaking-and-allowed — RabbitMQ 4.1 → 4.2 — breaking-and-forbidden — 4.1 → 4.3 — or not breaking at all) nor `Migratable()` (which is about the plans this binary ships). RabbitMQ's is a real **whitelist**, not "next minor": 3.11→3.12, 3.12→3.13, 3.13→{4.0, 4.1, 4.2}, 4.0→{4.1, 4.2}, 4.1→4.2, 4.2→4.3 — so 3.13 may go straight to 4.2 while 4.1 may not go to 4.3, and an unknown series is refused rather than guessed (`TestRabbitUpgradeMatrix`; a new series must be added there or its upgrade is reported as having no vendor path). Two published constraints are deliberately NOT modelled: 3.11.18 as the floor of 3.11→3.12 (no bundle has ever shipped 3.11) and "a 3.13 that already runs Khepri can only be moved blue-green" — that one is a property of the DATA, not of the versions, and the preflight's Khepri notice is where it is named. ZooKeeper has no hop table (the on-disk format has not moved since 3.5 and the vendor documents no procedure for a minor bump) but does have a **floor at 3.5**, because older data may predate `zookeeper.snapshot.trust.empty`, where a newer server reads an empty snapshot as valid state; the refusal names that property explicitly, because searching for it is what leads the operator to the vendor's own explanation. PostgreSQL, Keycloak and MongoDB answer forward-only with no path — no vendor here supports a downgrade of the data. `Migratable()` is now **postgres + rabbitmq + zookeeper**, and `TestEveryMigratableDependencyHasAMigratorAndARollback` pins the count at 3 and requires an entry in **both** registry tables. `migrators` and `rollbacks` (`internal/deps/migrate/registry.go`) are separate on purpose: a journal is written by whichever launcher started the migration and found by a possibly older or newer build, so "can I start this" and "can I finish undoing that" must not fail together.
- **A RabbitMQ or ZooKeeper upgrade rewrites a COPY of the data volume; the namespace's own volume is only ever READ.** That is the PostgreSQL plan's invariant kept by different means — for RabbitMQ it is the only rollback the vendor permits at all, since `export_definitions` carries the topology but no MESSAGES and the only supported restore is a byte copy of a stopped node's data directory onto a node with exactly the same node name. `internal/deps/migrate/copy_upgrade.go` is ONE plan shared by both, 11 steps: `stop-namespace, pull-image, create-volume, copy-volume, start-old, pre-upgrade, stop-old, start-new, post-upgrade, verify, stop-new`. Everything per-dependency is one struct, `CopySpec` — `ID`, `WaitReady`, `Inventory`, the optional `PreUpgrade`/`PostUpgrade` hooks, and the data `TempEnv`/`HostAlias`/`EnsureDirs`. `validate()` refuses three of them: an empty `ID`, a nil `WaitReady` (every step would race a booting server) and a nil `Inventory` (a verify step that verifies nothing). The invariant is **structural, not careful**: inside the run the source volume is derived once, journalled, and then touched by nothing but the copy step (`CopyPreflight` names it too, but only to check that it exists and to measure it), and every container comes from one `tempDef` that always passes `VolumeGen: r.toGen`, so nothing can land on the source even by accident — which is what keeps rollback equal to "delete what we created", i.e. `j.CreatedVolume` plus the temp containers `depsmig-src`/`depsmig-dst` and nothing else, reported in full rather than stopping at the first failure, idempotent so crash recovery can re-run it, and restarting the namespace only when the cleanup left nothing behind. The "before" inventory is read from the COPY, not from the namespace's live container, so the invariant is total rather than nearly total. `pull-image` runs before anything irreversible: an unreachable registry then costs a stopped namespace and nothing else. `create-volume` refuses an existing target **before** it journals anything (a journal claiming somebody else's volume would have the rollback delete it) and re-checks at the step, since a volume can appear after the preflight. The journal gained `ToVolumeGen` — recorded when it is OPENED, because the commit is a single atomic write of (image, generation) and must not re-derive the generation from a world the migration has been rewriting, and `CreatedVolume` cannot stand in for it: parsing a generation back out of a name would make the commit depend on the naming scheme staying invertible forever — and `SourceVolume`, which `MigrationResult.OldVolume` then reports so the operator knows which volume they may reclaim. The step ids deliberately do NOT reuse the PostgreSQL plan's `start-source`/`start-target`: they are locale keys, and a container running the old image on a copy is not "the current database". `Inventory.Diff` returns **problems AND notes** because ZooKeeper's ephemeral nodes belong to client sessions and expire while the migration runs: "every difference is a failure" would fail every real migration, "no difference is a failure" would not notice a lost patch-result marker. The shared set arithmetic makes the asymmetry the rule — **missing ⇒ problem, appeared ⇒ note**, since nothing writes to the copy but the upgrade itself — naming at most 20 items with an exact count for the rest. Readiness is shared (`copyReadyTimeout` 5 min, poll 2 s — measured against a 4.2 node booting in under two minutes and a ZooKeeper in one to two seconds, with the margin for a cold host still unpacking a layer) and `execOK` demands `err == nil && code == 0`, because a probe that cannot tell "the command failed" from "the command could not be run" would call a broker ready the moment Docker stopped answering. The `Env` seam grew `DependencyState`, `CopyVolume`, `EnsureVolumeDirs`, `ImageExists`, and both `RunAppDef` and `GenerateDefFor` now take the full `deps.DependencyState`/`TempContainerOpts` rather than an image string and a name. `CopyVolume` must preserve **ownership**, mode and mtimes — the data belongs to the image's uid (rabbitmq 999, zookeeper 1000, postgres 999) and a root-owned copy is a broker that will not start — and it may run for hours, so no implementation may bound it by a `cat` timeout. `EnsureVolumeDirs` exists because a temp container runs no INIT CONTAINERS and ZooKeeper's generated def has one whose whole job is `mkdir -p /zkdir/data /zkdir/datalog`. `TempContainerOpts` lives in `deps` rather than `migrate` for a mechanical reason: `migratetest.FakeEnv` must name the type to implement `migrate.Env` and cannot import `migrate` (migrate's own in-package tests import migratetest — that would be an import cycle in the test binary). **A ladder is walked on ONE copy.** The copy is taken once and raised through every rung: `pre-upgrade → stop-old|stop-new → start-new → post-upgrade` per rung, with `pre-upgrade` running before EVERY rung and never AFTER the top one — not for symmetry, but because RabbitMQ's `PreUpgrade` enables the feature flags the node about to start refuses to boot without, so it has to run on the node BELOW each rung: 4.1 → 4.2 → 4.3 runs it twice, once on 4.1 and once on 4.2, and never on 4.3 itself, since there is no rung above it left to prepare for. The generation grows by exactly **one** whatever the ladder's length, the source volume is still only ever read, and the rollback is still "delete the copy". The inventory is captured once at the bottom and compared once at the top; comparing at an intermediate rung would measure work a rung legitimately did. **PostgreSQL walks the ladder in one migration too**, but by its own means: it needs a LIVE cluster of each version, so it dumps and restores per rung and reuses ONE scratch volume (`<next generation>-hop`, journalled as `ScratchVolume` so the rollback removes it) for every intermediate — the peak on disk is source + one cluster + one dump, and only the final cluster lands in the next generation.
- **RabbitMQ's node identity is the trap, and both halves of the pin are mandatory.** The broker derives its node name from the container hostname and the data path CONTAINS it (`/var/lib/rabbitmq/mnesia/rabbit@rabbitmq`), while `buildContainerConfig` sets `Hostname` to the effective — i.e. overridden — name. Measured: a temp container named `depsmig-src` boots a fresh EMPTY node inside the copy, reports healthy, shows `guest` alone in `list_users` and grows a second `rabbit@depsmig-src` directory beside the real data. So the spec pins `RABBITMQ_NODENAME=rabbit@rabbitmq` **and** a `HostAlias` of `rabbitmq → 127.0.0.1`: the environment names the node (and with it the data directory), the `/etc/hosts` entry resolves that name's host part, without which Erlang refuses to boot with `epmd error for host rabbitmq: nxdomain` (measured). `HostAlias` is deliberately not a hostname override — moby registers a container's hostname as a DNS name on a user-defined network, so overriding it would make a temp container answer to the app's own name on the namespace network, whereas `/etc/hosts` is container-local. Readiness is three gates in order and never a port probe (`ping` succeeds and 5672 is open long before the node has booted): `test -e /var/lib/rabbitmq/.erlang.cookie`, then `rabbitmq-diagnostics -q check_running`, then `check_port_connectivity`. The **cookie gate is not politeness**: `docker exec` lands as ROOT (the image declares no `USER`; it drops privileges inside its own entrypoint) with `HOME=/var/lib/rabbitmq`, and every Erlang tool CREATES `$HOME/.erlang.cookie` mode 0400 when it is absent — while the entrypoint's repair (`find /var/lib/rabbitmq ! -user rabbitmq -exec chown rabbitmq {} +`) runs once, before the server, so a cookie that appears after it is never chowned and the broker (uid 999) dies with `Error when reading /var/lib/rabbitmq/.erlang.cookie: eacces` → `Kernel pid terminated`. Measured identically on 4.1.2-management and 4.2.9-management: the broker writes that cookie ~1.3 s after container start on an idle host, an exec inside that gap kills it deterministically (7/7 at ≤0.45 s), and `startTemp` probes ~0.2 s in. It is a gate rather than a fixed delay because the same cookie was also measured appearing **7.3 s** in on a starved host. **Feature flags are enabled on BOTH sides of the upgrade** (user's correction to the plan): before, on the old image, because a required flag left disabled makes the new node refuse to start — and for a ≥4.3 target `check_if_any_deprecated_features_are_used` runs first, so a refusal has changed nothing at all — and after, on the new image, which is what the upgrade was for. The deliberate consequence: on a ≥4.2 target `enable_feature_flag all` now includes `khepri_db`, so the irreversible Mnesia→Khepri migration happens there. That consequence is accepted **silently, with no warning of its own**, because of WHERE it happens — on the copy, with the source volume left exactly as it is — and because Khepri is mandatory for 4.3 anyway. The preflight used to carry a sentence about it; the user's ruling removed it (**"that you cannot simply go back after a migration is self-evident; do not frighten users with it"**), and it had also gone stale: written before the rollback existed, it sent the operator to `citeck edit rabbitmq`, which is precisely what the edit gate refuses. What replaced it is the next bullet: the gate now says where the way back is, at the moment somebody actually tries to take it. Deprecated features are checked from both sides: read-only against the namespace's own container when it is running, and only WARNED about when it is not (refusing there would make an upgrade impossible on a stopped namespace, which is most of them). The inventory is users, vhosts, exchanges, bindings, policies, parameters and per-queue `durable/type/messages`, all as the broker's own raw text (parsing a value the launcher does not understand would produce a broken inventory) — **message counts are in it for the reason the whole plan exists**, since a topology-only comparison would pass a migration that moved every queue and lost their contents, and a count that moved in EITHER direction is a problem because nothing is connected to either node. Vhosts are read first and drive everything else, so a lost vhost is one clear problem rather than a hundred missing queues. Two measured parsing rules: `list_users` takes no column arguments at all (a real 4.1 broker answers "Error (argument validation): too many arguments"), and rows are split without ever trimming **leading** whitespace, because the default exchange really has an EMPTY name — its row is `"\tdirect\ttrue"` — and a `TrimSpace` would silently read its type as its name on every namespace. The same root-exec hazard reaches the GENERATED app, and the answer there is a **measured margin, not a gate**: `generateRabbitMQ`'s startup probe execs `rabbitmq-diagnostics check_running -q`, `InitialDelaySeconds` is unset (default 5 s) and must stay that way — an exec at ≤0.45 s killed the broker 7/7, at ≥0.78 s never, and the first probe fires ~5 s in, a ~10× margin that held at `--cpus 0.25` and `--cpus 0.1` (8/8 with the cookie still `999:999`). Do not set it to 0 and do not front that probe with an un-delayed one. The wider alarm was **disproved** rather than fixed: a fresh volume is the one case that always works, the EACCES needs a volume that already holds another uid's 0400 cookie PLUS a `--user` start that disables the entrypoint's own repair, and the launcher is structurally safe there — `buildContainerConfig` sets no `User` and `appdef.ApplicationDef` has no user field at all, so no bundle, workspace config or `citeck edit` patch can introduce one (4.1.2, 4.2.9 and 4.3.5 all boot clean; their entrypoints are byte-identical).
- **ZooKeeper keeps a migrator even though 3.8 ↔ 3.9 was measured to be a plain container swap.** The experiment (`zk-experiment.md`, real containers, rootless Docker): 3.8.6 reads a data directory written by 3.9.5 directly, digest matching byte-for-byte, 67 znodes, an identical `ls -R /` tree — because 3.9's `serializeLastProcessedZxid` appends the zxid as its own trailing section with its own seal, and a 3.8 reader stops at the digest seal and never looks at the remaining **21 bytes** (confirmed independently by size: the same snapshot is 6360 bytes written by 3.9.5 and 6339 rewritten by 3.8.6). It holds with the fallback snapshot deleted, it replays a 3.9-written txnlog past the snapshot, it survives a 3.9→3.8→3.9 round trip, and every boot in every direction reached `/commands/ruok` in **1–2 s** with `Snapshot loaded` at 10–23 ms — there is no data-size-dependent one-off cost to budget for. The migrator exists anyway (user's ruling): ZooKeeper holds `ecos/patches/<app>/results/*` — absent means every webapp re-runs a local patch — and eproc's permanent mongo-disabled marker, so the data is NOT disposable; the copy costs under a second on a volume this size, insures against a future format change, and is what makes "put the old tag back" a real rollback rather than a hope. Its spec has **no pre- and no post-upgrade hook** — starting the new image on the copy IS the upgrade, and a hook here would be a progress line for work that does not exist — and no node identity to pin, because ZooKeeper's data path is fixed by `ZOO_DATA_DIR` and carries no hostname. Readiness is the admin server (`/commands/ruok` over loopback), never the client port: the process opens 2181 first and the embedded Jetty follows, and the budget the generated app's own startup probe was written against is a **10–30 s** cold start — an order of magnitude more than the 1–2 s measured on an idle host with a warm page cache, which is exactly why the probe waits on a condition rather than on that measurement. The preflight must **not** assert that a snapshot file exists — a clean SIGTERM writes none, since ZooKeeper snapshots right after LOADING, so the durable state after a graceful stop is the transaction log (measured), and such a check would refuse every ordinary stopped namespace over perfectly intact data. The inventory is `/commands/monitor`, `/commands/dump` and `zkCli.sh ls -R /`; a non-JSON admin body is an ERROR and never an empty result, since an error page read as "a server with no znodes" is the one verdict that must never be reached by accident, and result paths are recognized by the `/` PREFIX because zkCli writes log lines to stdout that CONTAIN a path (`Client environment:java.class.path=/apache-zookeeper-…`). Only a lost PERSISTENT path fails; ephemerals are expected to be gone, because the copy is booted with no clients at all.
- **Qdrant is the vector store behind RAG, and everything special about its plan follows from its IMAGE rather than its data.** It is registered like any other dependency — minor-breaking, one generation counter, the shared copy upgrade with no pre/post hooks — because starting the new image on the copy IS the upgrade (Qdrant migrates its own storage on boot) and a single-node instance records no hostname anywhere in its data, unlike RabbitMQ (verified by reading `raft_state.json` out of a real volume: `peer_address_by_id` is empty), so a temp container under an override name reads the same storage and the spec needs no `TempEnv`/`HostAlias`/`EnsureDirs`. Four things about it are NOT derivable from the other plans. (1) **The image ships neither curl nor wget** (Debian bookworm, verified on v1.14.1 and v1.15.5), so the readiness probe and the whole inventory are spoken by **bash over `/dev/tcp`** — as `HTTP/1.0`, which is what forbids a chunked body that would not parse as JSON, with a non-200 status exiting non-zero so the same command doubles as the probe. Readiness is **`/readyz`** ("all shards are ready"), never `/healthz`, which answers while the collections are still loading and would have the inventory read as a server with no points in it. (2) **Qdrant publishes no tag without a leading `v`** and no floating minor at all (`qdrant/qdrant:v1.14` is a 404, like the bare Keycloak major), which is why `ParseImageVersion` learned to skip that prefix — without it `deps.Breaking` answers true for every candidate and the dependency is held back permanently — and why its `LegacyImage()` names a concrete patch. (3) **Storage compatibility spans exactly ONE minor** (data written by 1.x is read by 1.(x+1), skipping a minor is unsupported, nothing is documented across a major), so `UpgradeSupport` is arithmetic rather than a hop table, and a skipped minor is refused naming the one hop the operator can take now. (4) **The data is extremely sparse** — measured, a store holding three points is 739 MB apparent against 1.6 MB allocated, a ratio of 455 from the 32 MiB write-ahead log Qdrant preallocates per collection — so `tar -S` is not an optimisation here, and the preflight's `max(apparent, allocated)` legitimately demands ~1.5 GB free for an index that occupies megabytes. The inventory is collections → `points_count` plus aliases → collection, and deliberately NOT the collection's `status` or `config`: across 1.14.1 → 1.15.5 the same data reads `green` then `grey` (grey means "optimizations have not run yet") and the config gains `strict_mode_config`, so a verify built on either would fail every real migration over work the upgrade itself did. An alias is how the RAG service addresses a collection, so a lost or repointed one is a problem, not a note. Registering it RENAMED the volume from `qdrant_storage` to `qdrant2`: a volume outside the generation counter cannot be migrated at all, since a copy upgrade builds the next generation beside the current one — and nothing in the field paid for it, because RAG has never been released. Qdrant is also the **third conditional dependency** and the only one whose condition is not in `namespace.yml`: it exists where the RAG webapp does, so `namespaceDependencies` takes the bundle, the workspace config and the detach set, and answers through `namespace.WillGenerateQdrant`. Wrongly answering ABSENT hands an existing index to the bundle's image; wrongly answering PRESENT costs a container inspect plus a ten-generation volume walk on every load of every community stand, which is the bill the keycloak filter exists to stop paying. The real pair is exercised end to end by `TestIntegration_Qdrant114To115` (`make test-integration-deps`), which is also the only test that runs the bash transport for real.
- **A rollback is one atomic pin write, one step deep, and deliberately NOT journalled.** The target lives on the PIN — `DependencyState.PrevImage` / `PrevVolumeGen`, written by `CommitMigration` in the same single write that moves the pin — and not on `MigrationResult`, because there is one result slot per NAMESPACE and migrating a second dependency would erase the first one's rollback offer while its retained volume was still on disk. `WithPrevious` drops the target's own target: **17 → 18 → 19 offers a rollback to 18 and, once taken, offers nothing**, because keeping the chain would mean keeping every generation's volume forever, which is the opposite of what the launcher tells the operator to do with the retained one. `WithoutPrevious` (the rollback's own write) clears it, because there is no roll-forward: re-adopting the newer volume would silently discard everything written since the rollback. `MigrationResult.Kind` distinguishes the two verdicts that share that one slot, with migration as the EMPTY string so every state file already on disk stays meaningful. The whole sequence is: refuse unless the preconditions hold → stop the namespace → write `(PrevImage, PrevVolumeGen)` back with the target cleared → reload, starting again if it was running. **Nothing is created and nothing is deleted**, so there is no partial state a journal could describe — and a journal would be actively harmful, since one surviving a crash makes boot recovery refuse to start the namespace until it is cleared, stranding it over a write that either landed or did not. The namespace is stopped BEFORE the write, or the RUNNING re-pin hook moves the image forward and leaves the generation behind; the whole thing runs under `longOpDepsRollback`, which is in no tolerance set. `RollbackPreflight` never mutates: it refuses an unregistered dependency, a missing target, a dependency with no volume of its own (Keycloak), a recorded generation that is not OLDER than the running one (only a corrupted state file or a wrong-sided commit can produce that, and both are better refused than described confidently and wrongly), a retained volume that is GONE — a state the launcher itself creates by telling the operator they may reclaim it — and, for PostgreSQL only, a retained volume whose `PG_VERSION` does not match the version the previous image names — plus two I/O arms, since a volume check or a marker read that FAILS is refused rather than assumed. RabbitMQ and ZooKeeper write no version marker, so that check is skipped rather than inventing a path that would refuse every rollback of those two. Warnings are printed only when there are no problems (printing consequences beside a refusal would describe a rollback that is not going to happen) and name all four: a target image not present locally (checked, never enforced — `ImageExists` cannot tell "not here" from "I could not ask"), which data comes back, that everything written since is frozen in the newer volume and will not be read again, and that there is no roll-forward. Progress reuses the MIGRATION's channel with three steps (`stop-namespace, switch-generation, start-namespace`) so the CLI renderer and the dialog work unchanged and only the title differs; `stop-namespace` is deliberately the same id both migration plans use, since a second spelling would be one sentence translated twice in 16 files. This ends the "the original volume is only ever read" guarantee **in the open, with a confirmation** — that guarantee is a property of a migration for the duration of that migration, not a promise never to write to a retained volume again, and a rollback cannot even start while a journal is open.
- **A backwards bundle is its own status, and patch-level backwards moves are still applied silently.** `deps.MovesBackwards` is a component-wise numeric comparison of `(Major, Minor, Patch)` — not a string compare, which would order 4.10 below 4.9 — and is deliberately NOT per-descriptor — which components make a move breaking differs (majors for PostgreSQL, minors for RabbitMQ), but 4.2.9 → 4.1.8 goes backwards for everyone. `deps.BundleOlder` is the CONJUNCTION of that with `Breaking`, so a bundle reverting a patch bump applies exactly as it always has (user's ruling: only format breaks are held) and an unparsable tag on either side answers false, because nothing orders it and claiming the bundle went backwards would be an invention. It gets its own status because the migrator refuses a downgrade with an EMPTY reason, so the old code fell through and called it "upgrade available"; `bundle-older` is asked FIRST, before "can we migrate it", since "update the launcher" is untrue forever for a downgrade. Two notices, built in one place: `BundleOlderNotice` when there is no rollback target — it must not borrow the words of a held-back upgrade, and above all not `citeck deps upgrade`, which would refuse the operator at the end of a trip the message sent them on — and `BundleOlderRollbackNotice` when the offered version is the one this namespace migrated FROM, where the retained volume is still on disk and `citeck deps rollback <id>` is the real answer. The plan's six-value `Move`/`Classify` machinery was **overruled and does not exist**; `Breaking` keeps today's semantics exactly, and the edit gate is unchanged.
- **A pin the launcher INVENTS may float; an image the launcher CHOOSES TO RUN may not.** `LegacyImage()` is a reference derived from data whose version could be read only as a major, so a concrete patch there would claim more than is known — and a patch tag that does not exist in a private registry is a container that cannot be pulled. A generator FALLBACK is the opposite: it is what the launcher runs when nothing else says otherwise, so it must be pinned. Two were not. `postgres:18` was the only floating tag the **dependency generator** had ever emitted (it arrived with the dependency-pin feature) and it matters most exactly where it is guaranteed to be re-resolved — the migration engine's `pull-image` step pulls unconditionally, so a floating tag would resolve afresh at the moment the data is being moved. It was **withdrawn before release rather than merely pinned**: the launcher's own default stays `postgres:17.5`, the value every release since Kotlin 1.3.9 has shipped, and a version bump is a BUNDLE's decision ("давай наверное всё-таки дефолт оставим на старой версии, а повышать будем через бандлы" — `community-rc` already declares 17.11). Nothing about PostgreSQL 18 was removed with it: the 18 layout, the 17→18 migration and the pin/seed machinery all stand, and 18 arrives from a bundle that declares it or from a completed migration. The floating default was also the only thing that could raise an upgrade banner on a stand whose bundle names **no** postgres at all — reported from the field as `postgres:17.5 → postgres:18.6`, a candidate that existed nowhere but in that one line (`TestABundleThatNamesNoPostgresOffersNothing`, `TestABundleThatNamesNoPostgresListsUpToDate`). Because `image=` is part of `GetHashInput`, a default that does not move recreates nothing, and the default def is **byte-identical** to a 17.5-pinned one — which is why `TestPostgresDefaultDefIsTheDefAPinned17NamespaceAlreadyRuns` shares `postgres17.hashinput.golden` instead of carrying its own (a second file holding the same bytes could only drift; `postgres18.hashinput.golden` went with the bump). `rabbitmq41` and `zookeeper39` are the volume-generation goldens and are unaffected. The data volume is untouched either way, since the name comes from the generation. Two images outside the gate still float and are deliberately left alone here, because neither is dependency DATA the launcher pins: the observer's own `postgres:18` and alfresco's `postgres:9.4` (`generator_webapp.go`), both routed around `resolveDependencyImage` on purpose. The second registry pin was worse: **`keycloak/keycloak:26` is a 404 on Docker Hub — Keycloak publishes no bare-major tag at all** — so that invented pin named an image that could never be pulled, and it only reaches a container when Keycloak is HELD BACK, i.e. on a stand whose Keycloak then cannot start. It is now `26.4`, which floats over the patch only (`majorBreaking` calls that harmless) and is the minor both the Kotlin 1.3.9 launcher and every Go 2.x release have emitted, so it is also the truthful answer to "what has this namespace been running". The fix is **forward-only**: seeding runs only where there is no pin, and a table of known-bad invented pins would be a new kind of thing to maintain for a state that already fails with an actionable pull error. `TestLegacyImagesFloatOnlyOverNonBreakingComponents` is the general rule — parse `LegacyImage()`, max out every component the tag OMITS, assert the result is not breaking — which is also why PostgreSQL's must stay a bare major (`postgresPinFromData` derives it as `"postgres:" + major` from `PG_VERSION`).
- **`VolumeSize` answers `max(apparent, allocated)`, and `tar -S` is an efficiency, not a licence to require less.** Both were found by the real-Docker runs and are invisible to every fake. Neither reading is an upper bound on its own: allocation under-reads sparse data by up to 4096× (a 64 MiB ZooKeeper txnlog measured as 16 KiB) and apparent under-reads dense data, because filesystems round to blocks. The two modes had silently disagreed — server mode measured apparent, desktop measured allocation — so the same ZooKeeper volume was 64 MiB to one preflight and 16 KiB to the other, i.e. the preflight under-required space; whether holes survive at all is a property of the DESTINATION filesystem, which the launcher cannot see. Over-requiring refuses a migration that would have fit and says exactly what it wanted; under-requiring is ENOSPC on an already-stopped namespace. The copy itself uses `tar -Scf - | tar -Sxpf -` through the utils container with the source mounted `:ro`, because without `-S` the same txnlog expanded 4096× on the way in. Its verification compares **file count plus summed APPARENT size**, never `du -sk`: block ALLOCATION failed every real RabbitMQ copy (36 files / 252 KiB against 36 files / 256 KiB — identical content, fewer blocks, because Mnesia's `schema.DAT` has holes), and the utils image's busybox `du` has no `--apparent-size`, so the size comes from `find /src -type f -exec stat -c %s {} + | awk`. A copy upgrade also sets `PreflightResult.SpaceChecked` rather than inferring "measured" from a non-zero host requirement, because it legitimately requires zero bytes on the host; every renderer owes the same rule of skipping a half whose requirement is 0.
- **`GetHashInput` stability** is a hard compatibility contract across versions — changes require migration
- **Volumes content hash covers directory mounts**: `computeVolumesContentHash` (feeds `GetHashInput`) hashes every bind-mounted file's content so an edited file recreates the container. A mount whose source is a **directory** (e.g. Spring webapps' `./app/<app>/props:/run/java.io/spring-props/`) is expanded via `expandDirMountKeys` to every generated file beneath it — without this, editing `application-launcher.yml` (or any dir-mounted props file) leaves the hash unchanged and the running app never picks the edit up. Restores Kotlin parity (`NsRuntimeFiles.fillFilesForAbsPath`). Two independent editors: `citeck edit <app>` (+`--reset`) edits the **ApplicationDef** (`/apps/{name}/config`); the mounted-**file** editor (`/apps/{name}/files/...`, incl. application-launcher.yml, reset via `/files/reset`) is exposed on the CLI via `citeck edit <app> --file <path>` (and in the web/desktop config editor). `citeck status` marks apps with either kind of edit with a `*` (from `AppDto.Edited` / `EditedFilesCount`).
- **Secrets**: AES-256-GCM per-secret encryption via `SecretService`; the master-password KDF is **Argon2id** for new envelopes (legacy PBKDF2 envelopes stay readable via a stored KDF discriminator — a hard compat contract; server mode auto-unlocks with the default password through the same dispatch); system secrets (JWT, OIDC, admin password, citeck SA) via `resolveOneSystemSecret` pattern
- **A pending 1.x secrets blob is as unreadable as a locked vault, and BOTH secret guards must say so.** `shouldDeferStartForSecrets` and `RegistryAuthBanner` keyed on `encrypted && locked` / `status.locked` alone, and missed the one state that exists only on the first boot after a 1.x → 2.x migration: the migrated secrets are still a single opaque blob awaiting the master password, so `SecretService` is neither encrypted NOR locked — it is EMPTY, and `locked` reports **false**. The namespace therefore auto-started, its private-registry pulls failed auth, and the registry-credentials dialog opened on top of the master-password prompt — the exact dead end the gate was written to prevent (picking a secret needs a vault that does not exist yet; saving a token answers 423). A migrating user was asked for a registry secret first and the master password second. The gate now takes `pendingKotlinImport` (`hasPendingKotlinSecrets` → a non-empty `store.GetSecretBlob()`) and defers on it **on its own, without consulting the vault** — at that point there is nothing in it to consult — and the banner's guard is `locked || hasPendingSecrets`. Consequence that must not be dropped: the resume then has to happen in **`handleSubmitMasterPassword`** (import) as well as `handleUnlockSecrets` (unlock), or the deferral is permanent and the namespace never starts after the password is entered; both call the shared `startNamespaceDeferredForSecrets`, after `rebuildAuthCaches` so the pull sees the credentials. Note the call site boxes `*storage.SecretService` into the interface only when the pointer is non-nil — a typed-nil passes `vault != nil` and panics inside `IsEncrypted()`.

One real store carried 11. `importNamespaces` now returns a `migratedNamespaces` index of what it actually wrote and the state import skips anything absent from it. The index is keyed on a **lower-cased workspace id** because Kotlin's `WORKSPACE_ALIASES` gives the legacy `default`/`global` workspaces an upper-case alias for the ENTITY scope only (`entities/DEFAULT!namespace`) while the runtime-state repo key keeps the real id (`default:<ns>`) — matching those exactly would file the state under a second, config-less `default` row, i.e. a phantom AND a real namespace robbed of its detach/bundle state.   - **`VersionedValueType` picks its wire shape ONCE PER PAGE, not per entry** (`org.h2.mvstore.tx.VersionedValueType#write(buff, storage, len)`), and getting that wrong is what silently gutted every 1.x → 2.x migration up to 2.11.1. A leaf's value block is `byte mode` followed by either the values back to back (`mode == 0`, the fast path taken whenever every value on the page is committed and non-null) or, per entry, `varLong(operationId)` plus — when that id is non-zero — a flags byte and the current (`&1`) / committed (`&2`) values. The reader instead assumed a per-ENTRY operation-id varint and no mode byte, which decodes entry 0 perfectly and then reads the first byte of entry 1's own length prefix as a non-zero operation id and skips it, and the next, and the next: **exactly one entry per leaf page survived**, with no error, no `readLoss` tally and no warning — a user with 19 namespaces migrated one. On a slow-path page it was worse than lossy: the `0x01` mode byte was eaten as entry 0's operation id, so every value landed under its PREDECESSOR's key and one namespace's config was written under another's name. Keys were never affected (`StringDataType` has no bulk header), which is why the store looked healthy from every angle that counts maps rather than rows. Two consequences for how this package is tested: the synthetic stores in `mvstore_test.go` encoded the same wrong belief as the decoder, so they agreed with it and passed — the fixture that pins this is `testdata/txnstore_h2.db`, written by **H2 itself** via `MVStore` + `TransactionStore` (regenerate with `testdata/gen/Fixture.java`) — and `TestRealStoreCorpus` could not have caught it either, because it asserts that nothing was REPORTED lost and this loss reported nothing. An uncommitted entry resolves to its **committed** value: `TransactionStore.init()` rolls open transactions back on open, so that is what 1.x itself would have shown. Values are `ByteArrayDataType` (`varInt(byteLength) || bytes`, see `Database.kt` `RepoImpl.set`) — a byte count, NOT `StringDataType`'s character count, which would truncate every Russian namespace name.
  - **`Chunk.len` is a BLOCK COUNT, not a byte length** (`org.h2.mvstore.Chunk`), and H2 emits no `blocks` attribute. Reading it as bytes forced every chunk to a single 4096-byte block, so any page past that offset was silently skipped and the layout map came back without `meta.id` — surfacing as the useless error `layout map missing meta.id entry` on a perfectly healthy store. The chunk FOOTER position is independent on-disk proof: `chunk:19f,len:2` at byte 65536 has its checksum-valid footer at `65536 + 2*4096 - 128`.
  - **Layout and meta reads are STRICT; user-data maps stay lenient.** Layout/meta are the index of everything else, so a partial read there must be a hard error — the original silent `continue` / `return result, nil` paths are exactly why a chunk-read failure masqueraded as a missing key. Partial recovery is still allowed for user maps.
  - `header["H"]` is the MVStore **magic constant 2 in both H2 1.4.x and 2.x** — it is NOT the format version. Gate on the real `format:` field (accept 2/3; 1 gets an actionable error). Both header blocks are fletcher-verified and the higher valid `version:` wins; a torn newest chunk falls back to the newest valid one.

- **Reclone safety (`internal/git/repo.go`)**: `doPull` pulls from the on-disk `origin` remote while `doClone` clones from `opts.URL` — nothing structurally ties them together, so a reclone can cleanly and atomically install a **different repository**. - **Every JVM pool is budgeted from the container limit** (`internal/namespace/memory_budget.go`, applied by `applyMemoryBudget` in `generateWebapp`): the launcher owns the limit, so it computes `-Xmx`, `-XX:MaxDirectMemorySize`, `-XX:MaxMetaspaceSize`, `-XX:ReservedCodeCacheSize` (plus `MALLOC_ARENA_MAX=2`) instead of sizing the heap and hoping the rest fits. Motivating measurement (`citeck_eproc`, 2026-08-12): 6144 MiB limit, 5760 MiB RSS, only 2690 MiB live heap — one bounded pool out of five, and an **unset `MaxDirectMemorySize` defaults to `Runtime.maxMemory()`**, i.e. the heap size again, so a Netty leak reaches the cgroup ceiling (silent kernel OOM-kill, no Java error, no dump) long before it reaches a Java OOM. `-XX:MaxRAMPercentage` is not the answer: it sizes the heap and only the heap, every other pool takes absolute bytes. The real argument is checkability — `heap + direct + metaspace + codecache + reserve ≤ limit` is a pure function of the limit, unit-tested in microseconds with no container (`TestMemoryBudgetInvariant`). Shares: reserve 8% (min 96 MiB), heap 58%, direct 13% (cap 1 GiB, deliberately generous — this is the pool we cannot measure without NMT and a tight cap turns a working app into `OutOfMemoryError: Direct buffer memory`), metaspace 12% but **floored at 384 MiB**, code cache 6% (48–240 MiB), remainder for thread stacks + G1 side structures. **The metaspace floor is the one number that does not scale with the limit** — it is set by how much code the app loads, and a Citeck webapp loads the same 26–43k classes in a 1 GiB container as in an 8 GiB one. Measured on the live stand with `citeck jcmd <app> VM.metaspace` (2026-08-12): gateway 114 MB, transformations 126, history 165, notifications 180, emodel 184, uiserv 186, eproc 205 — while the plain 12% share handed every 1 GiB app a 192 MiB cap, which **killed eapps and integrations outright** (`OutOfMemoryError: Metaspace`, heap dumps in their export dirs) and left four more within 6% of death. The floor is 384 rather than ~256 because of what the two killed apps did once they were UNCAPPED again: after 10 h of uptime eapps settled at 197 MiB and integrations at **275 MiB** — the biggest consumer was the app that never got to report a steady state, because the cap killed it first (its metaspace is 51 341 classes at ~5.6 KiB each: Camel 4312, ru.citeck.ecos 3811, Spring Boot 2423, kotlin.reflect 1861, jOOQ 1284, Spring Data 1258, Hazelcast 2231, and only 4 MiB of runtime-generated hidden classes). 448 MiB was rejected as the floor because it pushes eproc's 2 GiB container back out of the budget. The floor's consequence is that a 1 GiB webapp cannot carry a **full** budget (its classes want ~200 MiB and its own heap 256–500); it gets the **partial** one instead (next bullet), and full budgeting starts to fit around 2 GiB, which is where a runaway pool has room to hurt anyway. Pinned by `TestMemoryBudgetRefusesLimitsTooSmallForARealWebapp` and `TestMemoryBudgetOnTheStand`. **`-Xms` is deliberately NOT set** (images add `AlwaysPreTouch`; pinning it would make 24 enterprise apps claim their whole heap during a cold start on a 16 GB box). The **smallest budgetable limit emerges from the inequality**, not from a separate constant: the guard requires `remainder ≥ heap/64 + 64 MiB` — one rule to keep true instead of two. Measured against `ComputeMemoryBudgetWith` (2026-08-13, 8 MiB steps), that guard puts the floor at **2208 MiB with nothing hand-set**, and lower when the operator has already fixed the heap, because a hand-set heap is usually smaller than the 58% share: 1184 MiB at `-Xmx256m`, 1456 at `-Xmx500m`, 2040 at `-Xmx1g`, 3184 at `-Xmx2g`, 5472 at `-Xmx4g`. So on the community stand every 1 GiB app is refused while eproc (2 GiB, `-Xmx1g`) is budgeted, and a 3 GiB app with a hand-pinned 2 GiB heap (eapps) is refused, 112 MiB short of the 3184 MiB it would need. Applied **after the edit-patch merge** (`applyJVMRuntimeDefaults` in `Generate`, to the effective defs and the baseline alike): both the budget and the heap-dump flags derive from `resources.limits.memory` and `JAVA_OPTS`, and a `citeck edit` patch can change either — computed during generation, raising `memoryLimit` from 2g to 8g through the editor would have left the heap capped for 2g. Two traps live there: the effective def of an unpatched app is a struct **copy** of its baseline sharing one `Environments` backing array (so the pass clones before mutating, or the second pass reads its own output back as operator config), and the gate is **`IsJVM`, not `Kind`** — the proxy is `KindCiteckCore` running nginx while alfresco/solr are `KindCiteckAdditional` JVMs; `IsJVM` is `json:"-"`, so it stays out of the hash and out of the editor, and `ApplyAppDefPatch` restores it like `IsInit`. **A hand-set pool does NOT disable the budget — it is carved out of it.** That is the case that actually exists in the field: namespaces set `heapSize` and nothing else, which is exactly the shape that leaves direct memory, metaspace and the code cache unbounded, so stepping aside would leave the real problem in place. The shares are therefore **weights, not fractions of the limit**: whatever is fixed by hand is subtracted first and the remaining pools split what is left in the same proportions (with nothing configured the weights sum to 100 and each share is simply a percentage — one formula covers both). `parseManualPools` reads `-Xmx`, `MaxDirectMemorySize`, `MaxMetaspaceSize`, `ReservedCodeCacheSize` and `MaxRAMPercentage` (resolved against the same container limit the JVM would use; an explicit `-Xmx` wins over it, as in the JVM) out of the effective `JAVA_OPTS`, whoever wrote it — config `javaOpts`/`heapSize`, `environments.JAVA_OPTS`, or a `citeck edit` patch. A pool flag present with an **unreadable value refuses the whole budget** (a guessed number would describe a different container), and a fixed heap that leaves too little for the rest is refused a full budget rather than capped anyway (it gets the partial one instead). **Every budget outcome logs at DEBUG** — the full budget (`Computed JVM memory budget`) and both refusals in `applyPartialMemoryBudget` (they were INFO, INFO and WARN). None of them is a finding: a partial budget is the ordinary shape of a real namespace (a 1 GiB webapp, with or without an `-Xmx`) and stops nothing (the ceilings are applied, the app starts), while the numbers themselves are **configuration that is already readable where configuration is read** — `applyJVMRuntimeDefaults` runs inside `Generate` on the effective *and* baseline defs, so they are in what `GET /apps/{name}/config` serves to `citeck edit <app>` / the gear editor, and in the container env. Each line is emitted **per app on every generation**, so at INFO a 24-app reload was burying whatever the operator actually needed to see. The two refusal spellings stay, because at debug level *why* the full budget was refused is the only part not derivable from the numbers. `JVM memory budget skipped: cannot read the configured pool sizes` stays a **WARN**: it is rare, it means NO budget was applied, and it points at an unparseable operator flag.
- **A container the full budget refuses still gets ceilings** (`internal/namespace/partial_budget.go`, `ComputePartialBudget` → `applyPartialMemoryBudget`). All-or-nothing was leaving the most common container on a stand — a 1 GiB webapp with `-Xmx256m` — with *nothing*: metaspace unbounded, `MaxDirectMemorySize` defaulting to the heap size, a 240 MiB ergonomic code-cache reservation, and their ceilings summing well past the cgroup limit, which ends in a kernel OOM-kill (no Java error, no dump). The conflation that caused it: **`budgetMetaspaceMin` was doing two jobs** — the smallest SAFE CAP for metaspace *and* the space RESERVED for it in the fit inequality. The first is set by the worst case we must not kill (275 MiB measured), the second by ordinary demand, so the partial path reserves `budgetMetaspaceExpected` (288 MiB) and splits what is left by the same weights. Rules, each of which is a test: it **never caps metaspace** (that is what killed eapps and integrations), **never sizes the heap**, and **only ever LOWERS a ceiling** — the code cache below the ergonomic default, direct memory below the heap (which is what an unset `MaxDirectMemorySize` resolves to), so nothing it emits can newly forbid an allocation that works today. It makes **no claim that the pools fit** — that claim belongs to the full budget — and the log names the pools still unbounded (`unbounded=metaspace, heap`), because reporting only what was capped reads as "this app is covered". On the stand's gateway that is `-XX:MaxDirectMemorySize=166m -XX:ReservedCodeCacheSize=128m`. **`MALLOC_ARENA_MAX=2` is now set for every JVM app with a memory limit**, budgeted or not — it was previously emitted only on the budgeted path, i.e. never for the refused class that has no other protection — but an operator's own value is never overwritten. Sized from NMT, measured on the local stack (gateway, 1 GiB, `-Xmx256m`, 45 000 requests at concurrency 100): code cache 56.5 → 74.3 MiB against its 240 MiB reservation, threads 17.4 → 23.9 MiB, **direct ByteBuffers ("Other") 4.6 → 4.9 MiB** — so the code cache is the pool worth a ceiling and direct memory is hygiene, not protection; `partialCodeCacheMin` is 128 MiB because the weighted share alone lands on 76.8 MiB against a 76 MiB measured peak, which is a coincidence rather than headroom. NMT also showed **~120 MiB of anon memory it cannot see at all** (658.4 MiB anon vs 536.7 MiB NMT-committed); `/proc/<pid>/maps` had **zero** 64 MiB glibc arenas, so that gap is not arena bloat and `MALLOC_ARENA_MAX` is insurance against a known pattern rather than a measured win here.
- **The generator declares the container LIMIT, never a heap.** Config may size a heap (`heapSize` / `javaOpts` in the workspace or namespace config → `-Xmx`, honored as operator intent and carved out of the budget), but the launcher must not invent one for itself — a hand-written `-Xmx` is precisely the "one pool sized, the rest unbounded, no ceiling" shape the budget exists to remove. The two places that did are `generateAlfresco`: alfresco carried a hardcoded `-Xms4G -Xmx4G` **with no memory limit at all** (so the budget could not run, and the JVM's own ergonomics would otherwise take 1/4 of the HOST's RAM), and alf-solr `-Xms1G -Xmx1G` against a **1g** limit — a heap the exact size of its own container, i.e. a guaranteed kernel OOM-kill (no Java error, no dump) once metaspace, the code cache and thread stacks land on top. Both now declare only `resources.limits.memory` — alfresco **8g** (derived heap 4371m) and alf-solr **2560m** (derived heap 1366m) — each chosen so the DERIVED heap is not smaller than the value 1.x pinned, with solr's limit deliberately above the 2208m budget floor so a change to the formula cannot silently drop it onto the partial path. Pinned by `TestAlfrescoHeapComesFromTheBudgetNotTheGenerator`. One-time consequence: both containers are recreated once, since `GetHashInput` covers env and resources.
- **A configured `heapSize` becomes `-Xmx` and nothing else** (`heapFlagFor`, `internal/namespace/generator_webapp.go`, used by both config layers — the workspace `defaultWebappProps` / per-app `defaultProps` merge in `applyWebappDefaults` and the namespace `webapps[name]` override). 1.x wrote `-Xmx<heapSize> -Xms<heapSize>` (`NamespaceGenerator.kt:356`) and the Go port inherited it, but the config field is a **maximum** — nobody asked for a pinned initial heap, and the runtime images add `-XX:+AlwaysPreTouch`, so an enterprise namespace had 24 JVMs claim AND touch their whole heap simultaneously during a cold start on a 16 GB box. Same rule as `MemoryBudget.JavaOpts`, which emits no `-Xms` either: the launcher sizes **ceilings**, it does not reserve memory up front. An `-Xms` an operator writes themselves in `javaOpts` / `environments.JAVA_OPTS` / a `citeck edit` patch is untouched (and `parseManualPools` reads only `-Xmx` for the heap, so the budget is unaffected either way). Pinned by `TestConfiguredHeapSizeBecomesXmxOnly` (both layers) and `TestMemoryBudgetDoesNotPinInitialHeap`. Recreates every JVM webapp once.
- **Citeck webapps dump the heap on OOM out of the box** (`HeapDumpJavaOpts`, appended to `JAVA_OPTS` by `applyHeapDumpOnOOM` — after every other JAVA_OPTS writer, since it appends): `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/citeck/export -XX:HeapDumpGzipLevel=1`. Gzip is load-bearing (an uncompressed dump is the size of the heap, written exactly when the box is already under pressure), and an explicitly configured `HeapDumpPath` in bundle/namespace `javaOpts` always wins. **HotSpot refuses to overwrite an existing dump** (`Unable to create …: File exists` — measured) and `HeapDumpPath` has no timestamp placeholder (only `%p`, useless since a fresh container gives the JVM the same pid), so without help the FIRST OOM would be the only one ever recorded. `RotateHeapDumps` therefore runs at **container start** (`runtime_workers.go`, before create — every restart path passes through there, while a reload-only hook would miss the crash loop worth capturing): it keeps only the NEWEST dump, deletes the rest, and moves the survivor to `<name>-<UTC stamp>.hprof.gz` so the write path is free. Keeping one is what makes a crash loop safe on disk (a dump is heap-sized even gzipped); deletion happens only while the newest dump is already on disk, so there is never a window with no evidence, and an already-stamped survivor is not re-stamped (the stamp records when the dump was TAKEN). **This does not catch a container OOM-kill**: the cgroup limit is enforced by the kernel against the whole container and the JVM never runs a handler, so only a Java-level `OutOfMemoryError` produces a dump. **A flag the JVM does not know is fatal, not ignored** — `-XX:HeapDumpGzipLevel=1` on temurin-1.8.0_482 gives *"Unrecognized VM option" / "Could not create the Java Virtual Machine"* (measured), and `GC.heap_dump -gz=1` there fails the whole jcmd with *"Unknown argument … in diagnostic command"*. `alfresco` and `alf-solr` are pinned to **Java 8** and are not being updated, so they carry `appdef.JVMMajor = 8` (`json:"-"`, like `IsJVM`: it describes the image, stays out of the hash and the editor, and `ApplyAppDefPatch` restores it), and `HeapDumpJavaOptsFor` / `SupportsGzipHeapDump` drop the gzip flag and the jcmd `-gz=1` for them — an uncompressed dump instead of a container that never boots, with `RotateHeapDumps` already handling both `.hprof` and `.hprof.gz`. `JVMMajor = 0` means "current" and is what every Citeck webapp uses. The floor `GzipHeapDumpMinJVM = 17` is deliberately above the documented JDK 15 (JDK-8237354): guessing it too LOW costs an app that will not start, too HIGH costs only compression, and 17 is the oldest release the flag was actually verified present on. All four memory-budget flags (`-Xmx`, `MaxDirectMemorySize`, `MaxMetaspaceSize`, `ReservedCodeCacheSize`) exist in Java 8 — verified on the same JVM — so budgeting these two apps is unaffected. Pinned by `TestJava8AppsGetNoFlagFromANewerJVM`.
- **The pre-restart thread dump does NOT use `jcmd`** — the runtime images ship a JRE (`/opt/java/openjdk/bin` has `java jfr jrunscript jwebserver keytool rmiregistry` and nothing else), so the old `jcmd 1 Thread.print` recorded `(jcmd failed: exit=127)` on every restart, and it was wrong twice: **PID 1 is `sh -c /entrypoint.sh`, not the JVM** (java is a child — pid 7 in a measured container), so a JDK image alone would not have fixed it. `captureThreadDump` (`internal/namespace/reconciler.go`) tries three mechanisms in order: (1) the attach protocol from the host via `internal/jvmattach` — nothing needed inside the container, dump kept out of the app log, Linux-only and uid-gated; (2) the same protocol spoken **inside** the container by the embedded attach class (`runAttachInContainer`, `internal/namespace/jvm_attach.go`) — `CopyFileToContainer` → `java -cp /tmp CiteckAttach 0 threaddump` → `rm -f`, run by the image's own java, which also returns the dump directly and covers the case (1) cannot reach (macOS/Windows desktop, remote `DOCKER_HOST`); (3) SIGQUIT to the JVM inside the container, which works everywhere Docker does but delivers the dump through the container's stdout — so that path widens the log tail to `diagLogTailWithDump` (a 132–225-thread dump is 1500–2500 lines; at 500 the file would hold the dump's middle and neither its start nor the failure). Details of (2) that are load-bearing: the attach verb is HotSpot's own **`threaddump`**, not the jcmd spelling `Thread.print` (measured: *"Operation Thread.print not recognized!"*); the class is copied **non-executable, mode 0644, uid 0** (`tarSingleFile` in `internal/docker/client.go` — the tar header, not the API call, carries mode and ownership) so every image user can read it and the launcher never drops an executable into a running production container; it is removed in a `defer` on a `context.WithoutCancel` timeout so a timed-out diagnostic still tidies up, but a copy that never landed spends no exec on `rm`; and an exit-0 run with **empty output is treated as a failure**, since returning it would replace a working SIGQUIT capture with an empty dump. When both (2) and (3) fail the error names both — the diagnostics file is all its reader gets. The in-container search matches on `readlink /proc/<pid>/exe`, **never on the cmdline**: the scanning shell's own cmdline contains "java", so a cmdline match returns the shell. Vendoring `jattach` was the alternative — rejected in favour of ~200 lines of stdlib Go with no binary blob to pin, verify and re-license. Pinned by `internal/jvmattach/*_test.go` (fake procfs + fake attach listener) and `reconciler_diagnostics_test.go`.
- **Liveness tolerance is `(threshold-1) × period`, and the launcher targets ~60s of continuous failure** (`livenessGraceSeconds` / `livenessProbePeriodSeconds` / `livenessFailureThreshold` in `internal/namespace/reconciler.go`; every generated `LivenessProbe` uses the constant, pinned by `TestGeneratorLivenessTolerance`). The counter starts on the FIRST failed probe, so N failures span N-1 periods — hence 7 failures at a 10s cadence, not 6. The old value of 3 (≈20s) was too tight for the JVM apps this launcher runs: a stop-the-world pause does not refuse the connection, it just never answers, so every probe inside the pause burns its 5s timeout and counts as a failure — a `GC.heap_dump` on `citeck_eproc` tripped all 3 in 16s and the container was recreated mid-dump. Restarting a busy-but-alive app is worse than carrying a genuinely dead one for another 40s; the reconciler's crash/OOM path does not wait on probes and still catches real deaths. The **cadence** stays an operator knob (`daemon.yml` `reconciler.livenessPeriod`, default 10000 — `DefaultReconcilerConfig` used to say 30s while `periodForProbe` fell back to 10s, and since the struct is only wired in when a `reconciler:` section exists, setting an unrelated key like `reconciler.interval` silently tripled the window); the **tolerance** does not, so generated probes deliberately leave `PeriodSeconds` unset.
- **A deliberate diagnostic suspends the app's liveness probe** (`internal/namespace/liveness_suspend.go`): `SuspendLivenessProbe(app)` returns a release that callers MUST defer, and `WithLivenessSuspended(app, fn)` does that for them (release survives an error AND a panic — an app left unwatched because a diagnostic returned early is worse than the problem being diagnosed). Even the ~60s window does not cover a multi-GB `GC.heap_dump`, and the launcher is the one asking for it. The suspension is a **flag the runtime loop reads**, not a second scheduler: nothing outside the loop writes `livenessNextAt`. While it is up, `livenessPlanForAppUnderLock` skips dispatch, pushes the next probe out by a full period and clears the failure count (the app spent that time unwatched, so what is known about it starts from zero), and `handleLivenessProbeResult` drops a result that was dispatched before the diagnostic and landed during it. Suspensions are **refcounted and per-app** — a thread dump during a heap dump is normal, and dumping one JVM must not blind the launcher to the other 23 apps. Pinned by `liveness_suspend_test.go` (mutation-checked).
- **The reload PLAN resolves the proxy's TLS cert paths read-only** (`resolveProxyTLSPathsForPlan`, `internal/daemon/acme_certs.go`, called from `resolveReloadPlanInputs`). The plan re-reads the STORED `namespace.yml`, where `proxy.tls.certPath/keyPath` are empty for every self-signed and Let's Encrypt namespace — the daemon fills them in memory when it provisions the cert. Without this the plan generates an HTTP proxy and reports that `citeck reload` will strip `ENABLE_HTTPS`, `SERVER_TLS_CERT` and the 443 binding, i.e. that reloading is about to turn HTTPS off; it is not, because the real reload runs `ensureProxyTLSCerts` first. Measured on the test stand (2026-08-12): on a namespace where nothing had changed, the proxy was the ONLY app the plan wanted to recreate. The resolution obtains/renews/generates nothing — an explicitly configured path wins, a cert that is not on disk yet is left empty (the plan cannot know what an obtain would produce, and a first run recreates the proxy anyway).
- **Snapshot import**: CLI normalizes .zip suffix, validates existence via list endpoint BEFORE stopping namespace. Server validates name/file before lock acquisition. Event types: `snapshot_complete`/`snapshot_error` for both export and import.
- **install.sh** is a thin bootstrap (~260 lines): fetch + SHA256 verify + exec. All lifecycle logic (install/upgrade/rollback/SIGKILL preserve/systemd drop-in) lives in Go (`internal/cli/installer_lifecycle.go`)
- **Install wizard**: prefers `systemctl start citeck` when systemd service is installed; falls back to `forkDaemon()` when systemd unavailable
- **CloudConfigServer** skipped in server mode (webapps disable it via env)
- **Memory**: Community needs 16GB RAM minimum; Enterprise (24 apps) needs 24–32GB. On 16GB, detach non-essential apps (`citeck stop onlyoffice attorneys ai edi`) to free 4–5GB.

## CLI Conventions

- `stop <app>` detaches (persists across restart); `stop` (no args) stops all but doesn't detach
- `start <app>` re-attaches; `start` (no args) starts all non-detached
- `--detach`/`-d` for async on all commands (start, stop, reload) — don't wait, return immediately
- `--force` for destructive ops (clean); dry-run by default. `clean --volumes` scans **both** volume shapes: the server-mode volume DIRECTORIES and, since the startup sweep stopped removing data on its own, the desktop-mode Docker **named volumes** (`docker.ListAllLauncherVolumes` → `collectOrphanNamedVolumes`) — they are where a desktop namespace's PostgreSQL data lives, and nothing else reclaims them now. **Every scan is scoped to THIS installation by the workspace label** (`belongsToThisProfile`): `Client.workspace` is the workspace id in desktop mode and the EMPTY STRING in server mode, so on the ordinary developer machine that runs both, each was reading the other's live stand as orphaned — a desktop `clean --force` stopped and removed the server install's containers and network, and a server one offered every desktop stand's PostgreSQL volume for deletion, under a confirmation the operator gave about their own leftovers. It is the same rule `collectOrphanTargets` applies in the sweep, moved to where the operator is being ASKED rather than where the daemon decides alone. The named-volume scan is additionally skipped outside desktop mode entirely, because a server install owns no launcher-labeled named volume at all (it binds); `collectOrphanNamedVolumes` itself stays PURE and does not consult the mode — its caller is the gate. What no label can separate is two DESKTOP profiles (different `CITECK_HOME`), which is the sweep's limit too
- `--format json` for scripting on any command
- `--yes` to skip confirmations
- Hidden flags: `--desktop`, `--no-ui`, `_daemon` (internal)
- `edit <app>` opens the app's effective ApplicationDef in `$EDITOR` and saves the change as a per-app override patch (like `kubectl edit`); `--reset` drops the override, `--from <file|->` pipes YAML from a file/stdin. **A daemon that rejects the CONTENT (400) re-opens the editor with the operator's own text and the error in the header; every other failure keeps the temp file and prints where it is.** `openInEditor` deliberately does not own that file — it returns the path and removes nothing, and the two edit loops remove it only when nothing of the operator's is in it (a successful apply, "leave unchanged to cancel", an editor that failed before it ever produced their text). Without that, a 409 from an Update & Start holding `reloadMu`, a 503 with Docker down, or a socket dropped by a daemon restart threw away ten minutes of editing `application-launcher.yml` — the cases where the operator did nothing wrong. No status code is classified anywhere: 400 loops, everything else keeps the file, and the printed re-apply line is the real invocation (`--file`, `--no-apply` and all). Three details are each a test: the 400 loop supersedes its own temp file each round (a give-up leaves ONE file, not one per attempt); an editor that fails on a RETRY round does keep it, because the launcher seeded that round with the operator's text; and a mounted file that was saved but whose reload failed is not a lost edit — the content is on the daemon and the error already names `citeck reload` — so its copy is discarded rather than inviting a re-apply of work that already landed. Overrides persist in `state.EditedAppPatches` (server state / desktop SQLite) and recreate the container. Mirrors the desktop gear-icon config editor.
- `jcmd <app> <command> [args…]`, `jstack <app> [-l]`, `jmap <app> [-o path] [--histo] [--keep]` are the JVM diagnostics (`internal/cli/jvm.go` → `POST /api/v1/apps/{name}/jcmd` and `/heap-dump` → `Runtime.JVMCommand` / `Runtime.HeapDump` in `internal/namespace/jvm_command.go`). Named after the JDK tools deliberately: a generic `diagnostics <app>` would promise more than it delivers (not every app is a JVM), and `citeck jcmd <app> help` prints the command list **the JVM itself reports**, so nothing needs maintaining across JDK versions. No JDK in the image is required — this is the attach protocol, host-side where possible and via the embedded class otherwise; **SIGQUIT is deliberately not a fallback here** (it produces only a thread dump, only into the app's stdout, and a command the operator typed has to come back to the operator). Load-bearing details: the whole jcmd line goes into **ONE** attach argument slot (measured — `("VM.flags","-all")` in separate slots runs a bare `VM.flags` and drops the option); every command runs inside `WithLivenessSuspended`; a non-JVM app or one with no container is refused by typed errors (`ErrNotJVMApp` / `ErrAppNotRunning` / `ErrAppUnknown` → 400/409/404) **before** anything is copied or executed, answered from the generated defs when the namespace is stopped. The gate is the **container, not the RUNNING status**: STARTING / FAILED / UPDATING are exactly when an operator wants a dump — measured on the stand, `integrations` OOMed on metaspace, kept its container and sat in STARTING for two hours, so a status gate made the one app worth attaching to the one app that could not be attached to; the JVM-ness test is `IsJVM`, never `Kind`. `jmap` composes the whole flow — dump into the export dir with `-gz=1` (an uncompressed dump is the size of the live heap), then `export get --rm`; `--keep` leaves it on the daemon's host and prints the `export get` line. HotSpot reports "Unable to create …: File exists" as ordinary output with a success code, so **the file on disk is the verdict, not the prose**. Both endpoints lift the server write deadline and the client uses the timeout-free transport: a dump on a large heap outlives the 120s default (measured 3.2s for a 57 MB dump — it scales with the heap).
- `export ls|get|rm <app> [file]` is how an artifact leaves the box (`internal/cli/export.go` + `GET/DELETE /api/v1/apps/{name}/export[/{file}]`). `get` is **not destructive** — `--rm` opts into removing the file after a verified download, which is what the `jmap` flow uses; `--force` overwrites the destination; `-o` picks the path. The download is **size-verified** against the listing (a body cut short of its Content-Length is caught by the HTTP stack, but a short-and-honest body arrives as a clean, wrong-sized file — that one needs our own check) and a failed transfer deletes nothing and leaves no partial file. Output mode is **0600**, restated in the command's own output: a heap dump holds every password and personal record the process had in memory, in the clear. When the daemon runs on the SAME host the CLI skips the transfer — `os.Rename` with `--rm`, a local copy without — gated on `localExportUsable` (path reported, right size, readable, not a directory) and falling back to the download on **any** failure, so correctness never depends on the shortcut being available. Daemon side: the export dir is treated as **flat** and a name with a separator or a leading dot is refused outright rather than cleaned, and the resolved path is symlink-checked (the container can plant a link inside its own writable mount, and the daemon usually runs as root).
- `edit <app> --file <path>` edits a **mounted config file** instead (e.g. `app/<app>/props/application-launcher.yml`): stored as a delta over the generated content (`state.EditedFileEdits`) and applied via a reload (`--no-apply` to skip). `--reset` restores that file to the generated default; `--from <file|->` sets it non-interactively; `--list-files` lists an app's editable mounted files. Reuses the same daemon `/apps/{name}/files/...` endpoints as the web/desktop editor.
- `deps` (the same as `deps list`) shows every infra dependency with the version the namespace's DATA runs on, the version the bundle offers, and why a newer one was not applied — one of six statuses: `up to date`, `<version> applies on the next start` (a non-breaking bump the generator already emits), `upgrade available: citeck deps upgrade <id>` (held back, and this launcher can migrate it), `upgrade available, requires a newer launcher: citeck update` (held back and it cannot), `upgrade blocked (see the note below)` (this launcher HAS a migration and the PAIR is refused — by the vendor, like RabbitMQ 4.1 → 4.3 in one step, or by data too old to move), and `the bundle offers an older version; the data stays on <version>` (`bundle-older`). The last two carry the daemon's own English sentence in `StatusDetail`, printed verbatim BELOW the table because it runs to several hundred characters, and neither offers "update the launcher" — for a downgrade that advice is untrue forever. Below that, ONE `rollback available` line lists every offer that is still takeable; an offer whose retained volume the operator has deleted — which is what the launcher told them they could do — is deliberately not reported, or the list would argue with its own advice. It is the server-side surface of the desktop banner + Dependencies dialog, and `citeck status` prints a one-line hint when something is held back — two clauses now (`Upgrades available: …` and `the bundle offers an older version: …`) joined into ONE `see \`citeck deps\`` tail, or a namespace in both states would be told twice where to look.
- `deps upgrade <dependency>` runs the migration (PostgreSQL, RabbitMQ and ZooKeeper): it stops the namespace and, for PostgreSQL, dumps the data and rebuilds the cluster in a NEW volume, restores and verifies; for RabbitMQ and ZooKeeper it COPIES the data volume and upgrades the copy. Either way the original volume is only ever read and the switch-over is one atomic write, streaming per-step progress; `-d`/`--detach` returns immediately (the migration runs in the daemon — interrupting the command stops the output, not the work), `--replace-existing` confirms deleting a leftover target volume the preflight warned about; `--format json` prints ONE verdict object (`id/from/to/outcome/error/message/preflight`) and no progress prose, with `unknown` as its own outcome because a lost event stream is not a failed migration. Any failure rolls back to the untouched old volume.
- `deps rollback <dependency>` puts the namespace back on the version it migrated FROM, on the volume that migration retained. Exactly one flag of its own, `-d`/`--detach` — there is no `--replace-existing`, because a rollback creates no volume — and the outcomes are `refused / canceled / started / rolled-back / failed / unknown`. It stops the namespace, writes the pin back and reloads; the newer volume is kept, frozen and never read again, so everything written since the migration becomes unreachable, which is what the confirmation says. It is **one step deep**: 17 → 18 → 19 offers a rollback to 18 and, once taken, offers nothing. Progress reuses the migration's three-step channel, and `--format json` prints the same one verdict object as `deps upgrade` (`id/from/to/outcome/error/message/preflight`, with `rolled-back` as the outcome that distinguishes it — the report shape is deliberately one, so a script needs one parser). Internally the follow ALSO matches the result's `Kind`, because a namespace has one result slot and a migration's verdict must not end a rollback's follow.

## Agent Testing Guide (server-side)

Constraints and tactics for automated server-side testing on a 16GB box. Read before running lifecycle tests.

### Memory management (critical)

Enterprise bundle needs ~15GB for 24 Java apps. On 16GB server any extra container (S3Mock, MailPit, Playwright browser) triggers OOM → SSH hangs 10-20 min → recovery.

**Always detach non-essential apps BEFORE adding test infrastructure:**

```bash
# Frees ~4-5GB on enterprise
for app in onlyoffice attorneys ecom service-desk ecos-project-tracker ai edi; do
  citeck stop $app 2>/dev/null
done
# Verify: free -h → 5GB+ available
```

If SSH becomes unresponsive: wait 5 minutes (OOM killer finishes), don't retry aggressively. `systemctl stop citeck` + kill orphan containers to recover.

### Startup timing

- **Infrastructure** (postgres, mongo, rabbitmq, zookeeper): 30s–1m
- **Keycloak**: 1–2 min (5–10 min on fresh DB — realm import)
- **Webapps**: 5–15 min (Java startup + startup probes 90×10s)
- **Enterprise full startup on 16GB**: 10–15 min
- **`citeck reload`** on enterprise: 2–5 min

Don't poll more frequently than 30s. Use `sleep 120 && check` in background tasks.

### Docker network gotchas

- **Server mode**: only proxy publishes ports. `docker port <container>` returns empty for webapps.
- **Internal access**: use `docker inspect <name> -f "{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}"` to get container IP, then curl on its `SERVER_PORT` env (17022, 17026, 17027, etc. — varies per app).
- **Port numbers are not stable** — read from `docker inspect <name> --format "{{json .Config.Env}}" | grep SERVER_PORT` each time.

### Keycloak and auth

- **citeck SA** is the service account used for all launcher→Keycloak ops and webapp→RabbitMQ AMQP auth. Password in the launcher_state plain key `_sys_citeck_sa` (see `internal/daemon/system_secrets.go`). Survives snapshot import. In Keycloak it has the master `admin` role; in RabbitMQ it has `monitoring` tag + vhost `/` full permissions.
- **Admin bootstrap password**: `docker exec citeck_keycloak_default printenv KC_BOOTSTRAP_ADMIN_PASSWORD` — one-time bootstrap for master admin, not the current password after snapshot restore.
- **OIDC client secret**: `docker exec citeck_keycloak_default /opt/keycloak/bin/kcadm.sh ...` to fetch (see `internal/namespace/generator_keycloak.go`, which renders the init script from `internal/appfiles/embedded/keycloak/init.sh.tmpl`).
- **Gateway access**: OIDC token via `/realms/ecos-app/protocol/openid-connect/token` + `Authorization: Bearer <token>`.
- **Webapp direct access**: JWT HMAC-SHA256 with `ECOS_WEBAPP_WEB_AUTHENTICATORS_JWT_SECRET`. Not straightforward — prefer gateway API when possible.

### S3 testing

- **Fake-S3** (`lphoward/fake-s3`): NOT compatible with MinIO SDK used by ecos-content. Fails on `?location=` request. Avoid.
- **S3Mock** (`adobe/s3mock`): works, but `initialBuckets` env var doesn't create buckets automatically. Create manually: `curl -X PUT http://s3mock:9090/ecos-content`.
- **MinIO**: works but ~300MB RAM (too heavy for 16GB enterprise).
- **Content upload via ECOS**: `POST /gateway/emodel/api/ecos/webapp/content` with `multipart/form-data` (file, name, dir). Returns `{"entityRef":"emodel/temp-file@..."}`.
- **Set default S3 storage**: mutate `eapps/config@app/emodel$default-content-storage` with `_value?json:{"ref":"content/storage@content-storage-s3"}`.

### Background task polling

Don't poll background SSH commands with `cat output.file` every second — wastes context. Instead:
- Start the command with `run_in_background: true` (notification on completion)
- Include `sleep N && check` in the command itself
- Use short timeouts (5–15s) for direct queries when checking state

### Common test scripts (server-side)

```bash
# Quick status
./scripts/dev/ssh.sh 'citeck status 2>/dev/null | grep -c "RUNNING"'
# Use grep -c "RUNNING" NOT -cw RUNNING — ANSI colors break word boundary

# Memory check
./scripts/dev/ssh.sh 'free -h | grep Mem'
```

## TUI Testing

TUI commands (`install`, `setup`, `migrate`, etc.) are tested via tmux — it provides
screen capture as plain text and accepts key injection without modifying the binary.

```bash
# Start a session with fixed dimensions
tmux new-session -d -s tui-test -x 120 -y 40

# Launch a TUI command
tmux send-keys -t tui-test "./dist/bin/citeck install" Enter
sleep 1

# Read current screen as plain text (no ANSI codes)
tmux capture-pane -t tui-test -p

# Send keys
tmux send-keys -t tui-test Down        # arrow down
tmux send-keys -t tui-test Up          # arrow up
tmux send-keys -t tui-test "" Enter   # confirm (C-m, not literal Enter)
tmux send-keys -t tui-test "sometext" # type text

# Tear down
tmux kill-session -t tui-test
```

**Autonomous test loop:** `make build-fast` → start tmux session → capture screen →
analyze text → send keys → capture → analyze → fix code if broken → rebuild → repeat.

Cover all interaction branches: happy path, validation errors, back navigation,
cancellation, edge inputs (empty, too long, invalid chars). Fix any regressions before
moving on.

### Visual screenshots via Playwright

To verify colors, layout, and styling — not just text content:

```bash
# 1. Capture screen with ANSI escape codes and convert to HTML
tmux capture-pane -t tui-test -p -e | aha --no-header > /tmp/tui-screen.html

# 2. Wrap in a styled page (dark terminal background, monospace font)
cat > /tmp/tui-preview.html << 'EOF'
<!DOCTYPE html><html><head><meta charset="utf-8"><style>
body { margin: 0; background: #1e1e2e; padding: 24px; }
pre { font-family: 'JetBrains Mono', monospace; font-size: 14px;
      line-height: 1.5; color: #cdd6f4; background: #1e1e2e;
      margin: 0; white-space: pre-wrap; }
</style></head><body><pre>CONTENT_HERE</pre></body></html>
EOF
# (replace CONTENT_HERE with the inner content of /tmp/tui-screen.html)

# 3. Serve locally and screenshot with Playwright
python3 -m http.server 18888 &
# then: browser_navigate http://localhost:18888/tui-preview.html → browser_take_screenshot
```

**When to use visual screenshots:** checking active-item highlight color, border/glyph
rendering, truncation, layout regressions. Plain text capture is sufficient for logic
and navigation tests.

**Why not vhs:** vhs requires `ttyd` + `ffmpeg` (~200 MB) and only records fixed
scenarios — no mid-session inspection. The tmux approach allows reading screen state
at each step and reacting programmatically.

## CI/CD

> **Before every release (and ideally before any push to master): run `make check`.**
> It is a local superset of the test.yml gate below (same steps + web eslint),
> so green locally means green in the release pipeline. This is not optional for
> releases — because plain pushes to master skip CI (see below), the `v*.*.*`
> release tag is otherwise the *first* time linters/gates run, and a failure
> there fails the release after the tag is already public. `gofmt` + `go vet` +
> `go test` alone are NOT sufficient (they pass while golangci-lint / coverage /
> govulncheck / deadcode / audit can fail). Prereqs: `make tools` once, plus
> CGO + GTK3 dev headers for the deadcode gate.

GitHub Actions (three workflows):
- **Test suite** (`.github/workflows/test.yml`, reusable `workflow_call` — never triggered on its own): `go vet`, `golangci-lint v2.11.4`, `go test -race ./internal/...`, `pnpm vitest run`, full server build, linux/arm64 cross-compile check, plus the contract gates added in 2.5.x: per-package coverage floors (`scripts/ci/coverage-floor.sh`), reachable-vuln scan (`scripts/ci/govulncheck.sh`, triaged via `scripts/ci/govulncheck-allowlist.txt`), dead-code check (`scripts/ci/deadcode.sh`, built with `-tags desktop,gtk3`), and `pnpm audit --prod --audit-level high` (triage advisories via `web/package.json` → `pnpm.auditConfig.ignoreCves` / `ignoreGhsas`). Single source of truth for "is this commit good?". **`make check` mirrors this job step-for-step** (plus eslint) for local runs.
- **CI workflow** (`.github/workflows/ci.yml`): a thin trigger shim that just calls test.yml. Runs ONLY on `pull_request` → master and `push` → `release/**` branches — **plain pushes to master do NOT run CI** (the tag-time run in release-go.yml is the gate for what gets published).
- **Release workflow** (`.github/workflows/release-go.yml`): triggered by `v*.*.*` tags; runs test.yml as a gate, then builds server binaries for **all six desktop targets** — `{linux,darwin,windows} x {amd64,arm64}`, cross-compiled with `CGO_ENABLED=0` on one ubuntu runner (matrix build) — plus desktop installers and publishes the GitHub release directly (`draft: false`). Uses `go-version-file: go.mod`. Contains a MANDATORY release-signing step: signature verification is active (`internal/update/signature.go` embeds a real key), so the step fails the build if `RELEASE_SIGNING_KEY` is not configured rather than shipping an unsigned release that bricks auto-update.
- **The server tarball IS the desktop auto-update payload, on every platform.** The wrapper supervises the server binary as its daemon, so `citeck_<ver>_<os>_<arch>.tar.gz` is what `update.Stage` downloads wherever it runs (`PayloadAssetName`). Auto-update was Linux-only for exactly one reason — the release matrix built only `linux/*` — and `daemon/bootstrap.go` carried a `goruntime.GOOS == "linux"` gate to keep the macOS/Windows UI from offering an update it could not fetch. Both are gone: the matrix builds all six, and the gate is now `IsDesktopMode()` alone. Nothing in the apply path was ever platform-specific, because it **never touches the installed bundle** — the payload lands in `UpdatesDir` and `SelectDaemonBinary` hands it to the supervisor on the next spawn, so the notarized macOS `.app` keeps its seal (its signature covers the bundle, not a file in the user's data dir) and Windows never has to overwrite a running `.exe`. Two platform facts that make it work, both verified rather than assumed: a **darwin/arm64 binary cross-compiled from Linux carries `LC_CODE_SIGNATURE`** (Go's linker ad-hoc signs arm64 Mach-O itself), which Apple Silicon requires to exec at all, and it gets no `com.apple.quarantine` xattr because we download it ourselves rather than through a browser — so Gatekeeper's "damaged" dialog does not apply to the child. On **Windows the staged payload MUST be named `citeck.exe`** (`DaemonBinaryName`): `os/exec` resolves an absolute path through `lookExtensions` → `findExecutable`, which with a non-empty `PATHEXT` only tries `<name><ext>` and never the extension-less file, so a payload written as plain `citeck` stages perfectly and then cannot be started at all (`exec.ErrNotFound`) — and the health gate cannot rescue it, since nothing about the payload is *unhealthy*. `packaging/release-server.sh` names the tar member to match (via a `case`, not `[ ] &&` — that would abort the script under `set -e` on every non-Windows build). Pinned by `TestDaemonBinaryNameCarriesTheWindowsExeSuffix` and `TestReleaseMatrixBuildsAPayloadForEveryPlatformTheUpdaterAsksFor`, which reads the workflow matrix and fails if a platform we ship an installer for has no payload. `install.sh` is unaffected — it already refuses any OS but linux, so the new tarballs cannot mislead the server installer.
- **The wrapper must NOT use `WebviewWindow.Reload()` — it is a no-op on macOS.** In the pinned Wails v3 alpha, `reload()` is implemented on Linux (`webkit_web_view_load_uri`) and Windows (`execJS("window.location.reload()")`), but `macosWebviewWindow.reload` is a `//TODO: Implement` stub that logs a debug line and returns. Nothing reports the difference — the call succeeds silently everywhere — so the auto-update swap replaced the daemon underneath a page that was never told. The update dialog's only exit from its `applying` state was that reload, and it disabled Cancel meanwhile, so on macOS the launcher sat behind a modal with every button dead until the user quit and relaunched it (reported on 2.11.0, the first release to offer auto-update outside Linux — see the payload-matrix bullet below). `cmd/citeck-desktop/reload.go` drives the reload from JS instead, which is what Wails' own Windows implementation does, works on all three platforms, and keeps the SPA on its current route (which matters for the `/window/...` child windows). The UI no longer depends on it either: `UpdateDialog` polls `/desktop/update/status` and reloads when the **daemon's own `currentVersion` changes** — a condition, not a delay — with a 150s backstop (past a 60s health gate plus a 60s rollback restart) that ends in "restart the launcher" rather than a spinner, and **Cancel is never disabled**, because closing the dialog cancels nothing and was the last way out of a bricked window.

- **A booting daemon serves a LOADING PAGE for anything that is not an API call, and that is a compatibility contract with the wrapper, not a nicety.** An auto-update replaces the DAEMON only — the desktop wrapper stays whatever version the user installed — and a wrapper proxies the daemon's answer straight into the webview. So the moment 2.12.1's daemon began answering a document request with `503 DAEMON_STARTING` (the early-bind change above), a 2.12.0 wrapper running that daemon put the refusal JSON on screen and left it there: nothing reloads a webview, so the window was stuck until the user reinstalled the app. Reproduced exactly on the real pair (old wrapper + released 2.12.1 daemon, Docker blackholed so the boot window is wide): white screen with `{"error":"Service Unavailable","code":"DAEMON_STARTING",…}`, still there 30 s later. Before the early bind there was no such answer to proxy — the connection simply failed and the wrapper drew its own auto-refreshing loading page — so the fix restores that property from the DAEMON's side, where it holds for every wrapper ever shipped: `bootHandler` serves `bootLoadingPage` (a dark spinner with `<meta http-equiv="refresh">`, no words to translate — there is no locale at that point in the boot) for every non-`/api/v1` request and keeps the honest 503 for API calls. Verified on the same pair: spinner at 5 s, full UI at 25 s, unattended. The rule generalizes — **a daemon may not answer a WINDOW request with something only a newer wrapper knows how to interpret**; `cmd/citeck-desktop/assethandler.go`'s own boot-refusal fallback stays as defense in depth for wrappers that see one anyway.

- **The sweep's keep set is built from the NAMESPACES table directly, and an empty store is not an empty keep set.** Both rules exist because the same mistake — treating "this profile cannot account for it" as "it is garbage" — costs somebody else's stand. (1) `orphanKeepSet` (`bootstrap.go`) reads `store.ListAllNamespaceRefs()` (`SELECT DISTINCT ws_id, ns_id`), **never** a walk of `ListWorkspaces` → `ListNamespaces(ws)`: a namespace row can outlive its workspace row (every workspace deletion before the 2026-06-22 cascade left one behind), and a workspace-first walk cannot reach those at all. Measured on one real profile: **8 of its 11 stored namespaces** were unreachable that way, and every non-empty-workspace purge in its `daemon.log` had hit one of them. `citeck clean` builds its own keep set the same way (`knownNamespaceIDsFromStore`), for the mirror-image reason — there the hole offers a LIVE namespace's resources for deletion under a confirmation obtained on a false premise. (2) A store with no workspaces at all and no active namespace refuses the sweep outright: that is a fresh `CITECK_HOME`, a reinstall whose `launcher.db` was not kept, or a second profile opened for testing, and everything labeled on the host then belongs to somebody else's launcher. `orphanKeepSet` answers `(keep, ok)` with `ok == false` for **two different reasons that must not be merged**: a listing failed (the set would be incomplete), or the store has never held a workspace (the set would be complete and still means nothing). It is deliberately NOT widened to "the keep set came out empty": a workspace whose only namespace was deleted while its containers kept running is precisely what the sweep is for. Same asymmetry `deps_seed.go` draws between `seedUnknown` and `seedNoData`. (3) `collectOrphanTargets` skips a pair whose **workspace label is empty** as well as one whose namespace label is: only a launcher in SERVER mode writes an empty workspace (`docker/client.go` `Client.workspace`), so a desktop keep set can never contain such a pair and every server-mode stand on the host read as an orphan of its own — 8 of the 21 recorded purges on that machine were exactly that. Pinned by `internal/daemon/orphan_sweep_test.go` and `internal/docker/purge_test.go`, all mutation-checked, including cases that fail if a guard swallows the deleted-namespace case.
- **A staged payload that was never health-gated is judged at the next boot** (`GatePendingPayload`, `internal/desktop/pending_gate.go`, called once from the wrapper's start). `Stage` records the payload as `pending` **before** the swap, `SelectBest` treats `pending` as selectable, and `good`/`failed` are written in exactly one place — `applyDaemonSwap`. So everything that can happen between those two steps (the apply verb never reaching the wrapper: no control socket, transport error, its 5s timeout; a wrapper crash; the user quitting) left an entry `pending` **forever**, selected on every subsequent start with no gate and no path to `failed`. If it did not come up, the supervisor burned its restart budget, the next launch repeated it identically, and the only way out was deleting the updates directory by hand. The gate reuses the swap's own check (`Supervisor.WaitReady`, split out of `Restart`): ready in time ⇒ promote to `good` (so it is not re-judged forever), not ready ⇒ `failed` + `Restart`, which is the rollback the swap path would have done, and the webview is reloaded because it is now talking to the previous daemon. A canceled context records **no** verdict — condemning a release on the strength of a shutdown is worse than judging it one start later. `SelectBestEntry` exists for this: the caller needs the STATE it selected, not just the path. Pinned by `internal/desktop/pending_gate_test.go` (promote / fail+rollback / leave-judged-alone / no-verdict-on-shutdown), all mutation-checked.
