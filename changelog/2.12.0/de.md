## Neue Funktionen
- **Die Versionen der Infrastruktur sind jetzt an die Daten gebunden.** Ein Bundle-Update kann PostgreSQL, RabbitMQ, ZooKeeper, Keycloak oder MongoDB nicht mehr auf eine Version heben, die die vorhandenen Daten eines Namespace unbrauchbar machen würde. Der Launcher bleibt bei der Version, mit der die Daten angelegt wurden, und meldet die neue stattdessen — als Banner und im neuen Dialog **Abhängigkeiten** der Desktop-App, auf dem Server über `citeck deps`.
- **Migration von PostgreSQL 17 auf 18** — aus dem Dialog „Abhängigkeiten“ oder mit `citeck deps upgrade postgres`. Der Namespace wird gestoppt, die Daten werden exportiert, in einem **neuen** Volume entsteht ein neuer Cluster, dorthin wird wiederhergestellt und geprüft, danach schaltet der Namespace um — mit Fortschritt für jeden Schritt. Jeder Fehler wird automatisch auf die alten Daten zurückgerollt.
- **RabbitMQ und ZooKeeper lassen sich jetzt ebenfalls migrieren** — über denselben Dialog oder mit `citeck deps upgrade rabbitmq` bzw. `citeck deps upgrade zookeeper`. Ihr Daten-Volume wird kopiert und die Kopie aktualisiert, das Volume des laufenden Namespace wird also nur gelesen; bei RabbitMQ ist das der einzige Aktualisierungsweg, den der Hersteller überhaupt unterstützt.
- **Eine Migration lässt sich zurücknehmen.** `citeck deps rollback <Abhängigkeit>` oder die Schaltfläche im Dialog „Abhängigkeiten“ setzt den Namespace auf die Version zurück, von der er kam — auf das Daten-Volume, das die Migration aufbewahrt hat. Der Launcher fragt nach und benennt den Preis klar: Alles, was seit der Migration geschrieben wurde, bleibt im neueren Volume und wird nie wieder gelesen, und einen Weg zurück nach vorn gibt es danach nicht. Der Rollback geht genau einen Schritt weit, und das Angebot verschwindet, sobald Sie es genutzt oder das aufbewahrte Volume gelöscht haben.
- Das bisherige Daten-Volume **bleibt** nach einer erfolgreichen Migration erhalten. Daten-Volumes werden pro Migration nummeriert: Eine abgeschlossene Migration legt die Daten im nächsten Volume ab (`rabbitmq2` → `rabbitmq3`), das bisherige steht weiter auf der Seite „Volumes“ — löschen Sie es selbst, sobald Sie mit dem Ergebnis zufrieden sind.
- Liegt noch ein Ziel-Volume aus einem früheren Versuch vor, zeigt der Launcher dessen Größe und Version an und löscht es erst nach Ihrer Bestätigung.

## Änderungen
- Neue Namespaces werden mit PostgreSQL 18 angelegt; bestehende bleiben bis zur Migration auf PostgreSQL 17.
- Aktualisierungen von Keycloak und MongoDB werden gemeldet, aber noch nicht ausgeführt — sie warten auf eine Launcher-Version, die sie migrieren kann.
- Nicht jede Aktualisierung ist in einem Schritt möglich. RabbitMQ folgt der Upgrade-Matrix des Herstellers (4.1 → 4.3 etwa ist direkt nicht erlaubt): Der Launcher sagt das und nennt die Version, über die der Weg zuerst führt, statt eine neuere Launcher-Version in Aussicht zu stellen. ZooKeeper-Daten, die älter als 3.5 sind, werden aus einem ähnlichen Grund abgelehnt.
- Bietet das Bundle eine **ältere** Version an als die, auf der Ihre Daten laufen, sagt der Launcher das jetzt genau so, statt es als verfügbare Aktualisierung zu melden — und wenn Ihr Namespace von genau dieser Version weg migriert wurde, verweist die Meldung auf den Rollback.
- Die Version einer Abhängigkeit von Hand zu ändern, wird jetzt sauber beantwortet. Solange Daten vorhanden sind, die diese Version nicht annehmen kann, wird es abgelehnt, und die Meldung nennt den Weg zurück (das aufbewahrte Volume — oder dass es keines gibt). Ist das Daten-Volume gelöscht — der Fall, in dem es nichts zu bewahren gab —, ist es erlaubt, und der Launcher merkt sich die von Ihnen gewählte Version. Unterhalb der ältesten Version, mit der die Plattform getestet wird, wird abgelehnt, ganz gleich welche Daten vorliegen; und auf vorhandenen Daten führt der Launcher eine Abhängigkeit gar nicht mehr rückwärts, auch nicht auf einen älteren Patch.
- Starten, Neuladen und Löschen eines Namespace werden abgelehnt, während ein Snapshot oder eine Abhängigkeits-Migration läuft; die Meldung nennt den Grund.
- `citeck edit` verliert Ihre Arbeit nicht mehr: Kann der Daemon die Änderung nicht anwenden — es läuft gerade ein anderer Reload, Docker ist nicht erreichbar, der Daemon wurde neu gestartet —, bleibt Ihr Text erhalten und der Befehl zum erneuten Anwenden wird ausgegeben.
- Behoben: Ein Launcher, der auf einem frischen Profil startet — eine Neuinstallation oder eine, deren lokale Datenbank nicht übernommen wurde —, löscht nicht mehr die Container und Daten-Volumes von Namespaces, die er nicht kennt.
- Das PostgreSQL-Image, das der Launcher standardmäßig wählt, ist jetzt eine exakte Version (`postgres:18.6` statt eines gleitenden `postgres:18`), ebenso die Keycloak-Version, die er für einen bestehenden Namespace annimmt. Bei Namespaces, die diesen Standard verwenden, wird der PostgreSQL-Container beim nächsten Start nach dem Launcher-Update einmalig neu erstellt; die Daten bleiben unberührt.
