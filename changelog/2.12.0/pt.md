## Novidades
- **As versões da infraestrutura passam a estar ligadas aos dados.** Uma atualização do bundle já não pode levar o PostgreSQL, o RabbitMQ, o ZooKeeper, o Keycloak ou o MongoDB para uma versão incompatível com os dados que um namespace já tem. O launcher mantém a versão com que os dados foram criados e comunica a nova — com um aviso e o novo diálogo **Dependências** na aplicação de ambiente de trabalho, e com `citeck deps` no servidor.
- **Migração do PostgreSQL 17 para o 18**, a partir do diálogo «Dependências» ou com `citeck deps upgrade postgres`. O namespace é parado, os dados são exportados, é criado um novo cluster num volume **novo**, os dados são restaurados e verificados e o namespace passa a usá-lo — com progresso em cada passo. Qualquer falha é revertida automaticamente para os dados anteriores.
- **O RabbitMQ e o ZooKeeper também podem ser migrados** — a partir do mesmo diálogo, ou com `citeck deps upgrade rabbitmq` e `citeck deps upgrade zookeeper`. O volume de dados é copiado e é a cópia que é atualizada, pelo que o volume em que o namespace corre é apenas lido; no caso do RabbitMQ, é a única via de atualização que o próprio fabricante suporta.
- **Uma migração pode ser revertida.** `citeck deps rollback <dependência>`, ou o botão no diálogo «Dependências», coloca o namespace de novo na versão de onde veio, no volume de dados que a migração manteve. O launcher pede confirmação e diz com clareza o que isso custa: tudo o que foi escrito desde a migração fica no volume mais recente e nunca mais é lido, e depois não há caminho de regresso para a frente. A reversão é de um só passo e a oferta desaparece assim que a usar ou apagar o volume mantido.
- O volume de dados anterior **é mantido** após uma migração bem-sucedida. Os volumes de dados são numerados por migração: uma migração concluída coloca os dados no volume seguinte (`rabbitmq2` → `rabbitmq3`) e o anterior fica na página «Volumes» — elimine-o quando estiver satisfeito com o resultado.
- Se ainda existir um volume de destino de uma tentativa anterior, o launcher mostra o seu tamanho e versão e só o elimina depois da sua confirmação.

## Alterações
- A versão que o launcher escolhe por si não se move: os namespaces novos continuam a ser criados com PostgreSQL 17, tal como antes. O PostgreSQL 18 vem do **bundle** — quando um bundle o oferece, o launcher mantém os dados existentes no 17, avisa que o 18 está disponível e deixa-o executar a migração quando quiser.
- As atualizações do Keycloak e do MongoDB são comunicadas mas ainda não executadas — aguardam uma versão do launcher capaz de as migrar.
- Nem todas as atualizações podem ser feitas num só passo. O RabbitMQ segue a matriz de atualização do próprio fabricante (4.1 → 4.3, por exemplo, não é permitido diretamente): o launcher di-lo e indica a versão pela qual é preciso passar primeiro, em vez de sugerir que um launcher mais recente resolveria o caso. Dados do ZooKeeper anteriores à 3.5 são recusados por um motivo do mesmo género.
- Quando o bundle oferece uma versão **mais antiga** do que aquela em que os seus dados correm, o launcher passa a dizê-lo tal como é, em vez de o comunicar como uma atualização disponível — e se o seu namespace migrou precisamente a partir dessa versão, a mensagem aponta-lhe a reversão.
- Alterar à mão a versão de uma dependência passa a ter uma resposta adequada. É recusada enquanto existirem dados que essa versão não consegue aceitar, e a mensagem indica onde está o caminho de volta (o volume mantido, ou o facto de não haver nenhum). É permitida quando o volume de dados foi eliminado — o caso em que não havia nada que valesse a pena guardar — e o launcher regista então a versão que escolheu. Abaixo da versão mais antiga dessa dependência com que a plataforma é testada, é recusada haja ou não dados; e sobre dados existentes o launcher já não recua de todo uma dependência, incluindo a reversão de uma correção.
- Iniciar, recarregar ou eliminar um namespace é recusado enquanto decorre um snapshot ou uma migração de dependência, e a mensagem indica qual deles.
- O `citeck edit` já não perde o seu trabalho: se o daemon não conseguir aplicar a edição — está a decorrer outro recarregamento, o Docker está indisponível, o daemon reiniciou —, o seu texto é guardado e é impresso o comando para o voltar a aplicar.
- Corrigido: um launcher iniciado num perfil novo — uma instalação nova, ou uma cuja base de dados local não foi mantida — deixa de eliminar os contentores e os volumes de dados de namespaces que não conhece.
