## 新功能
- **RAG 语义搜索。** Enterprise bundle 现在提供 `rag` 应用，用于对知识库进行语义搜索，默认关闭。启动它会自动拉起 Qdrant 向量数据库，并为 AI 助手开启知识库访问；关闭状态下的 `rag` 依然不占用额外内存——Qdrant 甚至都不会被创建。Community bundle 不受影响，既不会出现 `rag`，也不会出现 Qdrant。
- **Qdrant 现在是受管理的依赖，并有专属迁移。** 启动器会固定向量索引实际运行的版本，因此提供了更新次版本的 bundle 会被拦下并上报，而不是被静默应用——Qdrant 只保证跨一个次版本读取自己的存储，跳过次版本不受支持。`citeck deps upgrade qdrant` 随后迁移索引：复制数据卷，升级这份「副本」，核对每个集合、别名和点数，之后才切换——原始卷全程只读不写，`citeck deps rollback qdrant` 可以退回到它。有一个后果需要知晓：数据卷现在叫 `qdrant2` 而不是 `qdrant_storage`，因此曾用预发布版本跑过 `rag` 的环境会以空索引启动，需要重新建立索引。
- **网页应用依赖可通过配置指定。** 网页应用的 `dependsOn` 现在可以通过 workspace 的 `webapps[].defaultProps.dependsOn` 和 namespace 的 `webapps.<id>.dependsOn` 扩展——配置的依赖会追加到内置依赖之上，而不是替换它们。`dependsOn` 出现循环依赖时，生成现在会以明确的错误失败，而不是让相关应用永远等待下去。
- bundle `dependencies:` 段中的基础设施镜像现在可以写成版本列表。最后一个是目标版本，之前的每一个
  都是启动器为到达目标而经过的中间步骤——全部在一次迁移中完成。这样，供应商不支持一步完成的
  升级，现在无需手动编辑即可达成。数据卷只复制一次，并逐级提升；原始数据保持不变，回滚方式也不变。

- **Bundle 现在可以声明所需的最低启动器版本。** 如果创建或编辑命名空间时选择的 bundle 需要比当前启动器更新的版本，操作将被拒绝，提示中会说明需要升级到的启动器版本。已经在运行此类 bundle 的命名空间不受影响，选择「LATEST」时始终会选取当前启动器能够运行的最新 bundle。
- **当 bundle 仓库中存在更新版本时，命名空间设置的齿轮图标会显示一个小圆点** —— 绿色表示当前启动器可以运行该版本，琥珀色表示需要先升级启动器。将鼠标悬停在图标上可查看具体版本及下一步操作。

## 变更
- **依赖被停止后，依赖它的应用不再绕过它启动。** 以前，某个应用的依赖被手动停止后，该应用仍会启动，随后在健康检查中失败。现在它会等待，并在状态中显示正在等待什么；依赖启动后即可继续。
- **bundle 中固定的镜像不再能被 workspace 或 namespace 配置覆盖。** 现在 bundle 始终优先；如需在某个 stand 上使用不同镜像，请显式使用 `citeck edit <app>`。仍试图通过配置覆盖镜像的情况，现在会记录为警告，而不是悄悄生效。
- **启动时的清理不再删除数据。** 桌面启动器启动时会删除它无法归属的命名空间遗留的容器——这正是为活动命名空间腾出所需端口的手段——而现在它不再动这些命名空间的具名卷和网络。此前它也会一并悄悄删除，可能抹掉同一台机器上服务器安装或第二个启动器配置所属的运行中环境。现在只有您亲手输入的操作才会释放磁盘空间：删除命名空间或工作区，或者 `citeck clean --volumes --force`——在您确认之前它只是试运行。
- **`citeck clean --volumes` 现在能看到 Docker 具名卷**，桌面命名空间的全部数据都存放在其中。它此前只扫描服务器模式的卷目录，因此在上述变更之后，已删除的桌面命名空间的磁盘将无人回收。
- **被您停止的依赖所阻塞的命名空间现在报告 STALLED**，而不是 STARTING。running 表示命名空间完整可用；stalled 表示出现了不会自行消失的问题，而有意的阻塞正属此类。有两点后果需要预先考虑：在 stalled 的命名空间上 `citeck deps upgrade` 会被拒绝；只要该依赖仍处于分离状态，命名空间状态指标与 `/health` 就会显示为不健康——重新启动它（`citeck start <app>`），命名空间会自行回到 running。

## 修复
- **切换 alfresco 现在会重新生成 namespace**，与 onlyoffice 和 ai 自 1.4.1 起的行为一致。以前手动停止/启动 alfresco 后，代理会继续按与事实不符的状态（可用或不可用）处理它，直到下一次无关的 reload 才会更正。
- **`citeck stop <基础设施依赖>` 不再卡死整个命名空间。** 停止 zookeeper、rabbitmq 或 postgres 会让命名空间永远停留在 STARTING——这会悄悄关闭整个命名空间的协调器和所有应用的存活探针——而 `citeck start` 则在等待一个永远不会到来的状态。现在无论依赖链有多少环，阻塞都能被识别，所有等待都会在此结束，状态行指出的是您真正需要启动的应用（被您停止的那个），而不是无法启动的中间应用。
- **`namespace.yml` 中 `dependsOn` 的拼写错误现在是一个错误**，而不再悄悄删除写下它的 Web 应用以及所有依赖该应用的内容。工作区层的行为有意保持原样——该文件由工作区的所有命名空间共享——但现在会记录一条指明缺失目标的警告。
- **Qdrant 会发布其健康检查所用的端口**，否则它在桌面环境中永远无法离开 STARTING，而 `rag` 会一直等待它。
- **未加引号的数字镜像标签不再让应用从 bundle 中消失。** 在 YAML 中 `tag: 17.10` 是数字而非字符串：在 `dependencies:` 段之外，启动器把它读成空标签，并悄悄丢弃整个应用——没有镜像、没有容器、也没有日志。现在各处的标签都从 YAML 原文读取，`17.10` 仍是 `17.10`；仍然无法读取的镜像会写入日志，而不是被悄悄跳过。
- **「Force Update」现在会真正重新拉取工作区仓库。** 此前在上次同步后的一小时内，该按钮会返回成功却不拉取任何内容，刚推送的 bundle 版本既不会出现在版本列表中，也不会触发「有更新的 bundle」提示。
- **bundle 列表旁的 ↻ 按钮现在刷新启动器真正读取的仓库。** 当 bundle 仓库位于工作区仓库内部（常见布局）时，它会为每个仓库克隆一份无人读取的副本并提示成功，而界面上没有任何变化。
- **在未运行的命名空间上启动单个应用时会明确说明原因。** 命名空间处于停止状态时，行内的启动按钮会被禁用并给出说明；此前它要么提示应用不存在，要么接受点击却什么也不做。将已分离的应用重新接入依然可用——它会随命名空间一起启动。
- **不能再基于仓库中没有的 bundle 版本创建命名空间。** 这样的命名空间启动后完全没有 Citeck 服务，只有第三方基础设施，因为没有任何可回退的内容。
- **重新加载时解析到的 bundle 会被记住。** 通过编辑命名空间选择的 bundle 在下次启动启动器之前不会进入缓存；若期间它从仓库中消失，命名空间就会空着启动。
