## 新機能
- **RAG によるセマンティック検索。** Enterprise バンドルに、ナレッジベースをセマンティック検索する `rag` アプリが追加されました。デフォルトでは無効です。起動すると Qdrant ベクトルデータベースが自動的に立ち上がり、AI アシスタントのナレッジベースへのアクセスが有効になります。無効な `rag` は引き続き余分なメモリを消費しません — Qdrant 自体が作成されないためです。Community バンドルには影響がなく、`rag` も Qdrant も現れません。
- **Qdrant が管理対象の依存関係になり、専用のマイグレーションが付きました。** ランチャーはベクトルインデックスが実際に動作しているバージョンをピン留めします。そのため、より新しいマイナーを提示するバンドルは黙って適用されず、保留されて通知されます — Qdrant が自身のストレージの読み取りを保証するのはマイナー1つ分だけで、マイナーを飛ばすことはサポートされていません。`citeck deps upgrade qdrant` はインデックスを移行します。データボリュームをコピーし、その「コピー」をアップグレードし、すべてのコレクション・エイリアス・ポイント数を照合してから切り替えます — 元のボリュームには一切書き込まれず、`citeck deps rollback qdrant` でそこに戻れます。知っておくべき影響が1つあります。データボリューム名が `qdrant_storage` から `qdrant2` に変わったため、リリース前のビルドで既に `rag` を動かしていたスタンドは空のインデックスで起動し、再インデックスが必要になります。
- **ウェブアプリの依存関係を設定可能に。** ウェブアプリの `dependsOn` を、ワークスペースの `webapps[].defaultProps.dependsOn` とネームスペースの `webapps.<id>.dependsOn` から拡張できるようになりました。設定した依存関係は組み込みの依存関係に追加され、置き換えることはありません。`dependsOn` が循環している場合、生成はいまや明確なエラーで失敗します。以前は関係するアプリが永遠に待ち続けていました。
- バンドルの `dependencies:` セクションのインフラ用イメージを、バージョンのリストとして書けるように
  なりました。最後の要素が目標で、それ以前の要素はランチャーが目標へ到達するために経由するステップ
  です — すべて1回の移行で処理されます。ベンダーが1ステップでのサポートを提供していないアップグレー
  ドも、手作業での編集なしに到達可能になります。データボリュームは一度だけコピーされ、各ステップを
  経て引き上げられます。元のボリュームはそのままで、ロールバックの仕組みも変わりません。

## 変更点
- **停止した依存先があっても、依存元のアプリはそれを無視して起動しなくなりました。** 以前は、依存先アプリが手動で停止されていても依存元アプリは起動を試み、その後ヘルスチェックに失敗していました。今は待機し、ステータスに何を待っているかを表示します。依存先が起動すると処理が進みます。
- **バンドルで固定されたイメージは、ワークスペースやネームスペースの設定で上書きできなくなりました。** これからは常にバンドルが優先されます。特定のスタンドで別のイメージを使いたい場合は、明示的に `citeck edit <app>` を使ってください。イメージの上書きを試みる設定は、黙って適用される代わりに警告としてログに記録されるようになりました。
- **起動時のクリーンアップがデータを削除しなくなりました。** デスクトップランチャーは起動時、把握できない名前空間の残存コンテナを削除します（アクティブな名前空間が必要とするポートを解放するのがその目的です）が、その名前付きボリュームとネットワークには手を触れなくなりました。以前はそれらも黙って削除しており、同じマシン上のサーバーインストールや 2 つ目のランチャープロファイルの稼働中スタンドを消し去ることがありました。ディスク容量を解放するのは、名前空間やワークスペースの削除、あるいは確認するまでは何も消さない `citeck clean --volumes --force` など、ご自身で入力した操作だけになりました。
- **`citeck clean --volumes` が Docker の名前付きボリュームを見るようになりました。** デスクトップの名前空間はそこに全データを保持しています。以前はサーバーモードのボリュームディレクトリしか走査しなかったため、上記の変更のあとでは削除済みデスクトップ名前空間のディスクを解放するものが存在しなくなっていました。
- **停止した依存関係に阻まれている名前空間は STARTING ではなく STALLED を報告するようになりました。** running は名前空間が健全で利用できることを意味し、stalled は自然には解消しない問題が起きたことを意味します。意図的な停止による阻害はまさに後者です。留意すべき影響が 2 つあります。stalled の名前空間では `citeck deps upgrade` が拒否されること、そして依存関係を切り離している間は名前空間ステータスのメトリクスと `/health` が「不健全」を示し続けること — 再び起動すれば（`citeck start <app>`）名前空間は自力で running に戻ります。

## 修正
- **alfresco の切り替えでネームスペースが再生成されるようになりました。** onlyoffice と ai では 1.4.1 からすでにこの動作でしたが、alfresco だけ抜けていました。以前は、手動での停止・起動の後もプロキシは実際とは異なる状態で alfresco が利用可能（または不可）だと扱い続け、無関係な次の reload まで直りませんでした。
- **`citeck stop <インフラ依存関係>` が名前空間全体を固めることはなくなりました。** zookeeper、rabbitmq、postgres を停止すると名前空間は永久に STARTING のままになり、名前空間全体のリコンサイラと全アプリの liveness プローブが黙って無効化される一方、`citeck start` は決して訪れない状態を待ち続けていました。阻害は依存関係チェーンが何段であっても認識されるようになり、すべての待機がそこで終了し、ステータス行には実際に起動すべきアプリ（あなたが停止したもの）が表示されます — 起動できない中間のアプリではありません。
- **`namespace.yml` の `dependsOn` の綴り誤りはエラーになりました。** 以前はそれを記述したウェブアプリと、そこに依存するものすべてを黙って削除していました。ワークスペース層の挙動は意図的に従来どおりです（このファイルはワークスペースの全名前空間で共有されるため）が、欠けている対象名を含む警告がログに出るようになりました。
- **Qdrant が自身のヘルスチェックに使うポートを公開するようになりました。** これがないとデスクトップのスタンドでは STARTING から抜け出せず、`rag` がいつまでも待ち続けていました。
- **引用符のない数値のイメージタグでアプリケーションがバンドルから消えることはなくなりました。** YAML では `tag: 17.10` は文字列ではなく数値です。`dependencies:` セクションの外ではランチャーがこれを空のタグとして読み、アプリケーション全体を黙って捨てていました — イメージもコンテナもログ行もないままです。タグはどこでも YAML のテキストから読まれるようになったため `17.10` は `17.10` のままとなり、それでも読めないイメージは黙って無視されずログに記録されます。
